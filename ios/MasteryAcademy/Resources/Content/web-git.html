Git & GitHub Field Guide

Git & GitHub Field Guide

From your first commit to rebases, rescues, pull requests and working safely with AI coding tools. Every chapter uses one small practice project, a recipe box, so you can type along.

What Git is, in one picture

Git saves snapshots of your project. Each snapshot is a commit. Git keeps every commit, so you can go back, compare, and work on several ideas side by side. GitHub is a website that stores a copy of your Git project so other people (and your other machines) can share it.

One-time setup

git --version                          # check it is installed
git config --global user.name  "Your Name"
git config --global user.email "you@example.com"
git config --global init.defaultBranch main
git config --global pull.rebase true   # optional: keeps history straight when you pull

The loop you will repeat every day

git status                 # where am I, what changed?
git diff                   # what exactly changed?
git add recipes/chai.txt   # choose what goes in the next snapshot
git commit -m "Add cardamom to chai"
git push                   # share it

Words you will hear

WordPlain meaning
Repository (repo)A project folder that Git is tracking. The history lives in the hidden .git folder.
CommitOne saved snapshot, with a message, an author, and a unique ID (the hash, like a1b2c3d).
BranchA movable name that points to a commit. Making a branch copies nothing; it just adds a name.
HEAD"You are here." Usually it points at the branch you are on.
RemoteAnother copy of the repo, usually on GitHub. The default name is origin.
CloneDownload a full copy of a remote repo, including all history.
Pull request (PR)A GitHub page that says "please review my branch and merge it."
Merge conflictTwo branches changed the same lines. Git stops and asks you to pick.

Commits, branches and merges

Every commit remembers its parent. That chain is the history. A branch is a label on one commit, and it moves forward each time you commit on it.

Branching commands

git branch                    # list branches
git switch -c add-dosa        # create and move to a new branch
git switch main               # move back
git switch -                  # jump to the previous branch
git merge add-dosa            # bring add-dosa into the branch you are on
git branch -d add-dosa        # delete a merged branch

Merge or rebase?

Both combine work. Merge keeps the true shape of history and adds one merge commit. Rebase replays your commits on top of the latest main, which gives a straight line but creates new commits with new IDs.

The one rule of rebase: do not rebase commits that other people already pulled. Rebase your own unshared branch freely.

Solving a merge conflict

When two branches change the same line, Git writes both versions into the file between markers and stops.

<<<<<<< HEAD
- 1 tsp jaggery
=======
- half tsp sugar
>>>>>>> less-sugar
  1. Run git status to see which files are in conflict.
  2. Open each file, keep the lines you want, and delete the three marker lines.
  3. git add <file> to mark it solved, then git commit (or git rebase --continue during a rebase).
  4. Want out? git merge --abort or git rebase --abort puts everything back.

Working with a remote

git clone git@github.com:you/recipe-box.git   # download a repo
git remote -v                                  # see where origin points
git fetch                                      # download new commits, change nothing locally
git pull                                       # fetch + merge (or rebase) into your branch
git push -u origin add-dosa                    # first push of a new branch
git push                                       # later pushes

git fetch is always safe. If you are unsure what a pull will do, fetch first and look with git log --oneline main..origin/main.

Parking work: stash

git stash push -m "wip peanuts"   # save uncommitted edits and clean the folder
git stash -u                      # also include brand-new files
git stash list
git stash pop                     # bring the latest one back

Marking releases: tags

git tag -a v1.0 -m "First menu"
git push origin v1.0

          Undo almost anything

          Pick the undo by answering two questions: is it committed, and has anyone else seen it?

          What each reset mode touches

          CommandBranch pointerStaging areaWorking filesUse it when
          git reset --soft HEAD~1moves backkeptkeptYou want to redo the last commit with the same changes.
          git reset HEAD~1 (mixed)moves backclearedkeptYou want to re-choose what to stage.
          git reset --hard HEAD~1moves backclearedoverwrittenYou want the commit and its changes gone.

          --hard throws away uncommitted edits, and those cannot be recovered. Committed work can, through the reflog.

          Everyday undo commands

          git restore chai.txt              # discard unstaged edits in one file
git restore --staged chai.txt     # unstage, keep the edits
git commit --amend                # fix the last message or add a forgotten file
git revert a1b2c3d                # new commit that cancels a1b2c3d (safe after push)
git restore --source=HEAD~3 chai.txt   # get an old version of one file
git clean -fdn                    # preview which untracked files would be deleted

          The rescue: reflog

          git reflog                        # every move HEAD made, newest first
git reset --hard "HEAD@{1}"       # go back to where HEAD was one move ago
git switch -c rescued a1b2c3d     # or put a branch on a lost commit

          Deleted a branch by mistake? Find its last commit in the reflog and run git branch name <hash>. Entries stay for about 90 days by default.

          Finding the commit that broke something: bisect

          git bisect start
git bisect bad                    # current commit is broken
git bisect good v1.0              # this old one worked
# Git checks out the middle commit. Test, then answer:
git bisect good    # or    git bisect bad
git bisect reset                  # when it names the culprit
git bisect run ./test.sh          # or let a script answer for you

          Bisect halves the search each step, so 1,000 commits take about 10 checks.

          GitHub: sharing and reviewing

          Teams rarely push straight to main. You push a branch, open a pull request, checks run, someone reviews, and then it merges.

          Connect your machine once (SSH)

          ssh-keygen -t ed25519 -C "you@example.com"
cat ~/.ssh/id_ed25519.pub      # paste into GitHub → Settings → SSH and GPG keys
ssh -T git@github.com          # should greet you by username

          Put the practice project on GitHub

          gh auth login                                  # GitHub CLI, once
gh repo create recipe-box --private --source=. --push
# without gh: create an empty repo on github.com, then
git remote add origin git@github.com:you/recipe-box.git
git push -u origin main

          A pull request from the terminal

          git switch -c add-upma
# edit, add, commit
git push -u origin add-upma
gh pr create --fill            # title and body from your commits
gh pr status                   # checks and reviews
gh pr checkout 12              # try someone else's PR locally
gh pr merge --squash --delete-branch

          Automatic checks: GitHub Actions

          Save this as .github/workflows/ci.yml. It runs on every pull request.

          name: CI
on:
  pull_request:
  push:
    branches: [main]
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: ./run-tests.sh

          Settings worth turning on

          • Branch protection on main: require a pull request, one approval, and passing checks.
          • CODEOWNERS file: the right reviewers are asked automatically.
          • Pull request template at .github/pull_request_template.md: what changed, how it was tested, screenshots.
          • Secret scanning and push protection: GitHub blocks pushes that contain known key formats.
          • Write Closes #12 in the PR body and issue 12 closes when the PR merges.

          Using Git with AI coding tools

          AI assistants (Claude Code, Cursor, Copilot, Codex) edit many files quickly. Git is what makes that safe: every AI change becomes a diff you can read, and one command takes it back.

          Habits that keep you safe

          • Commit before you prompt. A clean git status means the whole AI change is exactly git diff.
          • One task, one branch. Easy to review, easy to throw away.
          • Stage in pieces with git add -p. You approve each hunk, so nothing slips in unread.
          • You approve the risky commands. push --force, reset --hard, clean -fd and branch deletes should need your yes.
          • Keep secrets out. Put .env in .gitignore before the first commit, and check git diff --staged for keys.
          • Say who wrote it. Many teams add a Co-Authored-By: line to AI-assisted commits.

          This Mac already follows the fourth habit: a hook in ~/ai-handoff/hooks stops an AI session from running git commit unless you ask for it in that message.

          Prompts that work well

          You wantGive the AIAsk
          A commit messagegit diff --staged"Write a commit message: imperative subject under 60 characters, then why."
          A PR descriptiongit log main..HEAD and git diff main...HEAD"Summarise what changed, why, and how to test it."
          Help with a conflictThe conflicted file and both branch names"Explain what each side intended, then propose a merged version. Do not pick one side silently."
          To understand old codegit log -p --follow file or git blame -L 10,40 file"Why did these lines change over time?"
          To find a regressionA failing test command"Run git bisect with this test and tell me the first bad commit."
          To clean historygit log --oneline main..HEAD"Suggest how to squash these into logical commits. Show the plan first; do not run it."
          To recover from a mistakegit status and git reflog -15"I did X and lost Y. What is the safest way back?"

          Parallel AI sessions: worktrees

          A worktree is a second folder on a different branch that shares the same repository. Two AI sessions can work at once without overwriting each other's files.

          git worktree add ../recipe-box-hotfix -b hotfix   # new folder, new branch
git worktree list
git worktree remove ../recipe-box-hotfix          # when the branch is merged
claude --worktree add-upma                        # Claude Code: start a session in its own worktree

          AI on GitHub itself

          • Claude Code can run the whole loop when you ask in words: "commit this", "open a PR". It uses your git and gh.
          • @claude on pull requests: run /install-github-app in Claude Code to add the GitHub Action, then mention @claude in a PR or issue comment to ask for a review or a fix.
          • Copilot and Cursor have a button that drafts a commit message from the staged diff. Read it; it describes what changed, and you often need to add why.
          • AI review is a first pass. A person still approves the merge.

          Tell the AI your Git rules

          Put the rules in the file your tool reads at the start of each session (CLAUDE.md, AGENTS.md, or Cursor rules).

          # Git rules for this repo
- Never commit or push unless I ask.
- Branch names: feature/<ticket>-short-name
- Commit subject: imperative, under 60 characters.
- Never force-push, never rewrite main.
- Do not touch generated files or .env.
