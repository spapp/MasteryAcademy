SQL, from first query to production

SQL is the language you use to ask a database questions and to change what it stores. It is fifty years old (IBM built the first version in the 1970s) and it is still the language behind almost every backend, every analytics dashboard, and most AI products that need to remember anything.

This academy takes you from "what is a table" to reading query plans, designing schemas, handling concurrent writes, and running vector search for an AI feature. It teaches PostgreSQL, because that is the database you are most likely to meet in backend and AI work, and it points out where MySQL, SQLite and SQL Server differ.

What a database is

A database is a program that stores data safely and answers questions about it. "Safely" is the hard part: it must not lose data when the power fails, and it must stay correct when a thousand requests arrive at once. That is why you do not just keep data in files.

A relational database stores everything in tables. A table has columns (each with a name and a type) and rows (each row is one thing: one product, one order). You talk to it by sending text in a language called SQL, and it sends rows back.

In plain words

A table looks like a spreadsheet tab, with three strict rules a spreadsheet does not have. Every value in a column has the same type. Every row can be identified by its key. And rules you declare (this column may not be empty, this id must exist in that other table) are enforced on every write, by the database, for every program that connects.

You already know this from Swift and Dart

In Swift you keep an array of structs in memory and filter it with products.filter { $0.price < 70 }. SQL is the same idea with two differences: the data lives in another process (often another machine), and you say what you want, not how to loop. The database decides how.

In backend work

The database is the one place every API instance agrees on. Your service is usually stateless; the truth about orders, stock and money lives in tables.

In AI work

A model has no memory between calls. Anything it should remember or look up (the conversation so far, the user's documents, product facts) is fetched from a database and placed in the prompt.

Check yourself

What is the difference between a row and a column?

A column is one property that every record has, with a fixed name and type (price, an integer). A row is one record: one product with a value for each column.

Why not store application data in JSON files?

Files give you no safe concurrent writes, no way to change several things atomically, no enforced rules, and no fast lookup without reading everything. A database gives all four, plus recovery after a crash.

What does "declarative" mean for SQL?

You describe the result you want. The database's planner chooses the method: which index to use, which table to read first, how to join. The same query can run differently as the data grows.

What is a primary key?

The column (or set of columns) whose value identifies exactly one row. It is unique and never NULL.

SELECT: choosing columns

SELECT lists the columns you want; FROM names the table. You can also compute new columns from existing ones and give them a name with AS. The result of a query is itself a table: it has columns and rows, and nothing in the stored table changes.

SELECT * means "every column". It is fine while exploring. In application code, name the columns: your code will not break when someone adds a column, and the database does not have to fetch data you never use.

DISTINCT removes duplicate rows from the result.

Where people get hurt

  • DISTINCT applies to the whole row, not to the first column. SELECT DISTINCT city, name returns every distinct pair.
  • Strings use single quotes: 'Mumbai'. Double quotes mean an identifier (a column or table name) in standard SQL and PostgreSQL.
  • Dividing two integers gives an integer in PostgreSQL and SQLite: 7 / 2 is 3. Multiply by 1.0 or cast when you want decimals.

In backend work

An endpoint that returns a list should select only the fields its response needs. On wide tables this alone can halve response time.

In AI work

When you put query results into a prompt, every column costs tokens. Select the few columns the model needs and name them clearly, because the model reads the column names too.

Check yourself

Does a SELECT change the table?

No. It produces a new result set. Only INSERT, UPDATE, DELETE and DDL change stored data.

Why avoid SELECT * in application code?

It fetches columns you do not use, it prevents index-only scans, and the shape of the result changes silently when a column is added or reordered.

What does SELECT 7 / 2 return in PostgreSQL, and how do you get 3.5?

3, because both operands are integers. Use 7 / 2.0 or 7::numeric / 2.

What is an alias?

A name you give to an output column or a table with AS. It exists only for that query.

WHERE: filtering rows

WHERE keeps the rows for which a condition is true and drops the rest. Conditions compare values (=, <>, <, >=), and you combine them with AND, OR and NOT.

Where people get hurt

  • Without the brackets above, a OR b AND c is read as a OR (b AND c). That returns every placed order, whatever its slot.
  • BETWEEN '2026-02-01' AND '2026-02-28' on a timestamp misses almost all of 28 February, because the upper bound means midnight at the start of that day. Use >= '2026-02-01' AND < '2026-03-01'.
  • LIKE '%text%' with a leading % cannot use an ordinary index, so on a large table it reads every row.
  • In PostgreSQL LIKE is case-sensitive; use ILIKE for case-insensitive matching. In MySQL and SQLite LIKE is case-insensitive for ASCII by default.

In backend work

Almost every endpoint has a WHERE with the caller's id in it (WHERE customer_id = $1). Forgetting that filter is how one user sees another user's orders.

In AI work

In retrieval you filter before you rank: WHERE tenant_id = $1 AND doc_type = 'policy' first, similarity second. The filter is your access control.

Check yourself

Why is >= start AND < next_start safer than BETWEEN for time ranges?

BETWEEN includes both ends, and a date written without a time means midnight. The half-open form includes the whole last day and never counts a row in two adjacent ranges.

What does WHERE status = 'placed' OR status = 'cancelled' AND slot IS NULL return?

All placed orders, plus cancelled orders with no slot, because AND is evaluated before OR.

How do you find products whose name ends in "1 kg"?

WHERE name LIKE '%1 kg'.

Where does the WHERE filter run: in your app or in the database?

In the database, before rows are sent. Filtering in the app means transferring rows only to discard them.

ORDER BY and LIMIT

A table has no order. If you need rows in a particular order you must say so with ORDER BY, every time. LIMIT then cuts the result to the first few rows, and OFFSET skips some first.

Where people get hurt

  • LIMIT without ORDER BY returns "some" rows. It may look stable for months and then change after an update or an upgrade.
  • If the sort column has ties, the order among tied rows is not defined. For pagination add a unique column as the last sort key: ORDER BY placed_at DESC, id DESC.
  • NULLs sort last in ascending order in PostgreSQL and first in SQLite and MySQL. Write NULLS LAST or NULLS FIRST when it matters.
  • OFFSET 100000 still reads and throws away 100,000 rows. The performance track shows the fix (keyset pagination).

In backend work

Every list screen is ORDER BY … LIMIT …. "Latest 20 orders" is ORDER BY placed_at DESC, id DESC LIMIT 20.

In AI work

Retrieval for RAG is literally ORDER BY distance LIMIT k. The top-k chunks you send to the model are an ORDER BY and a LIMIT.

Check yourself

A query has no ORDER BY but always returns rows by id. Can you rely on it?

No. The order is an accident of how rows are stored and which plan was chosen. It can change after updates, a vacuum, or when the planner picks a different index.

Why add id as a last sort key when paginating by placed_at?

Two orders can share a timestamp. Without a tie-breaker the same row can appear on two pages or on none.

What does LIMIT 10 OFFSET 20 return?

Rows 21 to 30 of the sorted result.

NULL: the value that is not a value

NULL means "unknown" or "not applicable". It is not zero and it is not an empty string. A cancelled order has no delivery slot, so its slot is NULL.

Because NULL means unknown, any comparison with it is also unknown: is an unknown slot equal to 'morning'? Nobody can say. SQL therefore has three truth values: true, false and unknown. WHERE keeps only the rows where the condition is true.

So WHERE slot <> 'morning' silently leaves out orders with no slot. To include them, say it: WHERE slot <> 'morning' OR slot IS NULL.

COALESCE(a, b, c) returns the first argument that is not NULL. Use it to supply a default.

Where people get hurt

  • = NULL is never true. Always write IS NULL or IS NOT NULL.
  • NOT IN with a NULL in the list returns no rows at all. WHERE id NOT IN (SELECT referred_by FROM customers) is empty, because some customers have referred_by NULL. Use NOT EXISTS instead (shown in the subqueries lesson).
  • COUNT(column) counts non-NULL values; COUNT(*) counts rows. They differ whenever the column has NULLs.
  • NULL = NULL is unknown, yet GROUP BY and DISTINCT put all NULLs in one group. The two rules are different on purpose.
  • 'text' || NULL is NULL in PostgreSQL. One missing part blanks the whole string.

You already know this from Swift and Dart

NULL is like nil in an Optional, with one big difference. In Swift nil == nil is true. In SQL NULL = NULL is unknown. Think of each NULL as a separate sealed box: you cannot say two sealed boxes hold the same thing.

In backend work

Decide for every column whether it may be NULL, and add NOT NULL when it may not. A nullable column that "should never be null" will be null in production one day and crash a client that force-unwraps it.

In AI work

Missing values in data you feed a model or a metric distort results quietly: an average ignores NULL scores, so an evaluation with half the rows unscored can look better than it is. Count the NULLs first.

Check yourself

Why does WHERE slot <> 'morning' not return orders whose slot is NULL?

NULL <> 'morning' evaluates to unknown, and WHERE keeps only rows where the condition is true.

What is the difference between COUNT(*) and COUNT(email)?

COUNT(*) counts rows. COUNT(email) counts rows where email is not NULL.

Why can x NOT IN (subquery) return nothing?

If the subquery returns any NULL, x NOT IN (…, NULL) is x <> a AND x <> b AND x <> NULL, and the last part is unknown, so the whole condition can never be true.

What does COALESCE(NULL, NULL, 5, 7) return?

5, the first non-NULL argument.

Data types and casting

Every column has a type, and the type decides what you can store, how values compare and how much space they take. Choosing the right type is the cheapest correctness check you will ever add: a date column cannot hold "tomorrow-ish".

Where people get hurt

  • Store instants as timestamptz. Plain timestamp has no time zone, so "09:00" means different moments to servers in different regions. (The practice tables use plain timestamp only so they also load in SQLite.)
  • Date functions are the least portable part of SQL. date_trunc is PostgreSQL; MySQL uses DATE_FORMAT, SQLite uses strftime. The dialects lesson has a table.
  • An integer id overflows at about 2.1 billion. Busy event tables reach that. Use bigint for ids from the start.
  • Comparing a number with a string that holds a number ('10' < '9' as text) sorts alphabetically. Store numbers as numbers.

In backend work

Money as numeric or as integer paise, times as timestamptz in UTC, ids as bigint or uuid. These three choices prevent most data bugs that reach customers.

In AI work

Embeddings are vector(1536) or whatever your model outputs; the dimension is part of the type, so a vector from a different model is rejected instead of silently compared. Token counts and costs belong in exact types too.

Check yourself

Why is float wrong for money?

Binary floating point cannot represent most decimal fractions exactly, so sums drift by tiny amounts. Use numeric or integer minor units.

What is the difference between timestamp and timestamptz in PostgreSQL?

timestamptz stores an absolute instant (in UTC) and converts on input and output using the session time zone. timestamp stores the wall-clock digits with no zone, so its meaning depends on who reads it.

How do you write a cast in PostgreSQL and in standard SQL?

value::type is PostgreSQL shorthand; CAST(value AS type) works everywhere.

When would you choose uuid over bigint for a primary key?

When ids are created outside the database (offline clients, several services) or must not be guessable or reveal volume. bigint is smaller and keeps inserts in index order, so it is the default otherwise.

The order a query really runs in

You write SELECT first, but the database evaluates it near the end. Knowing the real order explains most beginner errors in one go: why WHERE cannot use an alias, why you cannot filter on COUNT(*) in WHERE, and why ORDER BY can use an alias.

The fix is to repeat the expression (WHERE price * stock > 5000) or to compute it one level down in a subquery or CTE and filter outside.

Where people get hurt

  • This is the logical order. The planner may physically do things differently (for example, filter while reading an index) as long as the result is the same.
  • A filter on a plain column belongs in WHERE, not HAVING. Both work, but WHERE removes rows before the expensive grouping.
  • Window functions are computed in step 5, after WHERE and GROUP BY. That is why you cannot filter on ROW_NUMBER() in the same WHERE.

In backend work

When a report query gives a wrong total, walk it in this order and run each stage on its own, exactly like the step-through above. The stage where the row count surprises you is the bug.

In AI work

Models that write SQL make precisely these mistakes: an alias in WHERE, an aggregate in WHERE, a window function filtered too early. Knowing the order lets you spot a wrong generated query in seconds.

Check yourself

Why does WHERE total > 100 fail when total is an alias defined in SELECT?

WHERE is evaluated before SELECT, so the alias does not exist yet.

What is the difference between WHERE and HAVING?

WHERE filters rows before grouping and cannot use aggregates. HAVING filters groups after grouping and can.

In which order are FROM, WHERE, GROUP BY, HAVING, SELECT, ORDER BY, LIMIT evaluated?

Exactly in that order: FROM/JOIN, WHERE, GROUP BY, HAVING, SELECT (with window functions, then DISTINCT), ORDER BY, LIMIT.

Can ORDER BY use a SELECT alias? Why?

Yes, because ORDER BY runs after SELECT.

Aggregates, GROUP BY and HAVING

An aggregate function turns many rows into one value: COUNT, SUM, AVG, MIN, MAX. On its own it summarises the whole table. With GROUP BY it summarises each group separately and returns one row per group.

The rule that trips everyone: once you group, each output row stands for many input rows, so every column in SELECT must be either in GROUP BY or inside an aggregate. Asking for placed_at next to COUNT(*) grouped by status makes no sense: which of the ten delivered orders' timestamps should it show?

Where people get hurt

  • MySQL in its old default mode accepts the ungrouped column and returns an arbitrary value from the group. The query runs and the answer is wrong. PostgreSQL's error is the better behaviour.
  • AVG of an integer column: PostgreSQL returns a decimal, SQL Server returns an integer. Cast first when moving between databases.
  • COUNT(*) over zero rows returns 0, but SUM over zero rows returns NULL. Wrap sums in COALESCE(SUM(x), 0) when the app expects a number.
  • FILTER is standard SQL and works in PostgreSQL and SQLite. In MySQL write SUM(CASE WHEN status = 'delivered' THEN 1 ELSE 0 END).

In backend work

Dashboards, badges ("3 items in cart"), limits ("5 orders per day"), and reports are all GROUP BY. One grouped query replaces a loop of per-user queries.

In AI work

Evaluation is aggregation: accuracy per prompt version, average latency per model, cost per tenant per day. GROUP BY model, prompt_version over a table of runs is how you decide which version ships.

Check yourself

Why can't you write WHERE COUNT(*) > 2?

WHERE runs before grouping, when no counts exist yet. Conditions on aggregates go in HAVING.

What must be true of every column in the SELECT list of a grouped query?

It is either listed in GROUP BY (or functionally dependent on it, such as other columns when you group by the primary key) or wrapped in an aggregate.

What do SUM and COUNT(*) return when no rows match?

SUM returns NULL; COUNT(*) returns 0.

How do you count delivered and cancelled orders in one query?

COUNT(*) FILTER (WHERE status = 'delivered') and the same for cancelled, or SUM(CASE WHEN … THEN 1 ELSE 0 END) where FILTER is not available.

Joins: combining tables

Data is split across tables on purpose (the design track explains why). A join puts it back together for one query: for each row on the left, find the rows on the right that satisfy a condition, usually "your foreign key equals my primary key".

The join type only decides what happens to rows that find no partner.

Read that result carefully. Every customer appears. Those with a cancelled order show it; the others show NULL. Now the most useful trick in SQL: keep only the rows that found no partner.

Where people get hurt

  • ON versus WHERE with LEFT JOIN. A condition on the right table placed in WHERE (for example WHERE o.status = 'cancelled') throws away the NULL-padded rows and silently turns your LEFT JOIN into an INNER JOIN. Put it in ON to keep all left rows.
  • Forgetting the ON condition, or joining on the wrong column, gives a cross product. If a result has far more rows than either table, look at the join condition first.
  • When two tables share a column name (id), always qualify it: o.id, c.id.
  • A join returns one row per matching pair. A customer with four orders appears four times. That is correct, and it is the source of the double-counting bug in the next lesson.

In backend work

An order detail screen is one query joining orders, order_items and products, instead of one call per item. Doing it in one query is how you avoid the "N+1 queries" problem.

In AI work

Retrieval joins too: chunks join documents join permissions, so the model only sees text the user is allowed to read. Feature tables for a model are built by joining facts about a user from many tables into one row.

Check yourself

What is the only difference between INNER JOIN and LEFT JOIN?

What happens to left rows without a match. INNER drops them; LEFT keeps them and fills the right table's columns with NULL.

How do you find rows in A that have no match in B?

A LEFT JOIN B ON … WHERE B.key IS NULL, or WHERE NOT EXISTS (SELECT 1 FROM B WHERE …).

You wrote FROM customers c LEFT JOIN orders o ON … WHERE o.status = 'delivered' and customers without orders vanished. Why?

For those customers o.status is NULL, the WHERE condition is unknown, and the row is dropped. Move the condition into the ON clause.

How many rows does a CROSS JOIN of a 4-row and a 5-row table return?

20.

Joining many tables, self joins, and double counting

You can chain joins: each one adds another table to the working set. Follow the foreign keys in the diagram on the start page and the path writes itself: customers → orders → order_items → products.

A self join joins a table to itself. Give the table two different aliases and treat them as two tables. Here referred_by points at another row of customers.

The double-counting trap

Order 106 has three items and two payment attempts. Join orders to both child tables and every item is paired with every payment: 3 × 2 = 6 rows. Any SUM over that is wrong.

Where people get hurt

  • Before you aggregate over a join, ask "how many rows per order does this produce?" If the answer is not one per thing you are summing, the sum is wrong.
  • COUNT(DISTINCT o.id) hides the symptom for counts. It does nothing for SUM.
  • Joining on a non-unique column multiplies rows the same way. Join on keys.

In backend work

Revenue and wallet reports go wrong exactly here. An order summary endpoint that joins items, payments and refunds in one flat query will overstate money.

In AI work

Training sets and evaluation sets built with a fan-out join contain duplicated examples, which inflates metrics and leaks the same row into train and test. Check row counts after every join.

Check yourself

Orders has one row for order 7, order_items has 4 rows and payments has 2 rows for it. How many rows does joining all three produce for order 7?

8. Each of the 4 items is paired with each of the 2 payments.

How do you total two different child tables for the same parent correctly?

Aggregate each child table to one row per parent in its own subquery or CTE, then join those results to the parent.

What is a self join used for?

Relating rows of the same table: an employee and their manager, a customer and their referrer, a category and its parent.

Why use LEFT JOIN in the referral query?

Customers who were not referred have NULL in referred_by. An inner join would drop them.

Subqueries and EXISTS

A subquery is a query inside another query. It can stand in three places: where a single value is expected, where a list is expected, and where a table is expected.

A correlated subquery refers to the outer row, so in principle it runs once for each outer row. EXISTS is the common case: it asks "is there at least one row such that…" and stops at the first hit.

Where people get hurt

  • A scalar subquery must return at most one row. If it returns two, the query fails at run time, possibly months later when the data changes.
  • Prefer NOT EXISTS to NOT IN: it behaves correctly when NULLs are present (see the NULL lesson).
  • A correlated subquery in SELECT that runs for every row of a big result can be slow. A join or a window function usually does the same work in one pass.
  • PostgreSQL's planner turns most IN and EXISTS subqueries into joins by itself. Write whichever reads more clearly, then check the plan if it is slow.

In backend work

"Show the Reorder button only if the user has a delivered order" is EXISTS. Permission checks ("does a membership row exist for this user and this team") are EXISTS too.

In AI work

"Documents that have no embedding yet" is WHERE NOT EXISTS (SELECT 1 FROM chunks …), the query your ingestion worker runs to find its backlog.

Check yourself

What is a correlated subquery?

A subquery that uses a value from the outer query's current row, so its result depends on that row.

Why is EXISTS often faster than COUNT(*) > 0?

EXISTS can stop at the first matching row. COUNT has to find all of them.

Where can a subquery appear?

As a scalar value (SELECT list, WHERE comparison), as a list (IN, ANY, ALL), as a table in FROM (derived table), and inside EXISTS.

Rewrite id NOT IN (SELECT customer_id FROM orders) safely.

NOT EXISTS (SELECT 1 FROM orders o WHERE o.customer_id = c.id).

UNION, INTERSECT and EXCEPT

Joins put tables side by side. Set operations stack query results on top of each other. Both queries must return the same number of columns with compatible types.

Where people get hurt

  • UNION sorts or hashes the whole result to remove duplicates. If duplicates are impossible or wanted, use UNION ALL: it is cheaper and says what you mean.
  • Columns are matched by position, not by name. Swap two columns in one branch and you get wrong data with no error.
  • ORDER BY applies to the combined result and goes once, at the end.
  • Oracle calls EXCEPT MINUS. MySQL added INTERSECT and EXCEPT only in 8.0.31.

In backend work

An activity feed ("order placed, payment received, refund issued") is a UNION ALL of several tables sorted by time.

In AI work

Hybrid search combines a keyword result set and a vector result set. Data-quality checks use EXCEPT to find rows present in the source but missing from the embedded copy.

Check yourself

What is the difference between UNION and UNION ALL?

UNION removes duplicate rows, which costs a sort or hash. UNION ALL returns everything.

What do the two queries in a set operation need to have in common?

The same number of columns, in the same order, with compatible types.

How do you find ids present in table A but missing from table B?

SELECT id FROM a EXCEPT SELECT id FROM b, or an anti-join.

CASE, text functions and dates

CASE is SQL's if/else. It is an expression, so it can go anywhere a value can: in SELECT, in ORDER BY, inside an aggregate.

Where people get hurt

  • A CASE with no ELSE returns NULL when nothing matches.
  • WHERE date_trunc('day', placed_at) = '2026-03-09' wraps the column in a function, so a plain index on placed_at cannot be used. Write a range: placed_at >= '2026-03-09' AND placed_at < '2026-03-10'.
  • GROUP BY 1 means "the first output column". Handy at the keyboard, fragile in saved code: reorder the SELECT list and the grouping changes.
  • The date table above is from the documentation of each database; only the PostgreSQL column was executed here.

In backend work

Status labels, price bands and "is this order late" flags can be computed in SQL with CASE and returned ready to display, or kept in app code. Keep business wording in the app; keep facts (is_late) in SQL.

In AI work

Bucketing with CASE turns raw numbers into categories a model or a metric can use: latency bands, score ranges, "short / medium / long" prompts.

CTEs: naming the steps of a query

A common table expression (CTE) is a named subquery written before the main query with WITH. It lets you build a complicated query as a short list of named steps that read top to bottom, instead of subqueries nested inside each other.

Where people get hurt

  • A CTE exists only for the one statement it is attached to. For something reusable across queries, create a view.
  • Before PostgreSQL 12 every CTE was computed in full and stored first (an "optimisation fence"), which could be slow. Since 12, a CTE used once is merged into the main query like a subquery. Write AS MATERIALIZED if you actually want it computed once and reused.
  • A CTE is not a temporary table. You cannot index it.

In backend work

Long report queries become reviewable. A teammate can read order_totals, then customer_totals, and check each one separately.

In AI work

Ask a text-to-SQL model to "write the query as CTEs, one step per CTE". The output is far easier for you to verify, and the model makes fewer mistakes when it works in steps.

Check yourself

What is a CTE?

A named, temporary result set defined with WITH that exists for the duration of one statement.

When would you add MATERIALIZED to a CTE in PostgreSQL?

When it is expensive, referenced several times, and you want it computed once; or when you deliberately want to stop the planner pushing conditions into it.

CTE, view, or temporary table: which lasts longest?

A view is permanent (a stored query). A temporary table lasts for the session. A CTE lasts for one statement.

Recursive CTEs: trees and hierarchies

Categories form a tree: Groceries contains Fresh, Fresh contains Fruits. How deep is it? You do not know in advance, so you cannot write a fixed number of joins. A recursive CTE repeats a join until it stops finding new rows.

It has two parts joined by UNION ALL: the anchor (where to start) and the recursive part (how to get from the rows found so far to the next ones).

Where people get hurt

  • If the data has a cycle (A's parent is B, B's parent is A) the recursion never ends. Guard with a depth limit (WHERE depth < 20) or track visited ids; PostgreSQL 14+ has a CYCLE clause.
  • Use UNION ALL. Plain UNION removes duplicates on every pass, which is slower, though it can also stop some cycles.
  • In PostgreSQL, generate_series(1, 7) is the simpler way to produce a list of numbers or dates.
  • SQL Server and Oracle omit the word RECURSIVE; MySQL 8+, PostgreSQL and SQLite require it.

In backend work

Category menus, comment threads, org charts, folder trees, "all sub-teams of this team" permission checks.

In AI work

Knowledge graphs and document hierarchies. "Give the model this section plus all its parent headings" is a walk up a tree; multi-hop questions over linked entities are a walk along edges.

Check yourself

What are the two parts of a recursive CTE?

The anchor member, which runs once and supplies the starting rows, and the recursive member, which joins to the rows produced by the previous pass. They are combined with UNION ALL.

When does the recursion stop?

When a pass produces no new rows.

How do you protect a recursive query from cyclic data?

Limit the depth, keep an array or path of visited ids and refuse to revisit, or use the CYCLE clause in PostgreSQL 14+.

Window functions

GROUP BY answers "what is the total per customer?" but loses the individual orders. Often you want both: each order and something computed from its neighbours: the running total so far, its rank, the previous order's date.

A window function does that. It computes a value for each row using a set of related rows (its window), and it does not collapse anything.

Three lines share the price 66. ROW_NUMBER still gives them different numbers, in an arbitrary order. RANK gives all three the same number and then skips two. DENSE_RANK gives the same number and skips nothing.

Where people get hurt

  • You cannot use a window function in WHERE, because windows are computed after WHERE. Compute it in a CTE, then filter in the outer query (next lesson).
  • With ORDER BY and no explicit frame, the default frame is RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW. "RANGE" treats rows with equal sort values as one, so ties get the same running total. Add a unique tie-breaker to the ORDER BY or say ROWS.
  • ROW_NUMBER() with ties and no tie-breaker gives different numbering on different runs.

In backend work

Leaderboards, "your 3 most recent orders per address", running wallet balance, numbering rows for pagination, "is this the customer's first order".

In AI work

Deduplicating training rows (keep ROW_NUMBER() = 1 per key), picking the top-k chunks per document, moving averages of latency or cost, comparing each evaluation run with the previous one using LAG.

Check yourself

What is the difference between GROUP BY and a window function?

GROUP BY returns one row per group. A window function returns every input row and adds a value computed across the row's window.

What do PARTITION BY and ORDER BY do inside OVER?

PARTITION BY splits the rows into independent groups; ORDER BY defines the sequence inside each group, which running totals, ranks and LAG/LEAD depend on.

ROW_NUMBER: 1, 2, 3. RANK: 1, 1, 3. DENSE_RANK: 1, 1, 2.

Why can't you filter on a window function in WHERE?

WHERE is evaluated before window functions are computed. Wrap the query in a CTE or subquery and filter outside.

CREATE TABLE and constraints

CREATE TABLE declares a table's columns, their types, and the rules rows must obey. Those rules are called constraints, and they are the most valuable lines in a schema: the database checks them on every write, from every program, forever. A rule that lives only in app code is skipped by the next script someone runs by hand.

Watch each rule refuse bad data on the practice tables.

Where people get hurt

  • UNIQUE allows many NULLs, because NULL is never equal to NULL. A nullable unique email lets any number of customers have no email. PostgreSQL 15+ has UNIQUE NULLS NOT DISTINCT if you want only one.
  • serial is the old way to auto-number in PostgreSQL. Use GENERATED ALWAYS AS IDENTITY. MySQL says AUTO_INCREMENT, SQLite INTEGER PRIMARY KEY.
  • A foreign key does not create an index on the referencing column in PostgreSQL. Add one yourself (CREATE INDEX ON addresses (customer_id)) or joins and cascading deletes will scan the table.
  • Constraint names matter when one fails in production. Name important ones: CONSTRAINT price_positive CHECK (price > 0).

In backend work

Validate in the API for good error messages, and also constrain in the database for correctness. Two requests racing each other can both pass an "is this email free?" check in code; only the UNIQUE constraint stops the second insert.

In AI work

Agents and pipelines write to your tables too, and they do not read your service code. Constraints are the guardrail that holds when a model emits an invalid status or a duplicate record.

Check yourself

What is the difference between PRIMARY KEY and UNIQUE?

Both enforce uniqueness. A primary key is also NOT NULL and there is one per table; it is the row's official identity. A table can have several UNIQUE constraints, and they allow NULLs.

Why enforce a rule in the database when the API already validates it?

The database is the only place every writer goes through, and the only place that can check atomically under concurrency. App checks can be bypassed or raced.

What does ON DELETE CASCADE do?

When the parent row is deleted, the rows that reference it are deleted too.

Does a foreign key create an index on the child column in PostgreSQL?

No. The parent's key is indexed (it is a primary key or unique), the child column is not until you index it.

Keys and relationships

Tables are connected by keys. A primary key names a row. A foreign key in another table stores that name to point at it. Every relationship in a schema is one of three shapes.

order_items has a composite primary key: (order_id, product_id). Neither column alone is unique, the pair is. That also guarantees a product appears at most once per order.

Where people get hurt

  • Use a surrogate primary key and a unique constraint on the natural key. One gives stable references, the other stops duplicates.
  • A column named customer_id with no foreign key constraint is only a hope. Orphan rows appear the first time a delete goes wrong.
  • ON DELETE CASCADE on a deep tree can delete far more than you meant with one statement. Financial and audit tables should use RESTRICT.

In backend work

The relationships decide your API shapes. One-to-many becomes a nested list (order.items[]), many-to-many becomes a link endpoint, and the foreign keys tell you what must be loaded together.

In AI work

Retrieval quality depends on these links. A chunk row with foreign keys to its document, its author and its tenant can be filtered and cited properly; a pile of unlinked text cannot.

Check yourself

How do you model a many-to-many relationship?

With a junction table that has a foreign key to each side, usually with the pair as its primary key, plus any facts about the pair (quantity, role, date).

What is a composite key?

A key made of more than one column, where the combination is unique.

Why might you prefer a surrogate key to using email as the primary key?

Emails change, are long, and would have to be updated in every referencing table. A surrogate id never changes.

What is the default behaviour when you delete a row that other rows reference?

The delete fails with a foreign key violation.

Normalisation, and when to break it

Normalisation means arranging tables so that each fact is stored in exactly one place. The reason is practical: if a customer's city is written on every one of their order rows, changing it means updating many rows, and missing one leaves the database contradicting itself.

A short test covers all three: for each column ask "what does this value depend on?" If the honest answer is not "this table's key", the column belongs in another table.

Deliberate copies are not violations

order_items.unit_price looks like a copy of products.price. It is not the same fact. One is "what this product costs today", the other is "what this customer paid on that day". Prices change; receipts must not.

Where people get hurt

  • Normalise first. Denormalise only for a measured performance problem, and write down which table is the source of truth.
  • A cached total that is updated in app code "after" the insert will drift. Update it in the same transaction, or compute it with a query.
  • Comma-separated ids in a text column ('3,7,9') cannot be joined, indexed or constrained. Use a junction table or an array.

In backend work

A normalised core (customers, orders, items) with snapshot columns for anything that must not change later is the standard shape of an order system.

In AI work

Feature and analytics tables are intentionally wide and denormalised, because a model wants one row per example. Build them from the normalised tables with a query, so they can always be rebuilt.

Check yourself

What problem does normalisation solve?

Redundancy. Storing a fact once removes update, insert and delete anomalies where copies of the fact disagree or disappear.

Is order_items.unit_price a normalisation violation?

No. It records the price at the time of sale, which is a different fact from the product's current price and must not change when the catalogue changes.

State third normal form simply.

Every non-key column depends on the key, the whole key, and nothing but the key.

When is denormalisation justified?

When a measured read cost is too high and you accept the write cost and staleness, or when the "copy" is really a historical snapshot.

Modelling decisions that are hard to change later

Adding a column is easy. Changing an id type, a money type or the meaning of a timestamp on a table with a hundred million rows is a project. These are the choices worth getting right on day one.

Where people get hurt

  • Soft delete breaks unique constraints (a deleted user still "owns" the email) and every query must remember WHERE deleted_at IS NULL. Partial unique indexes and a view of live rows fix both.
  • Storing local time without a zone makes "orders placed today" wrong for users in another zone and breaks twice a year where clocks change.
  • Do not put several meanings in one column (status = 'cancelled_refunded_partial'). Use separate columns or tables for separate facts.

In backend work

Design the table around the queries the endpoints will run. If the order list filters by customer and sorts by date, the schema and its index should make exactly that cheap.

In AI work

Add the columns an AI feature will need before you have data: model, prompt_version, token counts and cost on every model call, embedding_model next to every vector. You cannot backfill what was never recorded.

Check yourself

Why store timestamps as timestamptz in UTC?

An instant is unambiguous in UTC. Clients convert to local time for display. Local timestamps without a zone cannot be compared across regions or daylight-saving changes.

How do you enforce "only one default address per customer"?

A partial unique index: CREATE UNIQUE INDEX … ON addresses (customer_id) WHERE is_default.

What are the trade-offs of soft delete?

You can undo and audit deletions, but every query must exclude deleted rows, unique constraints need to ignore them, and the table keeps growing.

bigint is smaller and index-friendly and is the default. uuid suits ids generated by clients or several services, or ids that must not be guessable; prefer a time-ordered variant.

Views and materialised views

A view is a saved query with a name. You select from it as if it were a table, and the database runs the underlying query each time. It stores no data. Use it to give a complicated join a simple name, or to expose only some columns.

A materialised view stores the result. Reading it is as fast as reading a table, and it is as stale as its last refresh.

Where people get hurt

  • A view on a view on a view hides enormous queries behind a friendly name. When a view is slow, EXPLAIN it.
  • REFRESH MATERIALIZED VIEW locks out readers while it runs. REFRESH … CONCURRENTLY does not, and needs a unique index on the materialised view.
  • Views are permanent schema objects. Dropping a column that a view uses fails until the view is changed.

In backend work

Give analysts and admin tools views, not base tables. You can then change the tables underneath without breaking them.

In AI work

Give a text-to-SQL agent a small set of well-named views with clear column names instead of the raw schema. The model writes better SQL, and it cannot reach columns you did not expose.

Check yourself

Does a view store data?

No. It stores the query. A materialised view stores the result.

When is a materialised view the right tool?

For an expensive query that is read much more often than the data changes, where slightly old results are acceptable.

How do you refresh a materialised view without blocking readers?

REFRESH MATERIALIZED VIEW CONCURRENTLY name, which requires a unique index on it.

Model calls are JSON in and JSON out. Keep the request, the tool calls and the structured output as JSONB next to typed columns for the things you aggregate (model, tokens, cost, latency). Chunk metadata for retrieval filtering is usually JSONB with a GIN index.

What is the difference between -> and ->>?

-> returns JSON (so you can keep navigating); ->> returns text.

Which index type speeds up @> containment queries on JSONB?

A GIN index.

When should a JSON field become a real column?

When you filter, join, sort or constrain on it regularly, or when every row has it.

jsonb. It is stored in a parsed binary form, supports indexing and containment operators, and is faster to query.

Changing a schema that is in use

A migration is a script that changes the schema: add a column, create an index, split a table. Each one is a numbered file in the repository, applied in order, once, on every environment. The database records which ones have run.

The difficulty is that the app keeps running while the schema changes, and during a deploy the old and the new version of your code run side by side. So every change must be compatible with both.

Where people get hurt

  • A migration that waits for a lock blocks every query that arrives after it, even reads. A two-second ALTER TABLE stuck behind one long transaction can take the site down. Always set lock_timeout.
  • PostgreSQL DDL is transactional (a failed migration rolls back cleanly). MySQL commits DDL implicitly, so a half-applied migration is possible there.
  • Never edit a migration that has already run somewhere. Write a new one.

What is the expand, migrate, contract pattern?

Add the new structure alongside the old, move data and code over in steps while both work, then remove the old structure. At every moment both the old and new app versions can run.

INSERT, UPDATE, DELETE and upsert

Three statements change rows. INSERT adds rows, UPDATE changes columns of existing rows, DELETE removes rows. UPDATE and DELETE act on every row that matches their WHERE, and on every row in the table if there is none.

UPDATE 12: every product is now out of stock. (This build rolls each sample back, so the practice data is unharmed.) In a console, run the SELECT with the same WHERE first, and work inside a transaction so you can ROLLBACK.

"Add this product to the cart, or increase the quantity if it is already there." Doing a SELECT and then deciding in code has a race: two requests can both see "not there" and both insert. INSERT … ON CONFLICT does the check and the write as one atomic step.

Where people get hurt

  • excluded is the row you tried to insert. order_items.qty is the row already in the table.
  • ON CONFLICT needs a unique constraint or index on the listed columns. Without one there is no "conflict" to detect.
  • TRUNCATE empties a table instantly but skips row-level triggers and, in most databases other than PostgreSQL, cannot be rolled back.
  • Deleting millions of rows in one statement holds locks and bloats the table. Delete in batches, or drop a partition.

In backend work

RETURNING saves a round trip: insert an order and get its generated id and timestamps back in the same call. Upsert is the standard way to write "set this user's preference" and "add to cart" endpoints.

In AI work

Ingestion pipelines re-run. Upserting chunks by (document_id, chunk_index) makes re-embedding a document safe to repeat instead of creating duplicates.

What happens when you run UPDATE without WHERE?

Every row in the table is updated.

What does RETURNING do?

It makes INSERT, UPDATE or DELETE return the affected rows (or chosen columns), so you do not need a second query.

Why is "SELECT, then INSERT or UPDATE in code" unsafe?

Two concurrent requests can both find no row and both insert. INSERT … ON CONFLICT performs the check and the write atomically.

Transactions and ACID

Placing an order means several writes: insert the order, insert its items, reduce stock, record the payment. If the server dies after the second write, you have an order with items and no stock change. A transaction makes a group of statements behave as one: either all of them take effect, or none do.

Read that output line by line. The first insert worked. The second failed on the foreign key. After that PostgreSQL refused the UPDATE with "current transaction is aborted": once one statement fails, the whole transaction is poisoned until you roll back. After ROLLBACK the order row from the first insert is gone too.

Where people get hurt

  • Without BEGIN, each statement is its own transaction ("autocommit"). Three statements are then three separate all-or-nothing units, not one.
  • Keep transactions short. A transaction that stays open while your code calls a payment gateway holds locks and blocks cleanup for the whole wait. Never do network calls inside one.
  • A session left "idle in transaction" (BEGIN, then nothing) is a common cause of production incidents: it blocks schema changes and stops VACUUM. Set idle_in_transaction_session_timeout.
  • MySQL's old MyISAM tables have no transactions at all. InnoDB (the default for many years) does.

You already know this from Swift and Dart

A transaction is like a batch of edits to a document that you either save or discard as a whole. Core Data's context.save() and Realm's write { } block are the same idea on the device. The difference is that here thousands of batches run at the same moment, which is what the next three lessons are about.

In backend work

Wrap every multi-step business operation in one transaction: place order, transfer wallet money, cancel and refund. Frameworks give you a helper (with session.begin(): in SQLAlchemy, prisma.$transaction, @Transactional in Spring).

In AI work

When an agent's tool call writes several rows (create a ticket, log the action, update a counter), run it in one transaction so a failed or retried tool call cannot leave half a result. Store a document and its chunks in one transaction so search never sees a document without its text.

Check yourself

What does atomicity mean?

A transaction's changes are applied completely or not at all.

What happens to later statements after one statement in a PostgreSQL transaction fails?

They are rejected with "current transaction is aborted" until you ROLLBACK (or roll back to a savepoint).

How can COMMIT be fast and durable at the same time?

Only the log record is flushed to disk at commit, as a sequential append. The table pages are written later, and after a crash the log is replayed.

Why should you not call an external API inside a transaction?

The transaction stays open, holding locks and a connection, for as long as the call takes, and that time is unbounded.

MVCC: how readers and writers avoid each other

A simple database would lock a row while someone changes it, and readers would wait. PostgreSQL does something better. When a row is updated it keeps the old version and writes a new version beside it. Each transaction reads the versions that were committed when its snapshot was taken. This is multi-version concurrency control, MVCC.

The result: readers never block writers, and writers never block readers.

You can see the versions. Every PostgreSQL row has hidden columns: xmin is the id of the transaction that created this version, and ctid is its physical address (page, item).

Where people get hurt

  • Dead versions take space until VACUUM removes them. A table that is updated heavily and vacuumed too rarely grows ("bloat") and its scans slow down. Autovacuum normally handles this.
  • One long-running transaction holds an old snapshot, so VACUUM cannot remove anything newer than it, across the whole database. A forgotten open transaction can bloat every busy table.
  • Writers still block writers on the same row. MVCC removes read/write conflicts only.
  • MySQL InnoDB and Oracle also use MVCC but keep old versions in a separate undo area instead of in the table.

In backend work

A slow report does not freeze checkout, and checkout does not freeze the report. That is MVCC. It is also why "the count I read a moment ago" may be stale by the time you act on it.

In AI work

A long analytics or export job for a training set should run in one transaction at REPEATABLE READ so it sees one consistent snapshot of every table, while the app keeps writing. Keep it off the primary if it runs for hours.

Check yourself

What does MVCC stand for and what is the core idea?

Multi-version concurrency control. Updates create new row versions instead of overwriting, and each transaction reads the versions visible to its snapshot.

Does a SELECT wait for an uncommitted UPDATE on the same row in PostgreSQL?

No. It returns the last committed version.

What does VACUUM do?

It removes row versions that no transaction can see any more and makes their space reusable. It also updates the visibility information that index-only scans rely on.

Why is a long-open transaction harmful even if it does nothing?

It pins an old snapshot, so dead row versions created after it started cannot be vacuumed, and it may hold locks that block schema changes.

Isolation levels

Isolation is a dial. At one end transactions can see each other's committed changes mid-flight, which is fast and occasionally surprising. At the other end the result is guaranteed to equal some one-at-a-time ordering, which is safest and sometimes forces a retry. You pick a level per transaction.

Write skew: the case only SERIALIZABLE catches

Rule: at least one of Curd (6) and Paneer (7) must stay on sale. Two staff each check "both are in stock", and each takes a different one off sale. No row was written by both, so nothing looks like a conflict, yet together they broke the rule.

Where people get hurt

  • The SQL standard also defines READ UNCOMMITTED. PostgreSQL accepts the name and treats it as READ COMMITTED; it never shows uncommitted data.
  • MySQL InnoDB defaults to REPEATABLE READ, and its REPEATABLE READ behaves differently from PostgreSQL's (it uses gap locks). Never assume the default when you change databases.
  • A serialization failure is not a bug. It is the database telling you to retry. Code that uses these levels without a retry loop will surface random errors to users.
  • Higher isolation does not replace constraints. A UNIQUE constraint is cheaper and always on.

In backend work

READ COMMITTED plus explicit row locks (next lesson) covers most endpoints. Use SERIALIZABLE for the few operations that enforce a rule across several rows: slot capacity, seat booking, wallet limits.

In AI work

Agents that run in parallel and act on what they read ("if under budget, spend") are a write-skew machine. Either lock the row they decide on, or run the tool's transaction as SERIALIZABLE with a retry.

Check yourself

What is PostgreSQL's default isolation level and what can still happen under it?

READ COMMITTED. Each statement sees data committed before that statement began, so two reads in one transaction can differ (non-repeatable read) and new rows can appear (phantoms).

What must an application do when it uses REPEATABLE READ or SERIALIZABLE?

Catch serialization failures (SQLSTATE 40001), roll back, and retry the whole transaction.

What is write skew?

Two transactions read overlapping data, each makes a decision that is valid on its own snapshot, and they write different rows, so the combined result violates a rule. Only SERIALIZABLE (or explicit locking) prevents it.

What is a dirty read, and can it happen in PostgreSQL?

Reading another transaction's uncommitted change. It cannot happen in PostgreSQL at any level.

Row locks, lost updates and deadlocks

MVCC lets readers and writers pass each other. Two writers on the same row still have to take turns: the second one waits until the first commits or rolls back. That waiting is a row lock, and you rarely notice it. The trouble starts when your code reads a value, computes in the app, and writes back.

Fix 1: let the database do the arithmetic

stock = stock - 1 reads and writes under the row lock, so a second session's update waits and then subtracts from the new value. The AND stock >= 1 makes overselling impossible: if no row comes back, it was out of stock.

Fix 2: lock the row before you read it

Fix 3: optimistic locking

Do not lock. Write only if the row is still as you read it, and check how many rows you changed. Usually done with a version column; here the stock value itself plays that role.

Deadlock

Where people get hurt

  • Prevent deadlocks by always locking rows in the same order (sort the product ids before updating stock for an order). Then a cycle cannot form.
  • A deadlock victim gets error 40P01. Like a serialization failure, the right response is to retry the transaction.
  • FOR UPDATE on a query that matches many rows locks all of them. Lock the narrowest set you can.
  • Table-level locks exist too: ALTER TABLE takes one that blocks everything. See the migrations lesson.
  • Use FOR UPDATE NOWAIT or lock_timeout when failing fast is better than queueing.

In backend work

Stock, wallet balance, coupon usage counts, seat and slot capacity: anything of the form "check then change" needs one of the three fixes. This is the most common source of real money bugs.

In AI work

An agent retrying a tool call, or several agents sharing a budget or a queue, creates the same races. Give tools atomic SQL (UPDATE … WHERE budget_left >= $1 RETURNING …) instead of read-then-write logic.

Check yourself

What is a lost update?

Two transactions read the same value, each computes a new value from it, and the second write overwrites the first, so one change disappears.

Give three ways to prevent a lost update.

An atomic UPDATE that computes from the current value; SELECT … FOR UPDATE to lock before reading; optimistic locking with a version check and retry. (REPEATABLE READ also detects it and fails one transaction.)

What is a deadlock and how does PostgreSQL handle it?

A cycle of transactions each waiting for a lock another holds. After deadlock_timeout PostgreSQL detects the cycle and aborts one transaction with an error.

How do you avoid deadlocks by design?

Acquire locks in a consistent order in every code path, keep transactions short, and retry on deadlock errors.

Job queues, idempotency and the outbox

Backends have work that should happen later: send the confirmation email, generate the invoice, embed a document. A common, robust approach is a jobs table and several worker processes that each take the next job. The hard part is making sure two workers never take the same job, without making them wait for each other.

If a worker crashes mid-job its transaction rolls back, the lock disappears, and the job is queued again for someone else. No cleanup code needed.

Idempotency: making retries harmless

Networks fail after the server did the work and before the client heard about it, so clients retry. An operation is idempotent if doing it twice has the same effect as doing it once. The usual tool is a unique key supplied by the caller.

The first insert returned the key: this is new, do the work. The second returned no row: we have seen this request, return the earlier result and do nothing.

The outbox: change the database and send a message, reliably

Where people get hurt

  • A job can still run twice (the worker finished the email but crashed before marking it done). Queues give "at least once". Make the job itself idempotent.
  • Index the queue for its query: a partial index ON jobs (id) WHERE status = 'queued' keeps claiming fast when the table holds millions of finished jobs.
  • Long jobs should not hold a transaction open. Mark the job running with a locked_until time and commit, then do the work.
  • A database table is a fine queue up to thousands of jobs per second. Beyond that, or for fan-out to many consumers, use a broker (SQS, RabbitMQ, Kafka).

In backend work

Payment callbacks, order placement and "resend OTP" must be idempotent, because mobile clients retry on timeouts. The outbox is how an order service tells notification and analytics services about an order without losing or inventing events.

In AI work

Embedding jobs, batch model calls and agent tasks are queues. SKIP LOCKED workers with an idempotency key per (document, model version) let you re-run ingestion safely and never pay to embed the same chunk twice.

Check yourself

What does FOR UPDATE SKIP LOCKED do?

It locks the rows it returns and silently skips rows already locked by another transaction, so concurrent workers each get different rows without waiting.

What does idempotent mean?

Performing the operation several times has the same effect as performing it once.

How does a unique idempotency key make a POST safe to retry?

The first request inserts the key and does the work. A retry hits the unique constraint, so the server knows it is a duplicate and returns the stored result.

What problem does the transactional outbox solve?

Updating the database and publishing a message cannot be made atomic across two systems. Writing the message to an outbox table in the same transaction guarantees it is recorded if and only if the change commits; a relay then delivers it.

What happens when you send a query

You send text. Before any row is read, the database turns that text into a plan: a tree of steps such as "scan this index", "join with a hash table", "sort". There are usually many possible plans for one query, and the planner estimates the cost of each and picks the cheapest. Performance work is mostly understanding and influencing that choice.

Read it as: "scan the whole products table (Seq Scan), keep rows where price > 100; I estimate this returns about that many rows". cost is in arbitrary units (roughly "page reads"); the second number is the estimated total.

The estimates come from statistics that ANALYZE collects: how many rows a table has, how many distinct values each column has, which values are most common.

So the planner knows kind = 'view' matches half the table and user_id = 42 matches a handful of rows, and it will choose different methods for the two.

Where people get hurt

  • Stale statistics cause bad plans. After loading a lot of data, run ANALYZE (autovacuum does it for you eventually, not instantly).
  • EXPLAIN alone shows estimates. EXPLAIN ANALYZE actually runs the query and shows real numbers. Do not EXPLAIN ANALYZE a DELETE on production unless you wrap it in a transaction and roll back.
  • The planner is cost-based, not rule-based. An index that exists is not necessarily an index that is used.

In backend work

"The endpoint got slow after the table grew" is the planner switching method, or a plan that was always bad becoming noticeable. The first debugging step is always: copy the query, run EXPLAIN (ANALYZE, BUFFERS).

In AI work

Vector search goes through the same planner. Whether your similarity query uses the HNSW index or scans every vector depends on how the query is written, and EXPLAIN is how you find out.

Check yourself

What does the query planner do?

It considers different ways to execute a query (scan types, join orders, join methods), estimates their cost from table statistics, and picks the cheapest.

What is the difference between EXPLAIN and EXPLAIN ANALYZE?

EXPLAIN shows the plan and estimates without executing. EXPLAIN ANALYZE executes the query and adds actual row counts and timings.

Where do the planner's row estimates come from?

From statistics gathered by ANALYZE: row counts, distinct counts, most common values and histograms per column.

What are two benefits of prepared statements?

The query is parsed (and often planned) once and reused, and values travel separately from the SQL text, which prevents SQL injection.

Indexes: how a lookup avoids reading the whole table

Without an index, finding the rows where user_id = 4242 means reading every row and testing it: a sequential scan. An index is a separate sorted structure that maps values to row locations, like the index at the back of a book: look up the word, get the page numbers, go straight there.

The events table has 100,000 rows. Find one user's events, first without an index on user_id.

Compare the two outputs. The first says Seq Scan and "Rows Removed by Filter" close to 100,000. The second uses events_user_idx and touches only the matching rows. Look at the Execution Time lines: the exact numbers change from run to run, the gap between them does not.

An index is not always used

User ids run from 1 to 5,000. user_id > 100 matches 98% of the table: hopping through an index to almost every row is slower than reading the table front to back, so the planner correctly picks a sequential scan and ignores the index. user_id < 100 matches about 2%, and it uses the index through a bitmap scan: collect all matching row locations from the index first, then read the table pages in physical order.

There is no fixed percentage where it switches. The planner compares estimated costs, and those depend on row width, how the rows are laid out on disk, and whether the data is in memory.

Where people get hurt

  • Every index slows down INSERT, UPDATE and DELETE on that table and takes memory. Index for the queries you actually run; drop indexes nothing uses (pg_stat_user_indexes.idx_scan = 0).
  • A primary key and every UNIQUE constraint already have an index. Foreign key columns do not, in PostgreSQL.
  • An index on a column with few distinct values (a boolean, a status with three values) rarely helps on its own. See partial indexes in the next lesson.
  • On a tiny table the planner uses a sequential scan whatever indexes exist, because the whole table is one page. Do not judge indexes on test data with 20 rows.

In backend work

Almost every "list my X" endpoint needs an index that starts with the owner column: orders (customer_id, …). Missing indexes on foreign keys are the most common cause of slow APIs.

In AI work

Metadata filters in retrieval (tenant_id, document_id, created_at) need ordinary B-tree indexes, separate from the vector index. Without them a filtered similarity search scans far more than it should.

Check yourself

What is an index, physically?

A separate data structure (by default a B-tree) holding the indexed column values in sorted order, each with a pointer to the table row.

Why might the planner not use an index that exists?

The filter matches too large a share of the table, the table is very small, the query wraps the column in a function or a type cast, or statistics are stale. In those cases a sequential scan is estimated to be cheaper.

What is the cost of adding an index?

Disk and memory, and extra work on every insert, update and delete to keep it current.

What is a bitmap heap scan?

The executor first collects all matching row locations from the index into a bitmap, then visits the table pages once each in physical order, which is cheaper than random jumps when many rows match.

For WHERE user_id = ? AND created_at > ? ORDER BY created_at, what index and why?

(user_id, created_at). The equality column first lets the scan jump to that user's entries; within them the entries are already sorted by time, so the range and the order are both served.

What is a covering index?

An index that contains every column a query needs, so PostgreSQL can answer with an Index Only Scan and skip the table.

When is a partial index useful?

When queries always target a small, fixed subset of rows (queued jobs, non-deleted rows, one event type). It is smaller, cheaper to maintain and faster.

The index is sorted by customer_id first, so rows after 1 March are scattered across every customer's section. There is no single place to seek to.

In which order do you read a plan?

From the innermost (most indented) nodes outward. Children produce rows for their parent.

What is the N+1 problem and how do you fix it?

Loading a list with one query and then running one more query per item. Fix by fetching all related rows in one query (WHERE parent_id = ANY($1) or a join), which ORMs call eager loading.

A condition written so an index can be used to satisfy it: the bare column compared to a value or range, not wrapped in a function or cast.

Storage, VACUUM and partitioning

A few facts about how PostgreSQL stores data explain behaviour that otherwise looks mysterious: why a table grows when you only update it, why deleting rows does not shrink the file, and how tables with billions of rows stay manageable.

Updates leave dead rows behind

This is MVCC's bill. The first update wrote 100,000 new row versions next to the old ones. VACUUM marked the old ones as free space, so the second update reused that space and the file did not grow again. Autovacuum does this continuously in the background; your job is to make sure it can keep up and is not blocked by long transactions.

Partitioning: one logical table, many physical ones

Where people get hurt

  • Partitioning is not a general speed-up. Queries that do not filter on the partition key must scan every partition and get slower.
  • A primary key or unique constraint on a partitioned table must include the partition key.
  • VACUUM FULL rewrites the table under an exclusive lock. On a live system it is an outage.
  • Transaction ids are 32-bit and wrap around. VACUUM also "freezes" old rows to prevent that; a database where autovacuum has been disabled or blocked for long enough will eventually refuse writes to protect itself.

In backend work

Event, log, audit and notification tables are the ones that grow without limit. Partition them by month from the start and deleting a year of data is one DROP TABLE.

In AI work

Model-call logs, traces and conversation messages grow the same way, and they are what your cost and quality dashboards query. Partition by time, and keep bulky payloads (full prompts, tool outputs) in their own table or object storage so the hot table stays small.

Check yourself

Why does a PostgreSQL table get bigger when you only UPDATE rows?

Each update writes a new row version and leaves the old one in place until VACUUM marks it reusable.

Does VACUUM return disk space to the operating system?

Ordinarily no. It makes space inside the table file reusable. Only VACUUM FULL or a rewrite tool shrinks the file.

What is partition pruning?

The planner (or executor) skips partitions whose bounds cannot match the query's filter on the partition key.

When does partitioning hurt?

When queries do not filter on the partition key (every partition is scanned), and when there are thousands of partitions, which makes planning slow.

Connections and pooling

Opening a database connection is slow (a TCP and TLS handshake, authentication, and in PostgreSQL a new operating-system process on the server). So a service opens a handful at startup and reuses them. That set is a connection pool: a request borrows a connection, runs its queries, and returns it.

Where people get hurt

  • A bigger pool does not make the database faster. Past a few dozen active connections PostgreSQL spends its time switching between them, and throughput drops.
  • PgBouncer in transaction mode gives each transaction a possibly different server connection. Session state (SET, session-level prepared statements, advisory locks, LISTEN) does not survive across transactions there.
  • Always set a pool acquire timeout and a statement_timeout. Without them one stuck query can hold a connection forever.
  • The pool sample was not executed; psycopg_pool is not installed in the build environment.

In backend work

Pool exhaustion is among the most common production incidents. Monitor "connections in use" and "time waiting for a connection" per instance; a rising wait time is the early warning.

In AI work

Model calls take seconds. If a request holds a database connection while it waits for an LLM, twenty concurrent chats exhaust a pool of twenty. Read what you need, release the connection, call the model, then borrow again to write the result.

Check yourself

Why use a connection pool?

Creating a connection is expensive and the server can only hold a limited number. A pool reuses a small set across many requests.

What happens when all pooled connections are busy?

New requests wait up to the acquire timeout and then fail. The database may be nearly idle while the application appears down.

Why not set the pool size to 500?

Each PostgreSQL connection is a process with its own memory; hundreds of active ones cause contention and context switching and reduce throughput. Queueing a short time for one of a few connections is faster.

What is PgBouncer for?

It multiplexes many client connections onto few server connections, which is needed when there are many app instances or serverless functions.

Replication, read replicas and sharding

One database server is one point of failure and has one machine's worth of capacity. Replication keeps copies: the primary accepts all writes and streams its write-ahead log to replicas, which replay it and can serve reads.

Replication lag and "where did my order go?"

When one primary is not enough: sharding

Sharding means rows for different customers live on different database servers. Queries within one shard stay simple. Anything across shards (a join, a transaction, a global unique constraint, a report) becomes application work. It is a last resort; most systems never need it.

Where people get hurt

  • A replica is not a backup. DROP TABLE replicates in milliseconds. You need backups with point-in-time recovery as well.
  • Reading from a replica inside a write flow gives stale data and intermittent bugs that never reproduce locally, because your laptop has no replica.
  • A long query on a replica can conflict with replay and be cancelled ("canceling statement due to conflict with recovery").

In AI work

Embedding backfills and evaluation jobs are heavy reads; run them against a replica. Retrieval for a user who just uploaded a document must read from the primary (or wait), or the assistant will say it cannot find the file they sent a moment ago.

Check yourself

What is replication lag and why does it matter?

The delay between a commit on the primary and its appearance on a replica. A read routed to a replica right after a write may not see that write.

Is a replica a backup?

No. Mistakes replicate too. Backups with point-in-time recovery protect against deletion and corruption.

What is the trade-off of synchronous replication?

No acknowledged commit is lost on failover, but every commit waits for a replica, and writes stall if the replica is unreachable.

Why is sharding a last resort?

Cross-shard joins, transactions and constraints stop working at the database level and must be rebuilt in the application; operations get much harder.

Roles, privileges and row-level security

The database has its own users, called roles, and decides what each may do. The principle is least privilege: every program connects as a role that can do exactly what it needs and nothing else. Then a bug or a stolen credential can only do limited damage.

Row-level security: the database adds the WHERE clause for you

Every multi-tenant bug has the same shape: a query forgot WHERE customer_id = … and returned someone else's rows. With row-level security (RLS) you declare the rule once on the table, and the database applies it to every query from that role, including ones that forget.

Where people get hurt

  • The role that owns a table, and any superuser, bypass RLS by default. Your API must not connect as the owner. (ALTER TABLE … FORCE ROW LEVEL SECURITY applies it to the owner too.)
  • Use SET LOCAL inside a transaction for the tenant setting. A plain SET sticks to the pooled connection and leaks into the next request.
  • Privileges are not automatic for tables created later. Set ALTER DEFAULT PRIVILEGES or grant in each migration.
  • Never store passwords in plain text or with a fast hash. Store a slow salted hash (argon2, bcrypt) computed in the application.
  • Encrypt in transit (TLS), restrict network access, and keep credentials in a secret manager, never in the repository.

In backend work

Separate roles for migrations and for the running app, so an injection in the API cannot drop tables. RLS as a second line of defence for tenant isolation on top of your own WHERE clauses.

In AI work

A model that can run SQL must connect as a role that can only SELECT from views you chose, with RLS scoping rows to the current user. Then no prompt, however cleverly injected, can make the database return another tenant's data: the database refuses.

Check yourself

What is least privilege?

Each role gets only the permissions its job requires, so a compromise or a bug has limited reach.

What does row-level security do?

It attaches a policy to a table that filters which rows a role can see or modify, applied automatically to every query.

Why must the application not connect as the table owner when relying on RLS?

Owners and superusers bypass policies unless FORCE ROW LEVEL SECURITY is set.

Why use SET LOCAL for a per-request tenant id with a connection pool?

SET LOCAL lasts only until the transaction ends. A session-level SET would remain on the connection and apply to the next request that borrows it.

Functions, procedures and triggers

SQL can also live inside the database as named code. A function takes arguments and returns a value or rows; you call it inside a query. A procedure is called on its own with CALL and may commit as it goes. A trigger is a function the database runs automatically when a row is inserted, updated or deleted.

Where people get hurt

  • Triggers are invisible from application code. A simple UPDATE that silently writes to three other tables is hard to debug. Keep triggers few, small and documented.
  • A row-level trigger runs once per row. A bulk update of a million rows runs it a million times.
  • Functions written in PL/pgSQL are opaque to the planner. A plain LANGUAGE sql function can often be inlined into the calling query; a PL/pgSQL one cannot.
  • Stored logic is deployed by migrations, not by your app deploy. Version it in the repository like any other code.
  • Syntax is the least portable part of SQL: PL/pgSQL (PostgreSQL), T-SQL (SQL Server), PL/SQL (Oracle) and MySQL's stored programs all differ.

In backend work

Most teams keep business logic in services and use the database for integrity: constraints first, a few triggers for audit and timestamps, functions for shared calculations.

In AI work

A trigger or generated column that keeps a tsvector (and a queue row for re-embedding) in step with the text guarantees search never goes stale when someone edits content outside your pipeline.

Check yourself

What is the difference between a function and a procedure in PostgreSQL?

A function returns a value and is used inside a query; it cannot commit. A procedure is invoked with CALL, returns nothing directly, and can commit or roll back inside its body.

When does a BEFORE trigger run compared with an AFTER trigger, and what can each do?

BEFORE runs before the row is written and can modify or reject the new row. AFTER runs once the row is written and is used for side effects such as audit records.

Name a good use and a bad use of triggers.

Good: audit logs and updated_at that must hold for every writer. Bad: multi-step business workflows, which become hidden and hard to test.

Why prefer a constraint over a trigger when both could enforce a rule?

Constraints are declarative, checked efficiently, visible in the schema, and cannot be forgotten or written incorrectly.

Embeddings and vector search with pgvector

An embedding is a list of numbers that an embedding model produces for a piece of text (or an image). The model is trained so that texts with similar meaning get lists that are close to each other. "Money back" and "refund" share no letters, and their embeddings are neighbours.

pgvector is a PostgreSQL extension that adds a vector column type and distance operators. With it, "find the most similar rows" is an ordinary ORDER BY … LIMIT.

Real embeddings have hundreds or thousands of dimensions and no human-readable meaning per dimension. To make the geometry visible, the practice table uses hand-made 3-number vectors where the three numbers mean (sweet, dairy, crunchy).

Second row: [1,0,0] and [3,0,0] point the same way. Their cosine distance is 0 (identical direction) although their Euclidean distance is 2. Most text embedding models are meant to be compared by cosine distance; use the measure your model's documentation names.

Where people get hurt

  • Vectors from different embedding models (or different versions of one) are not comparable, even when the dimensions match. Store the model name beside every vector and never mix them in one search.
  • The query text must be embedded by the same model as the stored rows.
  • ORDER BY embedding <=> $1 must be written in ascending order with a LIMIT for an index to be used. Sorting by 1 - (embedding <=> $1) DESC defeats it.
  • A distance is not a probability. "0.21" means nothing by itself; decide a cut-off by testing on your own data.
  • The hand-made 3-number vectors here are for teaching. Dimensions of real embeddings are not individually meaningful.

In backend work

Semantic search, "similar products", duplicate detection and recommendations become one table and one query in the database you already run, inside the same transactions and backups as the rest of your data.

In AI work

This is the retrieval step of RAG, long-term memory for assistants, semantic caching of answers, and clustering of user feedback. Starting with pgvector avoids running a separate vector database until scale demands one.

Check yourself

What is an embedding?

A fixed-length list of numbers produced by a model so that inputs with similar meaning have nearby vectors.

What does ORDER BY embedding <=> $1 LIMIT 5 return?

The five rows whose embeddings have the smallest cosine distance to the query vector: the five most similar.

Cosine distance versus Euclidean distance?

Cosine compares only direction and ignores vector length; Euclidean is straight-line distance and is affected by length. For normalised vectors they rank results identically.

Why store the embedding model name with each vector?

Vectors from different models live in different spaces. Mixing them gives meaningless distances, and you need the name to re-embed when you change models.

Vector indexes: HNSW and IVFFlat

Without an index, a similarity search computes the distance from the query to every stored vector and sorts. That is exact, and its cost grows with the table. A vector index finds neighbours while looking at a small fraction of the vectors. The price: the answer is approximate. It usually contains the true nearest rows, and can miss some.

The practice database has doc_vectors: 20,000 random 16-dimensional vectors.

Recall: how many of the true neighbours did the index find?

hnsw.ef_search is the size of the candidate list the search keeps. Higher means better recall and slower queries. On this small, easy data set both settings found all 10 true neighbours; on millions of real embeddings a low setting misses some, and that is the trade you tune. This is the measurement to run on your own data: build the exact answer for a sample of queries, then count how many the index returns.

The filter trap

Retrieval almost always has a filter: this tenant, this document type. With an approximate index the filter is applied after the index hands back its candidates. If the filter is selective, most candidates are thrown away and you get fewer rows than you asked for.

Where people get hurt

  • A vector index is used only for ORDER BY distance LIMIT k with the operator matching its operator class. A cosine index does not serve an <-> query.
  • If you see Seq Scan + Sort in the plan of a similarity query on a big table, the index is not being used. Check the operator, the ORDER BY direction and that a LIMIT is present.
  • HNSW indexes are large and live in memory to be fast. Plan for them: often bigger than the table's other indexes together.
  • halfvec (16-bit floats) halves storage and index size with little recall loss; pgvector's vector type indexes up to 2,000 dimensions and halfvec up to 4,000 (from the pgvector documentation, not exercised here).
  • The recall numbers above come from 20,000 random low-dimensional vectors, which are easy. Measure on your real embeddings.

In backend work

Treat a vector index like any other: check the plan, watch its size and build time, and build it CONCURRENTLY on a live table.

In AI work

Retrieval quality has a ceiling set by recall. If the right chunk is not among the candidates, no prompt can recover it. Measure recall against exact search before blaming the model, and re-measure whenever filters or data volume change.

Check yourself

Why are vector indexes called approximate?

They examine only part of the data, guided by a graph or by clusters, so they can miss some true nearest neighbours in exchange for speed.

What does hnsw.ef_search control?

The size of the candidate list kept during the search. Larger values improve recall and cost more time.

Why can a filtered vector query return fewer rows than its LIMIT?

The index returns a fixed number of nearest candidates first and the WHERE filter is applied afterwards; if few candidates pass, fewer rows come back. Iterative scanning or filtering first fixes it.

How do you measure the recall of a vector index?

For sample queries, compute the exact top k without the index, run the same query with the index, and count the overlap.

Storing documents for RAG

Retrieval-augmented generation (RAG) means: before asking the model a question, fetch the pieces of your own documents that are relevant and put them in the prompt. The model then answers from text you chose, and can cite it.

The storage is two tables. documents holds one row per source. chunks holds the pieces: a few hundred words each, with the embedding of that piece and enough metadata to filter and to cite.

In this demo the three numbers of an embedding mean (refund, delivery, account). The question "how do I get my money back?" would embed to something like [0.9, 0.15, 0.1].

Notice chunk 3: "not eligible for money back". It contains the phrase from the question and never uses the word "refund". Vector search found it by meaning.

Where people get hurt

  • The tenant filter is security. Take the tenant id from the authenticated session, never from the model's output or the user's message, and back it with row-level security.
  • When a user deletes a document, its chunks must go in the same transaction. A leftover chunk is a privacy incident: the assistant keeps quoting a deleted file.
  • Retrieved text is untrusted input. A document can contain "ignore your instructions and…". Keep retrieved chunks clearly separated from instructions in the prompt, and do not let retrieved text trigger tool calls on its own.
  • Embedding calls fail and time out. Ingestion should be a queue with retries (see the job queue lesson), not a synchronous part of the upload request.

In backend work

Ingestion is ordinary backend work: an upload endpoint writes a documents row and enqueues a job; a worker chunks, embeds and upserts. Retrieval is one indexed query with the caller's tenant id.

In AI work

Most "the model gave a wrong answer" reports in a RAG system are retrieval problems. Log the chunk ids retrieved for every answer so you can check whether the right text was there, and keep source so answers can link to it.

Check yourself

What does a chunks table need besides the text and the embedding?

A link to its document, its position, the owner or tenant for filtering, the embedding model name, and usually source information for citations.

Why put tenant_id on the chunk row instead of joining to documents?

The filter is applied during the nearest-neighbour query. Having it on the same row keeps the query simple, indexable and hard to get wrong.

What must happen to chunks when their document is deleted?

They are deleted in the same transaction, for example through ON DELETE CASCADE, so deleted content can never be retrieved.

Why record which chunk ids were retrieved for each answer?

To debug wrong answers (was the right text retrieved?), to measure retrieval quality, and to show citations.

Full-text search and hybrid retrieval

Vector search is good at meaning and weak at exact tokens: an order number, an error code, a product SKU, a person's name. Keyword search is the opposite. PostgreSQL has keyword search built in (full-text search), and combining the two is called hybrid search.

"Refunds" was stored as refund and "methods" in the query became method, so they match. Words like "are" and "to" were dropped. The chunks table keeps this in a generated tsv column.

Keyword search found the chunks that say "refund" or "refunded", and the milk chunk through "milk". All five score the same here, because each contains one of the two words once, so the delete-your-account chunk ranks level with the refund policy only because it mentions "refunded". Vector search for "money back" ranks by meaning instead. Neither list is right alone.

Read the two rank columns. Chunks found by both searches score highest. The fusion uses only ranks, never the raw scores, so you do not have to make a ts_rank and a cosine distance comparable.

Where people get hurt

  • to_tsquery needs operators (&, |) and fails on raw user input. Use websearch_to_tsquery('english', $1) for text typed by a person; it accepts quotes and -word.
  • The text search configuration ('english') decides stemming and stop words. Use the right one per language, or 'simple' for codes and names.
  • ts_rank is not BM25. It is good enough for many uses; if keyword ranking quality matters a lot, look at a BM25 extension or a dedicated search engine.
  • Run both halves with the same filters. A hybrid query that applies the tenant filter to only one branch leaks through the other.

In backend work

A product search box usually wants full-text plus trigrams long before it needs vectors: exact matches first, typo tolerance second.

In AI work

Hybrid retrieval is a strong default for RAG over real company documents, which are full of ids, version numbers and jargon that embeddings blur. A reranking model on the fused top 20 is the usual next step.

Check yourself

What does to_tsvector do?

It splits text into words, removes stop words and reduces each word to its stem, producing a searchable list of lexemes with positions.

Why combine keyword and vector search?

Keyword search matches exact tokens (codes, names, rare words) that embeddings handle poorly; vector search matches meaning without shared words. Together they miss less.

How does reciprocal rank fusion score a result?

It sums 1 / (k + rank) over each list the result appears in, with k commonly 60. Only ranks are used, so differently scaled scores need no normalisation.

Which function should parse a search box's raw input into a tsquery?

websearch_to_tsquery, which never raises a syntax error on user text.

Letting a model write SQL, safely

"How many orders were cancelled last month?" A language model can turn that into SQL, run it through a tool you provide, and answer in words. This is text-to-SQL, and it is one of the most useful and most dangerous things you can connect a model to. Useful because every business question becomes answerable. Dangerous because the model will sometimes be wrong, and because text it reads can try to steer it.

The rule: the database enforces the limits, not the prompt. Assume the model will eventually produce any statement at all, and make the harmful ones impossible.

Step 1: describe the schema to the model

Put that in the prompt along with what the schema cannot say: what the status values mean, which column is money and in what unit, how tables join, two or three example questions with correct SQL. Better still, expose a few views with obvious names and give the model only those.

Step 2: make harm impossible

The question was answered from the view. The attempt to read emails from the base table was refused by the database. No instruction in a prompt can change that.

Where people get hurt

  • A filter that checks the SQL text for "DROP" or "DELETE" is not a security control. It is trivially bypassed and blocks legitimate queries mentioning those words. Permissions are the control.
  • Results go back into the model's context. A cell containing "ignore previous instructions…" is a prompt injection. Treat query results as data, and keep the tool unable to do anything but read.
  • Never let the model choose the tenant or user id. Bind it from the session and enforce it with row-level security.
  • Show the generated SQL with the answer. A wrong query that returns a plausible number is the real risk, and a human who can read SQL (you, now) is the best check.
  • Run it against a replica so an expensive question cannot slow the product.

In backend work

The same guard rails serve any untrusted reader: an internal admin console, a partner reporting API, an analyst's notebook. Read-only role, views, timeouts, row caps, replica.

In AI work

Agents with a SQL tool are far more capable than agents with a fixed set of endpoints, and need this lesson's limits in place first. Evaluate text-to-SQL with a set of question and expected-result pairs: compare result sets, not SQL strings, since many different queries are correct.

Check yourself

Why is a prompt instruction ("only write SELECT statements") not enough?

Models make mistakes and can be manipulated by text in their context. Only database permissions, read-only transactions and timeouts guarantee the limit.

Name four database-level guard rails for a text-to-SQL tool.

A role with SELECT on chosen views only; a read-only transaction; statement_timeout; an enforced row limit. Also row-level security for tenant scoping and running on a replica.

Why give the model views instead of base tables?

Views can have clear names, hide sensitive columns, pre-join and pre-aggregate to avoid fan-out errors, and stay stable when the schema changes.

How should you evaluate text-to-SQL quality?

Run generated queries and compare their result sets with expected results for a fixed set of questions. Many differently written queries are equally correct.

Analytics: OLAP, rollups and filling the gaps

The database behind your app does OLTP (online transaction processing): very many small reads and writes, each touching a few rows. Reports, dashboards and model training sets do OLAP (online analytical processing): few queries, each scanning millions of rows to aggregate them. The SQL is the same language. The right engine and table layout differ.

Subtotals in one query

Days with nothing still belong on the chart

GROUP BY day returns only days that have rows. A chart built from that silently skips empty days. The fix is a date spine: generate every day, then LEFT JOIN the data to it.

Where people get hurt

  • Do not run heavy analytics on the primary OLTP database at peak time. Use a replica or a warehouse.
  • count(o.id) in the spine query counts matched orders; count(*) would count the spine row itself and report 1 for empty days.
  • In a ROLLUP result the subtotal rows have NULL in the rolled-up columns. If the data itself can contain NULL there, use GROUPING(column) to tell them apart.
  • Warehouse SQL dialects differ in date functions, arrays and JSON. The engines in the table are named from general knowledge; nothing here was run on them.

In backend work

Product dashboards usually start as queries on a read replica and move to a warehouse when they get slow. Design event tables so they export cleanly: immutable rows, a timestamp, stable ids.

In AI work

Training sets, evaluation dashboards and usage analytics are OLAP work. DuckDB on Parquet files is a common choice for exploring model logs on a laptop with plain SQL; feature tables are built as warehouse transformations.

Check yourself

What is the difference between OLTP and OLAP?

OLTP handles many small transactions on current data; OLAP runs large aggregating queries over history. They favour different storage layouts and engines.

Why are column stores faster for analytics?

Queries read only the columns they need, and values of one column stored together compress very well, so far less data is scanned.

How do you make a daily count include days with zero events?

Generate the full list of days (a date spine, for example with generate_series) and LEFT JOIN the events to it, counting a column from the event side.

What does GROUP BY ROLLUP (a, b) produce?

Groups for (a, b), subtotals for each a, and a grand total.

PostgreSQL, MySQL, SQLite and SQL Server

The core of SQL is the same everywhere: SELECT, joins, GROUP BY, window functions, CTEs, transactions. The edges differ: auto-increment ids, string and date functions, upsert, limits, quoting. If you know PostgreSQL well you can work in any of the others with this table beside you.

You already know this from Swift and Dart

You already ship SQLite: Core Data, Room, Drift and sqflite all store their data in it. Everything in the Foundations and Querying tracks applies to the database inside your app, and you can open that file with the sqlite3 command line tool and query it.

Where people get hurt

  • Only the PostgreSQL and SQLite columns were exercised while building this page. The MySQL and SQL Server entries, and the vector-search row, are from their documentation and may lag behind new releases; check the version you use.
  • Code that works on SQLite in tests can fail on PostgreSQL in production: SQLite does not enforce column types strictly and ignores foreign keys unless PRAGMA foreign_keys = ON.
  • MySQL's default collations compare strings case-insensitively; PostgreSQL compares case-sensitively. A unique email constraint behaves differently on the two.
  • Run integration tests against the same database engine and major version as production.

In backend work

Pick one engine, learn its EXPLAIN output and its locking behaviour well, and use an ORM or query builder only as a convenience, not as a promise of portability.

In AI work

Tell a model which database and version it is writing for, every time. Unstated, it will mix dialects: MySQL date functions with PostgreSQL casts is a common result.

Check yourself

Name three things that differ between PostgreSQL and MySQL.

Upsert syntax (ON CONFLICT vs ON DUPLICATE KEY UPDATE), default isolation level (READ COMMITTED vs REPEATABLE READ), transactional DDL (yes vs no), RETURNING support, case sensitivity of comparisons, auto-increment syntax.

Why can tests on SQLite give false confidence for a PostgreSQL app?

SQLite is loosely typed, has different date and JSON functions, allows only one writer, and needs a pragma to enforce foreign keys, so queries and constraints can behave differently.

How do you limit rows in SQL Server?

SELECT TOP n … or ORDER BY … OFFSET m ROWS FETCH NEXT n ROWS ONLY.

Classic interview questions

Interviewers reuse a small set of questions. These are the ones that are not already answered inside a lesson. Every question from every lesson is also collected in the Interview bank tab.

In backend work

Backend interviews test joins, grouping, indexes, transactions and isolation, in that order of frequency.

In AI work

Data and ML interviews lean on window functions, deduplication, cohorts and "explain this query plan".

Check yourself

DELETE, TRUNCATE and DROP: what is the difference?

DELETE removes rows that match a WHERE, row by row, fires triggers, and can be rolled back. TRUNCATE removes all rows at once by deallocating storage, is much faster, resets identity counters if asked, and in PostgreSQL is still transactional. DROP removes the table itself, with its structure, indexes and constraints.

What is the difference between WHERE and HAVING, in one sentence each?

WHERE filters individual rows before grouping. HAVING filters groups after aggregation.

UNION versus JOIN?

UNION stacks the rows of two queries vertically (same columns). JOIN combines columns from two tables horizontally by matching rows.

What is a clustered index?

An index that determines the physical order of the table's rows, so there can be only one per table. In MySQL InnoDB and SQL Server the primary key is clustered by default and the table is stored inside that index. PostgreSQL tables are heaps: all its indexes are non-clustered, and CLUSTER reorders a table once without maintaining the order.

CHAR, VARCHAR and TEXT?

CHAR(n) is fixed length and pads with spaces. VARCHAR(n) is variable length with a maximum. TEXT is variable length with no declared maximum. In PostgreSQL the three perform the same and TEXT is the usual choice; in MySQL the choice affects indexing and row storage.

What is a candidate key, a primary key and a foreign key?

A candidate key is any minimal set of columns that uniquely identifies a row. The primary key is the candidate key chosen as the row's identity. A foreign key is a column whose values must match a key in another table.

What is referential integrity?

The guarantee that every foreign key value refers to an existing row (or is NULL). Foreign key constraints enforce it.

What is the difference between a correlated and a non-correlated subquery?

A non-correlated subquery can run once on its own. A correlated subquery references the outer row and is logically evaluated for each outer row.

Explain ACID in one line each.

Atomicity: all or nothing. Consistency: constraints hold before and after. Isolation: concurrent transactions do not interfere beyond what the isolation level allows. Durability: committed data survives a crash.

What are the standard isolation levels and which anomaly does each remove?

READ UNCOMMITTED allows dirty reads. READ COMMITTED removes dirty reads. REPEATABLE READ also removes non-repeatable reads (and in PostgreSQL phantoms). SERIALIZABLE removes all, including write skew.

Optimistic versus pessimistic locking?

Pessimistic locks the row before working on it (SELECT … FOR UPDATE), so others wait. Optimistic takes no lock, and at write time checks a version column and retries if someone else changed the row. Use pessimistic when conflicts are frequent, optimistic when rare.

How would you find the second highest salary (or price)?

SELECT MAX(price) FROM products WHERE price < (SELECT MAX(price) FROM products), or DENSE_RANK() in a CTE filtered to rank 2, which generalises to the nth and handles ties.

How do you find and remove duplicate rows?

Find with GROUP BY the duplicate key HAVING COUNT(*) > 1. Remove by numbering rows per key with ROW_NUMBER() and deleting those with number > 1, or DELETE WHERE id NOT IN (SELECT MAX(id) … GROUP BY key) to keep the newest. Then add a unique constraint so they cannot return.

What is a covering index and what is an index-only scan?

A covering index contains all columns a query needs. The database can then answer from the index without visiting the table, which PostgreSQL shows as an Index Only Scan.

Why might a query be slow even though the column is indexed?

The condition is not sargable (function or cast on the column, leading wildcard, type mismatch), the filter matches too many rows, the wrong column leads a composite index, statistics are stale, or the time is spent elsewhere: a sort, a join, lock waits.

What is a view, and can you update through it?

A view is a stored query. Simple views over one table (no aggregates, DISTINCT or joins) are automatically updatable in PostgreSQL; others need INSTEAD OF triggers.

What is denormalisation and when would you do it?

Deliberately storing redundant data (a cached total, a copied name) to avoid joins or aggregation at read time. Do it for measured read performance, and accept the cost of keeping the copies consistent.

What is the difference between a transaction and a batch?

A batch is several statements sent together; they are not atomic unless wrapped in a transaction. A transaction guarantees all-or-nothing.

How does an index affect writes?

Every INSERT, and every UPDATE or DELETE that touches indexed columns, must also update each index. More indexes mean slower writes and more storage.

What is a surrogate key?

An artificial identifier with no business meaning (an auto-number or UUID), used as the primary key because it never changes.

What are window functions and how do they differ from GROUP BY?

They compute a value across a set of rows related to the current row, defined by OVER (PARTITION BY … ORDER BY …), and return every row. GROUP BY collapses each group to one row.

What is a CTE and when is it better than a subquery?

A named subquery defined with WITH. It is better when the logic has several steps, is referenced more than once, or is recursive; it makes long queries readable and testable step by step.

What is sharding, and how is it different from partitioning?

Partitioning splits a table into pieces inside one database server. Sharding spreads data across several servers, each holding a subset, which scales writes and removes cross-shard joins and transactions.

How would you design the schema for an e-commerce order?

customers, products, orders (customer_id, status, timestamps), order_items (order_id, product_id, qty, unit_price snapshot, composite key), payments (order_id, amount, status, idempotency key). Foreign keys throughout, CHECKs on money and quantity, indexes on orders(customer_id, placed_at), status history as an append-only table.

You are told "the orders page is slow". Walk through your investigation.

Find the exact query (logs, pg_stat_statements). Run EXPLAIN (ANALYZE, BUFFERS). Look for sequential scans with many rows removed, row estimate errors, sorts, nested loops with huge loop counts. Check for N+1 at the application level. Add or fix an index, rewrite a non-sargable condition, switch OFFSET to keyset pagination, then measure again.

More interview questions: scenarios and deep dives

Fifty more questions, grouped the way interviews go: quick fundamentals, query writing, design, transactions, performance, and the newer AI and data questions. The scenario questions have no single right answer; what is scored is whether you name the trade-offs.

In backend work

Senior backend rounds are mostly the design, transaction and performance questions here.

In AI work

AI engineer and data rounds add vector search, retrieval storage, evaluation queries and safe text-to-SQL.

Check yourself

What is the difference between COUNT(*), COUNT(1) and COUNT(column)?

COUNT(*) and COUNT(1) both count rows and perform the same. COUNT(column) counts rows where that column is not NULL.

What is the difference between RANK, DENSE_RANK and ROW_NUMBER?

ROW_NUMBER gives every row a different number. RANK gives tied rows the same number and leaves gaps after them. DENSE_RANK gives tied rows the same number with no gaps.

What does DISTINCT do when several columns are selected?

It removes rows that are identical across all selected columns, not duplicates of the first column only.

Can you use an aggregate in WHERE? A window function?

Neither. Aggregates are filtered in HAVING; window functions are computed after WHERE, so filter them in an outer query.

What is a cross join and when is it useful?

Every row of one table paired with every row of the other. Useful for generating combinations: every product for every day, every user for every feature flag.

What is the difference between IN and EXISTS?

IN compares a value against a list or subquery result. EXISTS tests whether a correlated subquery returns any row and can stop at the first. They often plan the same; NOT EXISTS is safer than NOT IN when NULLs are possible.

How do you select every nth row, or a random sample?

Number rows with ROW_NUMBER() and keep those where the number modulo n is 0. For a sample, ORDER BY random() LIMIT n on small tables, TABLESAMPLE on large ones.

How do you pivot rows into columns?

One conditional aggregate per output column: SUM(CASE WHEN month = 'Jan' THEN amount END) AS jan, or FILTER (WHERE …). Some databases also have PIVOT or crosstab.

How would you find gaps in a sequence of ids?

Compare each id with the next using LEAD and keep rows where next − id > 1, or left join a generated series to the table and keep the missing ones.

How do you get the top 3 rows per group?

ROW_NUMBER() OVER (PARTITION BY group ORDER BY metric DESC) in a CTE, then WHERE rn <= 3. A LATERAL join with LIMIT 3 is an alternative that can use an index per group.

What is a LATERAL join?

A join where the right side is a subquery that can refer to columns of the left row, evaluated per left row. It expresses "for each customer, their 3 latest orders" directly.

What does COALESCE do, and NULLIF?

COALESCE returns its first non-NULL argument. NULLIF(a, b) returns NULL when a equals b, otherwise a; it is commonly used to avoid division by zero.

Why might two queries that look equivalent return different row counts with LEFT JOIN?

A condition on the right table placed in WHERE removes the NULL-padded rows, while the same condition in ON keeps them.

A SUM over a join is too high. What is the most likely cause?

Fan-out: the join produces several rows per entity being summed, usually because two one-to-many child tables were joined together. Aggregate each child separately first.

How do you update one table from another?

PostgreSQL: UPDATE t SET … FROM other WHERE other.key = t.key. Standard and portable: a correlated subquery in SET, or MERGE.

What is the difference between a temporary table and a CTE?

A temporary table is a real table that lasts for the session, can be indexed and analysed, and can be reused across statements. A CTE exists for one statement.

What are first, second and third normal form, each in one line?

1NF: atomic values, no repeating groups. 2NF: no column depends on only part of a composite key. 3NF: no column depends on another non-key column.

When would you choose a composite primary key over a surrogate id?

For pure junction tables where the pair is the identity (order_id, product_id) and nothing else references the row. Add a surrogate id when other tables need to point at it.

How do you model a hierarchy in SQL?

Adjacency list (parent_id, queried with recursive CTEs) is the default. Alternatives: materialised path (store '1/4/9'), nested sets, closure table (store every ancestor-descendant pair) when reads of whole subtrees dominate.

How do you store money and why?

As NUMERIC with fixed scale or as integer minor units, with a currency column. Floating point cannot represent decimal fractions exactly.

How would you implement soft delete, and what does it complicate?

A deleted_at timestamp. Every query must exclude deleted rows, unique constraints must ignore them (partial unique index), and foreign keys still see them.

How do you keep a history of changes to a row?

An append-only history or events table written in the same transaction (by application code or a trigger), or temporal tables where the database supports them. Never rely on overwriting.

Design question: a table of likes on posts. What keys and indexes?

likes(user_id, post_id, created_at) with primary key (post_id, user_id) to stop double likes and serve "who liked this post"; an index on (user_id, created_at) for "what did this user like". Keep a cached like count on posts, updated in the same transaction or asynchronously.

Design question: how do you make sure only one booking exists for a slot?

A unique constraint on (resource_id, slot), so the second insert fails. For overlapping time ranges, an exclusion constraint on a range type in PostgreSQL, or lock the resource row with SELECT … FOR UPDATE before checking.

What happens to a foreign key's child rows on delete, and how do you choose?

RESTRICT or NO ACTION refuses the delete, CASCADE deletes the children, SET NULL detaches them. Choose by whether the child has meaning without the parent.

What is the difference between a unique constraint and a unique index?

In PostgreSQL a unique constraint is implemented by a unique index. A plain unique index can do more: be partial or on an expression. Only a constraint can be the target of a foreign key.

What is a transaction log (WAL) for?

Durability and recovery: changes are appended to the log before data files are modified, so committed work can be replayed after a crash. It also feeds replication and point-in-time recovery.

Two requests both read a balance of 100 and each subtract 30. What is the final balance and how do you fix it?

70 instead of 40: a lost update. Fix with an atomic UPDATE … SET balance = balance - 30 WHERE balance >= 30, a row lock with SELECT … FOR UPDATE, or a version check with retry.

What is a phantom read?

Within one transaction the same range query returns extra rows the second time because another transaction inserted and committed matching rows.

What is the difference between a shared lock and an exclusive lock?

Many transactions can hold a shared lock on the same row at once (it blocks writers). Only one can hold an exclusive lock (it blocks other writers and lockers). FOR SHARE and FOR UPDATE request them explicitly.

How does PostgreSQL decide a deadlock exists and what does your code do?

After waiting for deadlock_timeout it checks the wait graph for a cycle and aborts one transaction with error 40P01. The application retries that transaction.

What is two-phase commit and when is it needed?

A protocol for committing one transaction across several databases: all participants prepare, then all commit. It is needed for atomicity across systems and is slow and fragile, which is why patterns such as the outbox and sagas are usually preferred.

What does idempotent mean for a write API, and how does SQL help?

Repeating the request does not repeat the effect. A unique idempotency key with INSERT … ON CONFLICT DO NOTHING lets the database detect the repeat atomically.

Why is a long-running transaction dangerous?

It holds locks, blocks schema changes, pins old row versions so VACUUM cannot clean up, and occupies a pooled connection.

What is the difference between an index scan, an index-only scan and a bitmap scan?

Index scan: walk the index and fetch each row from the table. Index-only scan: answer from the index without the table. Bitmap scan: collect matching locations from the index first, then read table pages in physical order, good for medium selectivity or combining indexes.

What is index selectivity and cardinality?

Cardinality is the number of distinct values. Selectivity is the fraction of rows a condition matches. Indexes help most when the condition is highly selective (matches few rows).

Why does WHERE lower(email) = 'x' not use the index on email, and what do you do?

The index stores email, not lower(email). Create an expression index on lower(email), or store a normalised column.

You added an index and writes got slower. Why?

Every insert, and every update of an indexed column, now also maintains that index and writes more WAL.

How do you find unused or missing indexes in PostgreSQL?

Unused: pg_stat_user_indexes with idx_scan = 0 over a representative period. Missing: slow queries from pg_stat_statements whose plans show sequential scans removing most rows, and tables with high seq_tup_read in pg_stat_user_tables.

A query is fast in the console and slow from the application. What do you check?

A different plan for the parameterised form (generic plan, type mismatch between parameter and column), a different role or search_path, lock waits, pool wait time, network latency or the amount of data being transferred, and N+1 around it.

How would you paginate a feed of 50 million rows?

Keyset pagination: order by (created_at, id) with a matching index and filter with a row comparison against the last row seen. Never deep OFFSET.

How would you delete 100 million old rows from a live table?

In small batches with pauses, each its own transaction, using an indexed condition; or better, partition by time and drop whole partitions. Never one giant DELETE.

How do you add a NOT NULL column with a default to a huge live table?

In PostgreSQL 11+ adding a column with a constant default is a metadata change and instant. For older versions or volatile defaults: add nullable, backfill in batches, add a NOT VALID check, validate, then set NOT NULL.

What is connection pooling and what goes wrong without it?

Reusing a small set of open connections. Without it each request pays connection setup, and a burst of traffic opens more connections than the server can serve.

When would you add a read replica, and what new problem does it create?

When reads saturate the primary. It introduces replication lag, so a read after a write may be stale; critical reads must go to the primary.

When does caching beat a faster query, and what is the risk?

When the same result is requested far more often than it changes. The risk is staleness and invalidation complexity; a materialised view or a short TTL keeps it manageable.

How does vector similarity search differ from a normal indexed lookup?

A B-tree finds exact or range matches exactly. A vector index finds approximately nearest neighbours by distance, trading some recall for speed, and its result depends on search-effort settings.

How would you design tables for a RAG system used by many customers?

documents and chunks tables; each chunk has document_id, tenant_id, position, text, embedding and embedding model. Filter by tenant in the query and enforce it with row-level security, index the vector with HNSW and the metadata with B-tree or GIN, cascade deletes from documents.

How do you make an LLM-generated SQL query safe to run?

Run it as a role with SELECT on selected views only, in a read-only transaction, with a statement timeout and an enforced row limit, on a replica, with tenant scoping done by row-level security rather than by the prompt.

How would you compare two prompt versions using SQL?

Store one row per test case per version. Compare pass rate overall and per category with conditional aggregates, then self-join on the case id to list cases that passed before and fail now.

What is connection pooling and what goes wrong without it?

Reusing a small set of open connections. Without it each request pays connection setup, and a burst of traffic opens more connections than the server can serve.

When would you add a read replica, and what new problem does it create?

When reads saturate the primary. It introduces replication lag, so a read after a write may be stale; critical reads must go to the primary.

When does caching beat a faster query, and what is the risk?

When the same result is requested far more often than it changes. The risk is staleness and invalidation complexity; a materialised view or a short TTL keeps it manageable.

How does vector similarity search differ from a normal indexed lookup?

A B-tree finds exact or range matches exactly. A vector index finds approximately nearest neighbours by distance, trading some recall for speed, and its result depends on search-effort settings.
