Start here · Basic

A PWA is a website that the phone treats like an app

It is still HTML, CSS and JavaScript served from a URL. Three additions change how it behaves: a manifest file tells the phone how to install it, a service worker script lets it open with no connection, and the Push API lets your server wake it up to show a notification.

Try the phone on the right. Add a task, switch the network off, add another, then switch it back on. The log shows what the real app does at each step. Chapter 4 explains every line of it.

You already know this shape from mobile work. The manifest is the web's Info.plist / AndroidManifest.xml. The service worker is a background isolate with no UI access. IndexedDB is the on-device database. Push goes through APNs and FCM, the same services native apps use.

  Pillar 1 · Basic
  
    Web App Manifest
    
  
    The manifest is a small JSON file that describes your app to the operating system: its name, its icons, which page opens first, and whether it shows browser controls. Without it the browser sees a website. With it the browser sees something it can install.
    

  
    The manifest of the task app
    
  

  
    
    
    FieldWhat it doesGet it wrong and
    
    
    name, short_nameFull name for the install dialog and splash screen; short name under the icon (aim for 12 characters or fewer).The name is cut off with "…" on the home screen.
    
    
    start_urlThe page that opens when the icon is tapped.The app opens on whichever page the user installed from, or shows the offline page because that URL was never cached.
    
    
    idThe app's identity. Lets you change start_url later without the browser treating it as a different app.A changed start URL produces a second install.

    iconsPNG at 192 and 512 pixels at least. A maskable icon fills the whole square so Android can crop it to any shape.No install prompt, or a small icon inside a white circle on Android.
    
    
    theme_color, background_colorColour of the status bar and title bar; colour of the splash screen before your CSS loads.A white flash on launch in dark mode.

    Linking it from the page
    
  
    The page points at the manifest with one <link> tag. iPhone needs a few extra tags because Safari takes its home-screen icon from apple-touch-icon.
    
  

  
    What makes an app installable
    
  
    
    
    Chrome and Edge
      
    • Served over HTTPS (or localhost).
    • Manifest with name or short_name, start_url, icons at 192 and 512 px, and display set to standalone, fullscreen or minimal-ui.
    • A service worker is no longer required for the prompt. You still need one for offline.
    
    
    Safari on iPhone and iPad
      
    • The user installs from Share, then Add to Home Screen. There is no prompt you can trigger. On iOS 26 Share sits under the ••• button, and Add to Home Screen is behind More in the share sheet.
    • From iOS 26, a site added to the Home Screen opens as a web app by default, even without a manifest. Seen on the iOS 26 simulator: the Add to Home Screen sheet has an "Open as Web App" switch that is already on, and it took the name and icon from the task app's tags. On iOS 16.4 to 18 it needs display: standalone.
    • Other iPhone browsers can add to the Home Screen too (since iOS 16.4).
    
  
    

  
    Maskable icons
    
  
    Android crops icons into circles, squircles and other shapes. A maskable icon has a full-bleed background and keeps its artwork inside the central 80% circle, so nothing important is cut. Provide one normal icon (purpose: "any") and one maskable. Do not mark a single file as "any maskable": it will look too small in one place or cropped in the other.
    

  
    Common mistakes
    
  
      
    
    • Serving the manifest from a path that redirects to a login page. Open the manifest URL directly and check it returns JSON.
      • 
    
    • A start_url outside scope. The browser ignores the manifest.
      • 
    
    • Only an SVG or a 144 px icon. Chrome wants PNG at 192 and 512.
      • 
    
    • Forgetting apple-touch-icon. iPhone then uses a screenshot of the page as the icon.
      • 
  
    
  
    Check it. Chrome DevTools, Application panel, Manifest. It lists every field it read, shows the icons, previews the maskable crop and prints installability warnings.
    

    


    
  Pillar 2 · Basic
  
    Service Workers
    
  
    A service worker is a JavaScript file the browser runs in the background, separate from your page. It sits between your app and the network. Every request the page makes reaches the worker first, and the worker decides how to answer. That is what makes offline possible.
    

  
    
    
    What it can do
    • Intercept requests (fetch event).
    • Read and write Cache Storage and IndexedDB.
    • Receive push messages and show notifications.
    • Run when no tab is open (push, background sync).
    
    
    What it cannot do
    • Touch the DOM, window or localStorage.
    • Stay alive. The browser stops it after about 30 seconds of idle and restarts it for the next event, so global variables are lost.
    • Run on plain HTTP (except localhost).
    • Control pages outside its scope (the folder it is served from).
    
  
    

  
    Life cycle
    
  
    

  
    
    
    First visit
    1. The page loads from the network as usual and calls register().
    2. install runs. The worker downloads the app shell into a cache.
    3. There is no older worker, so it activates straight away.
    4. clients.claim() makes it control the page that is already open. Without that call, control starts on the next page load.
    
    
    You deploy a new version
    1. On the next visit the browser re-downloads sw.js. If even one byte differs, it is a new worker.
    2. The new worker installs into a new cache while the old one keeps serving the old files.
    3. It waits. Two versions of your code never run in the same tab.
    4. When all old tabs close, or the user accepts your "Reload" prompt, it activates and deletes the old cache.
    
  
    

  
    Step 1: register it from the page
    
  
    Registration is one call. Most of this code handles the update prompt, explained under Advanced.
    
  

  
    Step 2: install, the moment to fill the cache
    
  
  
  
    event.waitUntil(promise) appears in every handler. It tells the browser "do not stop me until this promise settles". Work started without it can be cut off halfway.
    

  
    Step 3: activate, the moment to clean up
    
  

  
    Step 4: fetch, the moment to answer requests
    
  
    The handler below is a router. It looks at each request and picks a strategy. The strategies themselves are the next chapter.
    
  

  
    Common mistakes
    
  
      
    
    • Putting sw.js in a subfolder. A worker at /js/sw.js controls only /js/. Serve it from the root.
      • 
    
    • Caching sw.js itself for a long time. Send it with Cache-Control: no-cache. Browsers cap the HTTP cache for the worker script at 24 hours anyway, but a day-long stale worker is still painful.
      • 
    
    • Keeping state in a global variable. The worker is stopped and restarted often. Persist to IndexedDB or the Cache.
      • 
    
    • Changing a cached file without changing VERSION. The worker file is byte-identical, so the browser sees no update and users keep the old file.
      • 
    
    • Calling respondWith() after an await. It must be called synchronously inside the event handler.
      • 
  
    
  
    Check it. DevTools, Application, Service workers shows the state (activated, waiting), lets you tick "Update on reload" while developing, and has an Offline checkbox. Application, Cache storage shows exactly what was stored.
    

    


    
  Pillar 3 · Intermediate
  
    Caching strategies
    
  
    A caching strategy is the rule a service worker follows to answer one request: look in the cache, ask the network, or both, and in which order. There are five classic rules. A real app uses several, one per kind of file.
    

  
    Try each strategy
    
  
    
    
    Strategy
    
    
    Network
    
    
    Cache
    
    
    
    
      
    
      
    
      
      
      Time until the page gets a response
      
      
      
      
      answered from cacheanswered from network
      
      
      Numbers come from a simple model (cache read 5 ms, the network delay you picked, a 2.5 second timeout for network first). They are not measurements of a real site. For scale, in the task app on this Mac a cache-first hit took 0.8 ms and a network call to the local server 1.8 ms (median of 30 requests in Chromium), so the 5 ms cache figure is cautious. A real network adds tens to thousands of milliseconds; a cache read does not change.
      
    
      
  
      

  
      Which strategy for which file
      
  
      
    
      StrategySpeedFreshnessWorks offlineUse it for
      
    
      Cache firstInstantOld until the cache name changesYesThe app shell, fonts, hashed JS and CSS, icons
      
    
      Network firstNetwork speed; slow links wait for the timeoutAlways latest when onlineIf cached beforeHTML pages, an account balance, a feed's first page
      
    
      Stale while revalidateInstant after the first visitOne visit behindIf cached beforeAvatars, product images, config that changes rarely
      
    
      Cache onlyInstantNever updatesYesFiles you precached and never fetch any other way
      
    
      Network onlyNetwork speedAlways latestNoPOST, PUT, DELETE, payments, analytics, anything per-user and sensitive
      
  
      

  
      The three the task app uses
      
  
  
      Cache only and network only need no helper. Cache only is event.respondWith(caches.match(request)). Network only is not calling respondWith() at all, which is what the task app does for /api/ and for every non-GET request.
      

  
      Precache and runtime cache
      
  
      
    
      Precache
      A fixed list of files stored during install, before the user needs them. This is the app shell. It guarantees that the second visit works offline. Keep it small: every byte is downloaded by every user on first visit.
      
    
      Runtime cache
      Responses stored as the user browses, by the strategies above. It can grow without limit, so real apps cap it (for example, keep the 50 newest entries) and delete it by name when the version changes.
      
  
      

  
      Rules that prevent hard bugs
      
  
        
    
      • Clone before you store. A response body is a stream that can be read once. cache.put(request, response.clone()) keeps the original for the page.
        • 
    
      • Check response.ok before caching. Otherwise a 404 or 500 page is saved and served forever.
        • 
    
      • Only GET can be cached. cache.put throws on a POST request.
        • 
    
      • Be careful with cross-origin files. A response fetched without CORS is "opaque": you cannot read its status, so you may cache an error, and Chrome counts each opaque entry as about 7 MB against your storage budget. Ask the other server for CORS headers, or host the file yourself.
        • 
    
      • Never cache per-user responses under a shared URL unless you clear the caches on logout. The next person to sign in on that device would see them.
        • 
    
      • cache.addAll is all or nothing. One 404 in the precache list fails the whole install.
        • 
  
      
  
      Check it. DevTools Network panel: the Size column says "(ServiceWorker)" for responses the worker answered. Tick Offline and reload to see which requests still succeed.
      

      


      
  Pillar 3, continued · Intermediate
  
      Offline data
      
  
      Caching files makes the app open offline. It does not make the app useful offline. For that, the user's data must live on the device, and every change must be saved locally first and sent to the server later. This is called local-first, and it is also what makes an app feel instant when online.
      

  
      Where to keep what
      
  
      
    
      StorageHoldsUse in a PWA
      
    
      Cache StorageRequest and response pairsFiles: HTML, CSS, JS, images. Readable from page and worker.
      
    
      IndexedDBJavaScript objects, with indexes and transactionsApp data: tasks, drafts, the outbox. Readable from page and worker.
      
    
      localStorageSmall stringsA theme preference at most. It blocks the main thread and service workers cannot read it.
      
    
      CookiesTiny strings sent with every requestSession identity only.
      
  
      

  
      The write path
      
  
      User taps Addone transactionSave task + queue change in outboxinstantRedraw listthenTry to send outboxsuccessRemove from outbox
      
  
      Send fails (offline)change stays queuedOutbox keeps itconnection returnsBackground Sync or page retryin orderServer catches up
      
  
      The UI never waits for the network. The outbox is a list of changes the server has not confirmed yet. It survives closing the tab, restarting the phone and losing power, because it is in IndexedDB.
      

  
      Opening the database
      
  
      IndexedDB uses events instead of promises, so the first job is a small wrapper. Stores are created in onupgradeneeded, which runs only when the version number rises. That is your migration hook.
      
  

  
      Saving a task and queuing the change together
      
  
      The key detail: the task and its outbox entry are written in one transaction. If the app crashed between two separate writes, you could have a task the server never hears about.
      
  

  
      The page: write locally, redraw, sync
      
  

  
      Sending the outbox
      
  
      Changes are replayed oldest first. A network failure or a 5xx response stops the loop and keeps the entry. A 4xx response means the server rejected the change for good, so it is dropped rather than retried forever.
      
  

  
      When to try: Background Sync plus a fallback
      
  
      Background Sync lets the worker send the outbox after the tab is closed, as soon as the device is online. Only Chromium browsers have it. Safari and Firefox need the page to retry, so the app does both.
      
  
  

  
      Why retrying is safe: the server side
      
  
      A request can reach the server while its response is lost on the way back. The client then sends it again. This is harmless only if the server treats a repeat as a no-op. The client creates the task id, and the server stores by that id.
      
  

  
      Conflicts
      
  
      The app uses last write wins: each task carries updatedAt, and the server ignores a change older than what it has. That is enough for one person on two devices. It silently loses an edit when two people change the same task while offline. The Advanced chapter lists the stronger options.
      

  
      Common mistakes
      
  
        
    
      • Trusting navigator.onLine. true only means a network interface is up. Hotel Wi-Fi with a login page reports online. The reliable test is whether the request succeeded.
        • 
    
      • Ids made by the server. An offline-created task then has no id until sync, and every reference to it must be rewritten. Use crypto.randomUUID() on the client.
        • 
    
      • A POST that creates a row on every call. Retries create duplicates. Use PUT by id, or send an idempotency key.
        • 
    
      • Awaiting something else in the middle of a transaction. An IndexedDB transaction closes itself when the event loop goes idle. Do all the store calls synchronously, as withTx does.
        • 
  
      
  
      Check it. DevTools, Application, IndexedDB shows both stores. Stop the server, add a task, and watch a row appear in outbox. Start the server and it disappears.
      

      


      
  Pillar 4 · Intermediate
  
      Push notifications
      
  
      Push lets your server send a message to a user's device when your app is closed. The browser vendor runs a push service that holds a connection to the device. Your server hands the message to that service, the service delivers it, the browser starts your service worker, and the worker shows a notification.
      
  
      Run end to end on 13 November 2026 in Chrome 157 on macOS, in a clean profile with notifications allowed. The app subscribed with Google's push service, the server sent a reminder 5 seconds later with the tab closed, and the notification arrived with the right title, body and tag. A second push replaced the first instead of stacking. After unsubscribing, the next send got a "gone" answer and the server deleted the subscription. Still not run: tapping the notification (it is an operating-system banner a script cannot click), and push on a real iPhone.
      

  
      
    
      Two different APIs
      • Notifications API draws the banner. It works without any server.
      • Push API delivers a message from a server to the worker. It draws nothing.
      A push notification is the two used together.
      
    
      Three sets of keys
      • VAPID key pair: your server's identity. The public half goes to the browser, the private half signs each push.
      • Subscription keys (p256dh, auth): made by the browser, used by your server to encrypt the payload so the push service cannot read it.
      
  
      

  
      The whole flow
      
  
      

  
      The page: ask, subscribe, send to the server
      
  

  
      The worker: receive, show, handle the tap
      
  

  
      The server: keys, subscriptions, sending
      
  
      The web-push package does the encryption and signing. Your job is storing subscriptions and removing dead ones.
      
  

  
      Platform rules
      
  
      
    
      RuleDetail
      
    
      Ask from a user actionCall requestPermission() inside a tap handler. Safari requires it. Chrome hides the prompt for sites people usually deny.
      
    
      Every push shows a notificationuserVisibleOnly: true is a promise. Chrome shows a generic "site updated in the background" banner if you break it. Safari cancels the subscription after a few silent pushes.
      
    
      iPhone and iPadWeb push exists only inside an app added to the Home Screen (iOS 16.4 and later). In a Safari tab, PushManager does not exist. Tell users to install first.
      
    
      Denied is finalAfter "Block" you cannot ask again. The user must change it in browser settings. Ask at a moment when the value is obvious.
      
    
      Subscriptions expireThe push service answers 404 or 410 for a dead endpoint. Delete it. Re-send the current subscription to your server on each app start in case it changed.
      
    
      iPhone simulatorChecked on the iOS 26 simulator: the "Turn on reminders" button is missing in a Safari tab and appears once the app is opened from the Home Screen, and the system permission prompt shows. The subscription itself did not complete there. Use a real iPhone to test delivery.
      
    
      Headless ChromeIn headless Chrome pushManager.subscribe() never settles: no error, no result. Automated push checks need a normal Chrome window.
      
    
      Payload sizeAbout 4 KB. Send an id and a short text, and let the app fetch the rest.
      
  
      

  
      Asking well
      
  
        
    
      • Explain first, in your own UI: "Get a reminder when a task is due". Show the browser prompt only after the user taps your button.
        • 
    
      • Let people pick what they receive. One irrelevant notification gets the whole app blocked.
        • 
    
      • Use tag so a newer message replaces the older one instead of stacking five banners.
        • 
    
      • A tap should land on the exact screen the message was about, not the home page.
        • 
  
      

  
      Try it
      
  
        
    
      1. Run npm install then node server.js in the app folder and open http://localhost:5199 in Chrome.
        2. 
    
      2. Tap "Turn on reminders" and allow notifications. On a Mac, also allow Chrome in System Settings, Notifications.
        3. 
    
      3. Tap "Send a test reminder", then close the tab within 5 seconds. The notification should still arrive.
        4. 
    
      4. Tap the notification. The app should open or come to the front.
        5. 
  
      
  
      Check it. DevTools, Application, Service workers has a "Push" box that fires a fake push event at your worker, so you can test the display code without a server.
      

      


      
  Polish · Intermediate
  
      Making it feel native
      
  
      Installing and working offline make a PWA behave like an app. Feeling like one is mostly small details: no browser bar, content that respects the notch, taps that respond at once, and no web habits such as text selection on buttons or a page that bounces.
      

  
      The CSS that does most of the work
      
  

  
      
    
      Native behaviourHow to get it on the web
      
    
      Opens instantlyPrecache the app shell and draw from local data first. Fetch fresh data after the first paint.
      
    
      No browser bar"display": "standalone" in the manifest.
      
    
      Content clear of notch and home indicatorviewport-fit=cover plus env(safe-area-inset-*) padding.
      
    
      Status bar matches the app<meta name="theme-color">, one per colour scheme.
      
    
      Taps respond immediatelytouch-action: manipulation, targets of 44 px or more, a pressed state in CSS.
      
    
      No accidental zoom on input focus (iPhone)Inputs with a font size of 16 px or more.
      
    
      No pull-to-refresh or page bounceoverscroll-behavior-y: none on the body.
      
    
      Screen transitionsThe View Transitions API (document.startViewTransition), with a plain swap as the fallback.
      
    
      Number on the app iconThe Badging API, below.
      
    
      Share sheetnavigator.share({ title, text, url }) from a tap.
      
    
      Dark modeprefers-color-scheme media query and color-scheme.
      
  
      

  
      Your own install button
      
  
      Chromium fires beforeinstallprompt when the app is installable. Keep the event and show a button at a moment that makes sense, for example after the user has added a few tasks. Safari has no such event, so detect iPhone and explain the manual steps.
      
  

  
      A badge on the icon
      
  

  
      Layout differences when installed
      
  
        
    
      • No back button. In standalone mode there is no browser chrome. Every screen needs its own way back.
        • 
    
      • No address bar. Users cannot copy the URL. Add a share action where a link matters.
        • 
    
      • No reload button. This is why the update prompt in the app matters: without it users may run an old version for weeks.
        • 
    
      • External links open in an in-app browser view on Android and in Safari on iPhone. Keep your own pages inside scope.
        • 
  
      

  
      Common mistakes
      
  
        
    
      • Using 100vh for a full-height layout. On mobile it is taller than the visible area. Use 100dvh.
        • 
    
      • Hiding the install button with user-agent checks. Use the display-mode media query, as the stylesheet does.
        • 
    
      • Disabling zoom with user-scalable=no. It breaks accessibility, and iOS ignores it.
        • 
    
      • Showing the install prompt on first visit. People dismiss it, and Chrome will not offer it again for a while.
        • 
  
      
  
      Check it. DevTools device toolbar previews notches for common phones. For the real thing on a phone, the app must be served over HTTPS: deploy it or use a tunnel.

  Advanced
  
      Advanced topics
      
  
      These are the problems that appear after launch: users stuck on an old version, storage that disappears, bugs that only happen on one phone. The four snippets in this chapter are not part of the task app. Each was copied from this page and run in Chrome 157 on 13 November 2026; the result is under it.
      

  
      1. Updates without breaking open tabs
      
  
      Deploy new filesnext visitBrowser fetches sw.js, sees a changeinstallNew worker waitsuser taps ReloadskipWaiting()controllerchangePage reloads once
      
  
      
    
      ApproachBehaviourRisk
      
    
      Do nothingThe new version takes over after every tab of the app is closed.Installed apps are rarely fully closed. Users stay on old code for a long time.
      
    
      skipWaiting() inside installThe new worker takes over at once.An open page built from v1 HTML starts receiving v2 files. Lazy-loaded scripts can fail.
      
    
      Prompt, then skip and reload (the task app)The user chooses the moment.Slightly more code. This is the safe default.
      
  
      
  
      Bigger apps give files hashed names (app.3f9a1c.js) and generate the precache list at build time, so a file's URL changes whenever its content does. Then cache first is always correct and you never bump a version by hand.
      

  
      2. A kill switch
      
  
      If a bad worker ships, you cannot ask users to clear their browser. Deploy this as sw.js: it removes itself and every cache, then reloads open pages.
      
  
  
      Result. Deployed over the task app's v1 worker: the cache list went from static-v1 to empty, the registration count from 1 to 0, and the open page reloaded once with no controller.
      

  
      3. Storage limits and eviction
      
  
        
    
      • Cache Storage and IndexedDB share one budget per origin. Chromium allows up to about 60% of the disk; Safari and Firefox are in the same order of size for normal sites. The Start chapter shows your live number.
        • 
    
      • Storage is "best effort" by default: under disk pressure the browser may delete an origin's data, least recently used first.
        • 
    
      • Safari deletes script-written storage for a site not visited in 7 days of browser use. Apps added to the Home Screen are exempt, which is one more reason to encourage installing.
        • 
    
      • Ask for persistence. Chrome grants it automatically to installed or often-used sites; Firefox asks the user.
        • 
    
      • Handle QuotaExceededError on writes: delete the runtime cache and retry.
        • 
  
      
  
  
      Result. In a brand-new Chrome profile persist() returned false and logged "Storage is still best-effort", which is expected for a site with no engagement yet. trimCache on a cache of 5 entries with a limit of 3 kept the 3 newest.
      

  
      4. Navigation preload
      
  
      When a user opens the app after a pause, the browser must start the worker before it can even begin the page request. Navigation preload starts the network request in parallel with worker start-up. It only helps strategies that go to the network for HTML. It is not in Firefox's or Safari's oldest supported versions, so feature-test it.
      
  
  
      Result. navigationPreload.getState() reported enabled, and the server received the page request with the header Service-Worker-Navigation-Preload: true. With the server stopped, a reload returned the cached /index.html. The snippet has no install step, so the run added one that caches /index.html; without it the fallback has nothing to return.
      

  
      5. Workbox
      
  
      Workbox is Google's library for service workers. It gives you the same strategies as tested, configurable classes, builds the precache list with file hashes, and handles cache expiry and a background-sync queue. Write a worker by hand once, as in this guide, so you can debug one. Then use Workbox in real projects. It needs a bundler such as Vite or webpack.
      
  
  
      Result. Bundled with esbuild (about 105 KB before minifying) with a two-file manifest. Workbox created its precache with both files and an images cache, and with the server stopped the page and its image still loaded. One thing to know: the pages cache stayed empty, because precacheAndRoute is registered first and answers / from the precache before the network-first route is tried. Network first only applies to pages that are not in the precache list.

      ApproachHow it worksGood for
      
    
      Last write winsThe newest timestamp replaces the record. Device clocks can be wrong, so prefer a server-assigned version number.Personal data on a few devices
      
    
      Per-field mergeSend only changed fields with the version they were based on; merge fields that do not collide.Forms, settings, task details
      
    
      Reject and askThe server answers 409 when the base version is old; the app shows both versions.Documents where silent loss is unacceptable

      7. Security
      
  
        
    
      • HTTPS everywhere. A service worker can rewrite every response, so browsers refuse to install one over HTTP.
        • 
    
      • A worker outlives your deploy. An XSS hole that lets an attacker register a worker gives them lasting control of the origin. Keep a strict Content-Security-Policy and never serve user uploads from the app's origin.
        • 
    
      • Clear on logout. Delete caches and IndexedDB that hold a user's data, and unsubscribe their push subscription.
        • 
    
      • Do not cache responses to authenticated requests unless you key them per user and clear them on logout.
        • 
    
      • Treat push payloads as untrusted when choosing the URL to open: only open paths on your own origin, as the task app's notificationclick does by resolving against self.location.origin.
        •

      9. Getting into the stores
      
  
        
    
      • Google Play: a Trusted Web Activity wraps your PWA in a thin Android app with no browser bar. Bubblewrap or PWABuilder generates it. You prove you own the site with a Digital Asset Links file.
        • 
    
      • Microsoft Store: PWABuilder packages the PWA directly.
        • 
    
      • Apple App Store: there is no direct route. You need a native wrapper around a web view, and Apple rejects apps that are only a repackaged website, so it must add something native.
        • 
  
      

  
      10. iPhone limits to design around
      
  
        
    
      • No install prompt API. Installing is always Share, then Add to Home Screen.
        • 
    
      • No Background Sync or Periodic Background Sync. Sync when the app is opened or returns to the front.
        • 
    
      • Push only for Home Screen apps, and only after a tap-triggered permission request.
        • 
    
      • A Home Screen app has its own storage, separate from Safari. A user signed in on the website is not signed in inside the installed app.
        • 
    
      • Every browser on iPhone uses WebKit (outside the EU's alternative-engine rules), so a WebKit limit applies to Chrome and Firefox there too.

        • 
    
      • The app works with the service worker unregistered (first visit, private windows).
        •
