Power BI in 4 weeks

Clean data with Power Query, connect it in a model, calculate with DAX, then design a dashboard people can read in five seconds. Weeks 5 to 8 take the same four skills to an advanced level. Each week ends with a mini-project and a 3-question quiz.

How Power BI works, in one picture

Power BI is four jobs done in order. Raw files go in on the left. A report other people can use comes out on the right. Each week of this plan covers one job.

Before day 1

  • Install Power BI Desktop. It is free, from the Microsoft Store or the Microsoft download page.
  • You are on a Mac, and Power BI Desktop runs on Windows only. Use a Windows virtual machine (Parallels or similar), a cloud Windows PC, or a spare Windows laptop. The Power BI website alone is not enough for weeks 1 to 3.
  • No account is needed to build. You need a work or school account only when you publish and share, which is week 8.

Week 1: Power Query, the cleaning room

Goal turn a messy file into a tidy tableTime 10 hoursYou finish with a clean Orders query that refreshes with one click

Power Query is a recorder. Every click you make to clean the data is saved as a step. When a new file arrives next month, Power BI replays the steps for you. You never edit the source file by hand.

QueryOne recipe that produces one table.Like a saved macro, but readable.
Applied StepsThe list on the right. Each row is one change. You can click any step to see the data at that point, rename it, or delete it.
Data typesText, whole number, decimal, date. Wrong types cause wrong sums and broken date charts. Set them on purpose.
UnpivotTurns month columns (Jan, Feb, Mar) into rows. Charts and slicers need one column per kind of thing.
Merge and AppendMerge adds columns from another table by a matching key. Append stacks rows of tables with the same columns.Merge is a join. Append is a union.
Close & ApplyLoads the cleaned result into the model. Until you press it, the report still has the old data.

Week 2: Data modeling, the wiring

Goal connect tables so one slicer filters everythingTime 10 hoursYou finish with a star schema of Orders, Products, Stores and Date

A model is a set of tables joined by relationships. Instead of one giant sheet with everything repeated, you keep events in one table and descriptions in small lookup tables. Power BI then knows that choosing Tea in the Products table should filter the matching orders.

Fact tableThings that happened. One row per order, payment or visit. Long, mostly numbers and keys.Here: Orders.
Dimension tableThings you describe and filter by. One row per product, store or day. Short, mostly text.Here: Products, Stores, Date.
RelationshipA line between a key column in two tables. Almost always one-to-many: one product, many orders.
Filter directionFilters flow from the one side to the many side. A product filter reaches orders. An order filter does not reach products.
Date tableOne row per calendar day with year, month and quarter columns. Needed for month sorting and for year-to-date measures in week 3.
Star schemaOne fact in the middle, dimensions around it. Simple to read, fast, and the shape DAX expects.

Why not one flat table?

One flat tableStar schema
Category spellingRepeated on every order row. One typo creates a new category.Stored once per product.
Product with no sales yetCannot appear at all.Appears with a blank total.
File size and speedGrows with every repeated text value.Small. Text lives in short tables.
DAXMeasures need workarounds.Standard patterns work as written.

Week 3: DAX, the calculator

Goal write measures that stay correct under any filterTime 12 hoursYou finish with ten measures, from Total Sales to month-over-month growth

DAX looks like Excel formulas, but it works on whole columns and tables, never on a cell like B2. One idea explains most of it: a measure has no fixed answer. It is recalculated for every cell of every visual, using only the rows that survive the current filters. Those surviving rows are the filter context.

MeasureA formula calculated when a visual asks for it. Changes with slicers. Use for anything you total, average or divide.
Calculated columnA formula calculated once per row at refresh and stored. Use for values you slice or group by, such as a price band.
Row contextWorking through a table one row at a time. Calculated columns and the X functions (SUMX, AVERAGEX) have it.
CALCULATERuns a measure under changed filters. Add one, replace one, or remove one. It is the most used function in DAX.
Time intelligenceReady-made date shifts: TOTALYTD, DATEADD, SAMEPERIODLASTYEAR. They need the marked Date table from week 2.
VariablesVAR stores a step, RETURN gives the result. Easier to read and to debug.

Measure or calculated column?

MeasureCalculated column
CalculatedWhen a visual needs itOnce, at refresh
Stored in the fileNoYes, one value per row
Reacts to slicersYesNo
Can go on a slicer or axisNoYes
ExampleMargin % = DIVIDE([Profit], [Total Sales])Price Band = IF(Products[price] >= 400, "Premium", "Standard")

Rule of thumb: if the answer is a number shown in a card, table or chart, write a measure. Reach for a column only when you need to filter or group by the result.

The ten measures to learn, in order

Total Sales   = SUMX ( Orders, Orders[qty] * RELATED ( Products[price] ) )
Orders Count  = COUNTROWS ( Orders )
Avg Order     = DIVIDE ( [Total Sales], [Orders Count] )
Total Cost    = SUMX ( Orders, Orders[qty] * RELATED ( Products[unit_cost] ) )
Profit        = [Total Sales] - [Total Cost]
Margin %      = DIVIDE ( [Profit], [Total Sales] )
Tea Sales     = CALCULATE ( [Total Sales], Products[category] = "Tea" )
% of Regions  = DIVIDE ( [Total Sales],
                    CALCULATE ( [Total Sales], REMOVEFILTERS ( Stores[region] ) ) )
Sales YTD     = TOTALYTD ( [Total Sales], 'Date'[Date] )
Sales MoM %   =
    VAR Prev = CALCULATE ( [Total Sales], DATEADD ( 'Date'[Date], -1, MONTH ) )
    RETURN DIVIDE ( [Total Sales] - Prev, Prev )

Mistakes beginners make this week

  • Averaging a percentage column. Divide the totals in a measure and the result is right at every level.
  • Using / where the bottom can be zero. DIVIDE returns blank and avoids the error.
  • Writing SUM(Orders[qty]) * SUM(Products[price]). That multiplies two totals. Use SUMX to multiply row by row.

Week 5: Advanced Power Query, built to scale

Goal queries that handle many files and large tablesTime 10 hoursYou finish with a folder-driven Orders query with a parameter and a reusable function

Week 1 cleaned one file by hand. Real work has a new file every month and tables with millions of rows. This week you make the same cleaning steps reusable, and you learn why some queries refresh in seconds while others take an hour.

ParameterA named value, such as a folder path or a region, that queries read. Change it once and every query follows.Home, Manage Parameters.
Custom functionA query that takes an input and returns a result. Write a cleaning rule once and call it on any column or file.
Combine files from a folderPoint at a folder. Power BI builds the steps on one sample file and runs them on every file, then stacks the results.
Query foldingWith a database source, Power Query turns your steps into one SQL query so the database does the work. A step it cannot translate runs on your PC, and so does everything after it.
try ... otherwiseCatches a conversion error in one cell and returns a fallback, so one bad value does not fail the whole refresh.
Incremental refreshReload only recent rows, such as the last 7 days, and keep older data as it is. Needs two date/time parameters named exactly RangeStart and RangeEnd.

How a folder of files becomes one table

Query folding simulator

Four patterns to type once

// 1. A parameter used in a filter (RegionParam is a text parameter)
= Table.SelectRows(Orders, each [region] = RegionParam)

// 2. A custom function: New Source, Blank Query, name it fxCleanAmount
(amountText as nullable text) as nullable number =>
    if amountText = null or amountText = "" then null
    else Number.FromText(Text.Replace(amountText, "Rs ", ""), "en-IN")

// 3. A safe conversion: bad cells become null, good cells convert
= Table.AddColumn(Source, "amount_num",
    each try Number.FromText([amount], "en-IN") otherwise null, type nullable number)

// 4. The incremental refresh filter (the column must be date/time)
= Table.SelectRows(Source, each [order_datetime] >= RangeStart and [order_datetime] < RangeEnd)

Pattern 4 uses >= on one side and < on the other so a row on the boundary is never loaded twice.

Week 6: Advanced modeling, the hard cases

Goal handle two dates, many-to-many, big data and securityTime 11 hoursYou finish with a model with a delivery date, three security roles and a clear storage choice

A star schema covers most reports. Four situations need more: a fact with two dates, two things that relate many-to-many, data too large or too fresh to copy, and people who must see only their own rows.

Role-playing dimensionOne Date table used for two purposes, such as order date and delivery date. Only one relationship can be active. The other is switched on inside a measure with USERELATIONSHIP.
Bridge tableA small table that sits between two tables that relate many-to-many, with one row per valid pair.A product can be in many promotions. A promotion covers many products.
Storage modeImport copies data into the model. DirectQuery leaves it in the source and asks on every click. Dual does either, as needed. Direct Lake reads Fabric lake files directly.
Composite modelA model that mixes modes, such as an imported Products table with a DirectQuery fact.
Row-level securityA DAX filter attached to a role. A member of the role sees only the rows where the filter is true, in every visual and every total.Modeling, Manage roles.
Dynamic securityOne role for everyone. The filter compares a column with the signed-in user: Stores[manager_email] = USERPRINCIPALNAME().

Mistakes people make this week

  • Loading a second copy of the Date table for every date column when one inactive relationship would do. A second Date table is fine when readers need to slice by both dates at once.
  • Choosing DirectQuery because it sounds modern. It moves the performance problem to the database.
  • Building security with hidden pages or slicers. Anyone can undo those. Only roles are security.

A documented limit: Microsoft's reference says USERELATIONSHIP can raise an error when row-level security is defined on the tables in that relationship. In this project the roles filter Stores, and the inactive relationship joins Orders and Date. If you do hit the error in your own model, give the second date its own Date table instead.

Week 7: Advanced DAX, thinking in tables

Goal rank, accumulate and compare against any totalTime 12 hoursYou finish with ranking, running totals, share measures and a calculation group

Week 3 measures returned one number from the current filters. Advanced DAX builds a small table in memory first, such as one row per product, and then works on that table. Three ideas carry most of it: context transition, the ALL family, and iterating over a list of values.

Context transition

ALL and REMOVEFILTERSIgnore filters on a column or table. The denominator becomes the grand total.
ALLSELECTEDIgnore the filter from the visual's own rows, but keep slicers. The denominator becomes the visible total.
ALLEXCEPTRemove every filter on a table except the columns you name. Used for a share within a group.
VALUESThe distinct values of a column that are visible right now. Iterate over it to work per customer, per month or per product.
RANKX and TOPNRANKX gives a position. TOPN returns the best rows as a table you can filter by.
Calculation groupA calculation such as YTD written once with SELECTEDMEASURE() and applied to any measure.Model view, Calculation group.

Share of what? ALL against ALLSELECTED

Ranking and running totals

Calculation groups

// Calculation group "Time view", three calculation items
Current = SELECTEDMEASURE ()
YTD     = CALCULATE ( SELECTEDMEASURE (), DATESYTD ( 'Date'[Date] ) )
vs PM % =
    VAR Prev = CALCULATE ( SELECTEDMEASURE (), DATEADD ( 'Date'[Date], -1, MONTH ) )
    RETURN DIVIDE ( SELECTEDMEASURE () - Prev, Prev )

Put the Time view column on a matrix's columns and any measure in values. Total Sales, Profit and Orders Count all get Current, YTD and vs PM % without nine separate measures. Power BI asks you to switch on "discourage implicit measures" first, because calculation items only apply to measures you wrote.

Making DAX fast

  • Store a value in a VAR when you use it twice. It is calculated once.
  • Filter a column, not a whole table: Products[category] = "Tea" beats FILTER ( Products, ... ).
  • Find the slow visual with View, Performance analyzer, then copy its query into DAX query view to test changes.
  • Fix the model before the measure. A missing relationship or a wide flat table costs more than any formula.

Week 8: Publish, secure and maintain

Goal a report other people can rely onTime 11 hoursYou finish with a published report with scheduled refresh, tested security and a safe way to change it

A report on your laptop helps nobody. This week moves it to the Power BI service, keeps its data fresh, controls who sees what, and sets up a way to change it without breaking what people use every morning. You need a work or school account for this week.

WorkspaceA shared folder in the service for the people who build. Roles: Admin, Member, Contributor, Viewer.
AppA packaged, read-only view of a workspace for the people who read. One link, clean navigation.
Scheduled refreshThe service reloads the data on a timetable using saved credentials, and emails you when it fails.
Security in the serviceOpen the semantic model's menu, choose Security, add people to roles, then Test as role. Roles apply to Viewers only. Admins, Members and Contributors see everything.
Deployment pipelineDevelopment, Test and Production stages, each its own workspace. You change Development and promote when it is right.
Power BI projectFile, Save as, Power BI project. The report and model become text files you can keep in Git and compare line by line.
