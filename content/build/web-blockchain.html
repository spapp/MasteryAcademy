A course in three parts · basic to advanced

Blockchain from Zero

A blockchain is a record book that many strangers keep together, where every page is glued to the one before it. This course builds that idea up piece by piece until you can read how a decentralized app works.

The picture to keep in your head

Think of a housing society's maintenance register. Normally the secretary keeps it, and everyone trusts the secretary. Now imagine every flat owner holds an identical copy. A new entry counts only when most owners agree it is correct, and each page carries a stamp calculated from the previous page. Nobody can quietly change an old entry, because their copy would stop matching everyone else's.

Part 1

Core mechanics

Four ingredients make a blockchain: a shared ledger, hashing, digital signatures, and a rule for agreeing. Learn them in that order.

Basic

A ledger everybody holds

A ledger is a list of who paid whom. Your bank keeps one. When you send money by UPI, no coins move. The bank lowers one number and raises another. You trust the bank to do that honestly and to never let you spend the same rupee twice.

Spending the same digital money twice is called the double-spend problem. A file can be copied, so digital money needs someone to keep score. Before 2008 that someone was always a central party. Bitcoin's whitepaper, published on 31 October 2008, showed how a group of strangers could keep the score together instead.

Bank ledgerBlockchain ledger
Who holds the recordOne companyThousands of computers, called nodes
Who approves an entryThe bankThe network, by a fixed rule
Can old entries changeYes, by the bankPractically no. Corrections are new entries
Who can read itThe bank and youAnyone, on a public chain
What you give upControlSpeed, cost, and the option to undo mistakes

That last row matters. A blockchain is slower and more expensive than a database on purpose. You pay that price only to remove the need for a trusted scorekeeper.

Basic

Hashing: a fingerprint for data

A hash function takes any input, a word or a whole film, and returns a short fixed-length code. Bitcoin uses one called SHA-256, which always returns 64 hexadecimal characters.

Analogy

A fingerprint. It identifies a person, it is always the same size, and you cannot rebuild the person from it.

  • Same input, same hash. Every time, on every computer.
  • One way. You cannot work backwards from the hash to the input.
  • Tiny change, completely different hash. This is called the avalanche effect.
  • No two inputs you can find share a hash. In theory collisions exist. In practice nobody can find one.
Try it · real SHA-256 running in this page

Blockchains use hashes for three jobs: to label a block, to link each block to the previous one, and to make mining a measurable amount of work.

Basic

Blocks, and why they form a chain

A block is one page of the ledger. It holds a batch of transactions and a small header. The header includes the hash of the previous block. That single field is what turns separate pages into a chain.

Try it · break the chain

This is a four-block chain. A block is valid when its hash starts with 00. Edit the data in block 1 and see what happens to the blocks after it. Then repair it one block at a time.

You just did what an attacker has to do. To rewrite one old entry, they must redo the work for that block and for every block after it, and they must do it faster than the rest of the world is adding new blocks. On a real network that is the whole defence.

Intermediate

Merkle trees: one hash for a thousand transactions

A block can hold thousands of transactions. Instead of hashing them as one big lump, the block hashes them in pairs, then hashes those results in pairs, until one hash is left. That final hash is the Merkle root, and it sits in the block header.

Analogy

A knockout tournament bracket. To confirm one player reached the final you only need the matches on their path, not every match played.

Basic

Keys and signatures: proving it is you

There are no usernames or passwords on a blockchain. You have a key pair. The private key is a very large secret number. The public key is calculated from it, and your address is a short form of the public key.

Analogy

Your address is a letterbox with a slot. Anyone can drop money in. Only the person with the key to the box can take money out. A signature is proof that you hold the key, shown without revealing the key.

The hard truth about keys. Whoever holds the private key controls the funds. There is no "forgot password" link and no helpline. A wallet's 12 or 24 word seed phrase is the private key in readable form. Lose it and the money is gone. Share it and the money is someone else's.

Basic

The life of one transaction

The network is a set of computers called nodes. Each node holds a copy of the chain and passes messages to its neighbours, the way news spreads in a WhatsApp group. There is no central server.

Every node checks each transaction itself: is the signature valid, and does the sender have the money. A node does not take anyone's word for it. "Don't trust, verify" is the working rule.

Intermediate

Consensus: agreeing without a boss

Thousands of nodes each see transactions in a slightly different order. They need a rule for deciding who writes the next page. The rule must also make cheating expensive, because anyone can join and create a million fake identities for free.

Proof of Work

Used by Bitcoin. Computers called miners race to find a number, the nonce, that makes the block's hash start with a required number of zeros. The only method is guessing. The first to find one publishes the block and earns the reward.

Analogy

A Sudoku. Solving it takes real effort. Checking a finished one takes seconds. The effort is the miner's cost, and that cost is what makes rewriting history expensive.

Bitcoin adjusts the difficulty every 2,016 blocks, about two weeks, so that a block arrives roughly every 10 minutes no matter how many miners join.

Proof of Stake

Used by Ethereum since 15 September 2022. There is no puzzle. Participants called validators lock up coins as a deposit. The protocol picks one at random to propose each block, and the others vote on it. A validator who cheats loses part of the deposit. That penalty is called slashing.

Analogy

A security deposit on a rented flat. You behave because you have money on the table, not because you burned electricity.

Voting among known members

Private company networks know exactly who the members are, so they can simply vote. These methods go by names like PBFT, Raft and Proof of Authority. They are fast and final, and they work only because membership is controlled.

Advanced

Forks, finality and the 51% attack

Sometimes two valid blocks appear at nearly the same moment. For a short while the network has two versions of the last page. This is a fork. Nodes follow the branch with the most accumulated work, and the next block usually settles it. Transactions in the losing block go back to the mempool.

This is why a payment gets safer with every block added on top of it. Each new block is one more block an attacker would have to redo.

A 51% attack is when one party controls most of the mining power or stake. They could then build a private branch faster than everyone else and replace recent history, which lets them reverse their own payments. They still cannot forge your signature, spend your coins, or create coins outside the rules. On large networks the cost of gathering that majority is the deterrent. Small Proof of Work chains have been attacked this way.

Two more terms worth knowing. A soft fork tightens the rules in a way old software still accepts. A hard fork changes the rules so that old software rejects the new blocks, and if some people refuse to upgrade the chain splits into two. Ethereum and Ethereum Classic split this way in 2016.

Part 2

Cryptocurrencies vs smart contracts

Bitcoin put a ledger of money on a blockchain. Ethereum put programs on one. That is the whole difference, and everything else follows from it.

Basic

Bitcoin: a blockchain that does one job

Bitcoin's first block was mined on 3 January 2009. It does one thing: record who owns how many bitcoin. New coins enter only as the reward to whoever produces a block, and that reward halves every 210,000 blocks, about every four years. The total can never pass 21 million.

How Bitcoin tracks money: unspent notes

Bitcoin has no account balances. It tracks individual chunks of coin called UTXOs, unspent transaction outputs. Your "balance" is the total of the chunks your key can unlock.

Analogy

Cash in a wallet. To pay ₹600 you hand over a ₹500 and a ₹200 note and get ₹100 back as change. You cannot tear a note. Bitcoin works the same way: whole chunks go in, new chunks come out.

Basic

Smart contracts: programs that live on the chain

Ethereum went live on 30 July 2015 with a different idea. If a network can agree on a list of payments, it can also agree on the result of running a program. A smart contract is a small program stored on the chain. It has its own address, it can hold money, and it runs exactly as written when someone calls it.

Analogy

A vending machine. Put in the right money, press a button, get the item. No shopkeeper decides whether to serve you. The rules are built into the machine and are the same for everyone.

Here is a real one, written in Solidity. It holds a buyer's payment and releases it to the seller only when the buyer confirms delivery.

// SPDX-License-Identifier: MIT
pragma solidity ^0.8.20;

contract Escrow {
    address public buyer;
    address public seller;
    bool public paidOut;

    // Runs once, when the buyer deploys it and sends the money in.
    constructor(address _seller) payable {
        buyer = msg.sender;
        seller = _seller;
    }

    function confirmDelivery() external {
        require(msg.sender == buyer, "Only the buyer can confirm");
        require(!paidOut, "Already paid out");
        paidOut = true;                              // record first
        (bool ok, ) = seller.call{value: address(this).balance}("");
        require(ok, "Payment failed");               // then pay
    }
}
  • msg.sender is whoever signed the transaction. That is the only login there is.
  • payable means the function can receive coins.
  • require stops everything and undoes all changes if the condition is false.
  • Once deployed, the code cannot be edited. Anyone can read it and anyone can call it.

Intermediate

Gas and the EVM

Every Ethereum node runs every contract call to check the result. The software that runs them is the Ethereum Virtual Machine, or EVM. Because everyone's computer does the work, a program that looped forever would freeze the whole network. Gas prevents that.

Analogy

A taxi meter. Every step of computation adds to the meter. You state the most you are willing to pay before the ride starts. If the meter hits that limit, the ride stops, the work is undone, and you still pay for the distance covered.

  • Each operation has a fixed gas cost. A plain transfer of ETH costs 21,000 gas. Writing to storage costs far more than arithmetic.
  • Fee = gas used × price per unit of gas. The price is quoted in gwei, and one gwei is a billionth of one ETH.
  • Since 2021 the price has two parts. A base fee set by the protocol is destroyed. A tip goes to the validator.

A worked example. A transfer uses 21,000 gas. At a price of 10 gwei the fee is 210,000 gwei, which is 0.00021 ETH. The same transfer at 100 gwei on a busy day costs ten times as much, and nothing about the transfer has changed.

For a developer this changes how you write code. Storage is the expensive resource, so you store as little as possible on chain and emit events, which are cheap log entries, for anything the app only needs to read later.

Intermediate

Tokens: assets made by contracts

A coin such as ETH or BTC is built into its chain. A token is just a smart contract that keeps a table of who owns how much. Standards make every token contract expose the same functions, so any wallet or exchange can handle a token it has never seen.

StandardWhat it representsEveryday comparisonExamples
ERC-20Interchangeable units. Any one is as good as anotherCurrency notes, loyalty pointsUSDC, DAI, LINK
ERC-721One-of-a-kind items, each with its own ID. These are NFTsA property deed, a numbered ticketDigital art, event tickets, name registrations
ERC-1155Both kinds in one contractA game inventory: 500 gold coins and one unique swordGame items

A stablecoin is a token designed to stay at the value of a currency, usually one US dollar. Some are backed by cash and bonds held by a company. Others are backed by crypto locked in contracts. They are the most used tokens because they let people move dollars at blockchain speed.

An NFT proves who holds a token ID. The picture or file usually lives somewhere else, and the token only points to it. Owning the token is not automatically owning the copyright.

Intermediate

Oracles: how a contract learns about the outside world

A contract can read only what is already on its chain. It cannot call a weather API or check a share price. If it could, different nodes would get different answers at different moments and could never agree on the result.

An oracle is a service that writes outside data onto the chain so contracts can read it. Chainlink is the best known. Good oracles collect the same data from many independent sources and publish the combined answer, so that no single reporter can lie.

Analogy

A referee's scoresheet. The betting slip, which is the contract, pays out based on the official score. It does not watch the match. The slip is only as honest as the scorer, so the oracle is often the weakest point of an otherwise solid design.

Advanced

When contracts fail

Three properties that make contracts useful also make them dangerous. The code is public, it holds real money, and it cannot be patched. A bug is an open vault that anyone can study at leisure.

The best known failure is The DAO in June 2016. An attacker drained about 3.6 million ETH through a reentrancy bug. The contract sent money before it updated its own records. The attacker's contract received the money and, inside that same call, asked for a withdrawal again. The records still showed the old balance, so the contract paid again, and again.

Look back at the escrow code. It sets paidOut = true before it sends the money. That ordering, check first, update your records second, talk to outsiders last, is the standard defence. It is known as checks-effects-interactions.

  • Access control mistakes. A function that should be owner-only is left open.
  • Oracle manipulation. The contract trusts a price that an attacker can move for one transaction.
  • Front-running. Pending transactions are public in the mempool, so others can see yours and pay to get ahead of it.
  • Upgrade keys. Many contracts sit behind a proxy that lets the team swap the code. That fixes bugs, and it also means you are trusting whoever holds the upgrade key.

Serious projects respond with independent audits, automated testing, bug bounties, and limits on how much money a new contract may hold.

Deep dive

Smart contracts, properly

Part 2 showed what a contract is. This section shows how one is written, deployed, attacked and tested. It assumes you have written code in some language before.

Intermediate

From source code to a live contract

Ethereum has two kinds of account. A normal account is controlled by a private key. A contract account is controlled by code and has no key at all. It can only react when someone calls it.

Analogy for app developers

Bytecode is the compiled binary. The ABI is the header file or API spec. Deploying is a release that can never be replaced, to a server everyone in the world shares.

After that there are two ways to use the contract, and the difference matters every day:

Call (read)Transaction (write)
Changes stateNoYes
Costs gasNo, when made from outside the chainYes, always
Needs a signatureNoYes
SpeedImmediate. One node answersWaits for a block
ReturnsThe function's return valueA receipt with status, gas used and events. Not the return value

That last cell surprises most newcomers. An app cannot read the return value of a write. It reads the events the transaction emitted, or makes a follow-up read call.

Intermediate

Anatomy of a contract

This crowdfunding contract uses every building block you will meet. People pledge ETH before a deadline. If the goal is reached the owner collects. If not, each backer takes their own money back.

// SPDX-License-Identifier: MIT
pragma solidity ^0.8.20;

contract Crowdfund {
    // 1. STATE. Lives on chain forever. The costly part.
    address public immutable owner;
    uint256 public immutable goal;
    uint256 public immutable deadline;
    uint256 public raised;
    mapping(address => uint256) public pledged;

    // 2. EVENTS. Cheap log entries that apps listen for.
    event Pledged(address indexed backer, uint256 amount);
    event Refunded(address indexed backer, uint256 amount);

    // 3. ERRORS. Named reasons for a revert.
    error NotOwner();
    error TooLate();
    error TooEarly();
    error GoalNotMet();
    error GoalMet();

    // 4. MODIFIER. A reusable guard placed in front of a function.
    modifier onlyOwner() {
        if (msg.sender != owner) revert NotOwner();
        _;
    }

    // 5. CONSTRUCTOR. Runs once, at deployment.
    constructor(uint256 _goal, uint256 _days) {
        owner = msg.sender;
        goal = _goal;
        deadline = block.timestamp + _days * 1 days;
    }

    // 6. FUNCTIONS.
    function pledge() external payable {
        if (block.timestamp >= deadline) revert TooLate();
        pledged[msg.sender] += msg.value;
        raised += msg.value;
        emit Pledged(msg.sender, msg.value);
    }

    function withdraw() external onlyOwner {
        if (raised < goal) revert GoalNotMet();
        (bool ok, ) = owner.call{value: address(this).balance}("");
        require(ok, "Transfer failed");
    }

    function refund() external {
        if (block.timestamp < deadline) revert TooEarly();
        if (raised >= goal) revert GoalMet();
        uint256 amount = pledged[msg.sender];
        pledged[msg.sender] = 0;                         // record first
        (bool ok, ) = msg.sender.call{value: amount}("");
        require(ok, "Refund failed");                    // then pay
        emit Refunded(msg.sender, amount);
    }

    function daysLeft() external view returns (uint256) {
        if (block.timestamp >= deadline) return 0;
        return (deadline - block.timestamp) / 1 days;
    }
}
State variables
The contract's database. public makes the compiler generate a free getter. immutable values are fixed at deployment and cost almost nothing to read.
mapping
A key-value table. Every possible key exists and starts at zero, so you cannot list its keys or ask how many there are.
Events
Written to the transaction log, not to state. Contracts cannot read them back. Apps and indexers can, and indexed fields are searchable.
Custom errors
Cheaper than text messages, and an app can decode them by name to show a proper message.
Modifier
The _; marks where the function body runs. Think of it as a route guard or middleware.
msg.sender
The account that made this call. It can be a person or another contract.
msg.value
The ETH sent with the call, in wei. Only payable functions accept it.
block.timestamp
The block's time in seconds. Fine for deadlines measured in days. The block producer can nudge it by a few seconds.

Notice what a revert does. If any check fails, every change made during that transaction is undone, as if it never ran. Only the gas is spent. This all-or-nothing behaviour is called atomicity, and it is the property that makes contracts safe to compose.

Two more labels describe what a function may touch. A view function reads state and changes nothing. A pure function does not even read state. Both are free to call from an app.

Where data lives

  • storage is the contract's permanent data on chain. Reading is moderately costly and writing is very costly.
  • memory is scratch space that exists only during the call. Cheap.
  • calldata is the read-only input that came with the transaction. Cheapest. Use it for array and string parameters of external functions.

Solidity is not the only option. Vyper is a stricter, Python-like language for the EVM. Solana programs are written in Rust. Aptos and Sui use Move. Hyperledger Fabric chaincode is written in Go, Java or JavaScript. The ideas in this section carry across all of them.

Advanced

What actually costs gas

Gas prices reflect the burden an operation puts on every node. Arithmetic is forgotten the moment it finishes. A storage write must be kept by every node forever. The price list follows from that.

OperationGasIn plain terms
Add two numbers3Practically free
Read a storage slot, first time in a transaction2,100Later reads of the same slot cost 100
Change an existing storage valueabout 5,000
Write to a storage slot that was zeroabout 22,100The single most expensive common operation
Emit an event with one indexed field and 32 bytes of dataabout 1,400Roughly fifteen times cheaper than a new storage slot
Base cost of any transaction21,000Paid before your code runs
Deploy a contract32,000 + 200 per byteA mid-sized contract costs over a million gas

These numbers come from the protocol's fee schedule and have been changed by upgrades before, so treat them as a guide to proportions.

The habits that follow:

  • Store only what the contract needs to make decisions. Put history in events.
  • Never loop over a list that users can grow without limit. One day the loop will not fit in a block and the function will be stuck forever.
  • Read a storage value into a local variable once instead of reading it inside a loop.
  • Store a hash of a large document on chain and keep the document elsewhere.
  • Pack small values together. Several variables that fit inside 32 bytes share one slot.
Intermediate

Build a token from scratch

An ERC-20 token is two tables and three functions. This is a complete, working one.

contract SimpleToken {
    string public name = "Society Points";
    string public symbol = "SOC";
    uint8 public decimals = 18;
    uint256 public totalSupply;

    mapping(address => uint256) public balanceOf;                       // table 1
    mapping(address => mapping(address => uint256)) public allowance;   // table 2

    event Transfer(address indexed from, address indexed to, uint256 value);
    event Approval(address indexed owner, address indexed spender, uint256 value);

    constructor(uint256 initialSupply) {
        totalSupply = initialSupply;
        balanceOf[msg.sender] = initialSupply;
        emit Transfer(address(0), msg.sender, initialSupply);
    }

    function transfer(address to, uint256 value) external returns (bool) {
        balanceOf[msg.sender] -= value;      // reverts if the balance is too low
        balanceOf[to] += value;
        emit Transfer(msg.sender, to, value);
        return true;
    }

    function approve(address spender, uint256 value) external returns (bool) {
        allowance[msg.sender][spender] = value;
        emit Approval(msg.sender, spender, value);
        return true;
    }

    function transferFrom(address from, address to, uint256 value) external returns (bool) {
        allowance[from][msg.sender] -= value;   // reverts if not allowed that much
        balanceOf[from] -= value;
        balanceOf[to] += value;
        emit Transfer(from, to, value);
        return true;
    }
}

"Sending" a token moves nothing. It lowers one number in balanceOf and raises another. Your tokens are a row in that contract's table, which is why a wallet must know the contract's address before it can show them.

Why approve exists

A contract cannot pull tokens out of your account by itself, and it cannot tell that you sent it tokens with a plain transfer. So paying a contract takes two steps. You first allow it to take a set amount. Then you call it, and it collects.

Analogy

A UPI AutoPay mandate. You approve a merchant to debit up to a limit. The merchant then pulls the payment when it is due. You never hand over your PIN.

Advanced

Design patterns you will see everywhere

Checks, effects, interactions
Inside every function: validate first, update your own state second, call other contracts or send money last. This ordering alone prevents most reentrancy bugs.
Pull over push
Do not loop through users sending them money. Record what each is owed and let each one withdraw. One user whose address rejects payments then cannot block everyone else. The crowdfund's refund works this way.
Ownable and roles
A stored owner address plus an onlyOwner guard. Larger systems use named roles such as minter and pauser. In production the owner should be a multi-signature wallet, never one person's key.
Reentrancy guard
A lock flag set at the start of a function and cleared at the end. A second entry while the lock is set reverts. Used in addition to correct ordering.
Pausable
An emergency stop that the owner can trigger to freeze sensitive functions while a problem is investigated.
Timelock
Admin actions are announced on chain and can run only after a delay, such as 48 hours. Users get time to leave if they disagree.
Factory
A contract that deploys other contracts, so each user or market gets its own instance from one audited template.

There is a tension in that list. Pause switches, owners and upgrades make a system safer against bugs, and they also put trust back into a small group. When you assess any project, find out who holds those keys.

Advanced

How "immutable" contracts get upgraded

Code at an address cannot change. So teams split a contract in two. A small proxy holds the data and never changes. It forwards every call to a separate logic contract. To upgrade, an admin points the proxy at a new logic contract.

The mechanism is an instruction called delegatecall. It runs another contract's code against the caller's own storage.

Analogy

A shop that keeps its own stock room and cash register but hires a manager from an agency. Replace the manager and the stock is still there. Hire a bad manager and they have full access to the register.

  • The new logic must keep the old storage layout. Reordering variables makes the new code read the wrong slots and corrupts the data.
  • Logic contracts cannot use a constructor for setup. They use an initialize function that must be callable only once. Forgetting that guard has led to real takeovers.
  • Whoever controls the upgrade can replace the code with anything. Good setups put that power behind a multi-signature wallet and a timelock.
Advanced

Attack catalogue

Start with the famous one, shown side by side. A bank contract lets users withdraw their deposit.

Vulnerable 
function withdraw() external {
    uint256 amount = balances[msg.sender];
    (bool ok, ) = msg.sender.call{value: amount}("");
    require(ok);
    balances[msg.sender] = 0;   // too late
}
Fixed 
function withdraw() external nonReentrant {
    uint256 amount = balances[msg.sender];
    balances[msg.sender] = 0;   // first
    (bool ok, ) = msg.sender.call{value: amount}("");
    require(ok);
}

Sending ETH to a contract runs that contract's receive function. The attacker writes one that calls withdraw again before the first call has finished:

receive() external payable {
    if (address(bank).balance >= 1 ether) bank.withdraw();
}

A flash loan deserves one more sentence. It is a loan with no collateral that must be repaid within the same transaction, or the whole transaction reverts. It is only possible because of atomicity. It means an attacker never needs to be rich, so "nobody has that much money" is never a valid security assumption.

Advanced

Testing and shipping

You cannot hotfix a contract, so testing carries far more weight than in app development. The standard tools are Remix for experiments in the browser, and Foundry or Hardhat for real projects. Both run a private chain on your machine where you control the clock and every account.

A Foundry test file for the crowdfund contract. Tests are themselves written in Solidity.

import {Test} from "forge-std/Test.sol";
import {Crowdfund} from "../src/Crowdfund.sol";

contract CrowdfundTest is Test {
    Crowdfund fund;
    address asha = makeAddr("asha");

    function setUp() public {
        fund = new Crowdfund(10 ether, 30);   // goal 10 ETH, 30 days
        vm.deal(asha, 5 ether);               // give Asha test money
    }

    function test_PledgeIsRecorded() public {
        vm.prank(asha);                       // next call comes from Asha
        fund.pledge{value: 2 ether}();
        assertEq(fund.pledged(asha), 2 ether);
        assertEq(fund.raised(), 2 ether);
    }

    function test_RefundBlockedBeforeDeadline() public {
        vm.prank(asha);
        fund.pledge{value: 2 ether}();
        vm.prank(asha);
        vm.expectRevert(Crowdfund.TooEarly.selector);
        fund.refund();
    }

    function test_RefundAfterFailedCampaign() public {
        vm.prank(asha);
        fund.pledge{value: 2 ether}();
        vm.warp(block.timestamp + 31 days);   // jump the clock forward
        vm.prank(asha);
        fund.refund();
        assertEq(asha.balance, 5 ether);
    }
}

Every contract in this course, and this test file, was compiled with Solidity 0.8.28 and run on a local chain. The reentrancy attack was run too: against the vulnerable bank the attacker left with 11 ETH, and against the fixed one the attack reverted. They are teaching samples and have not been audited, so do not put real money in them.

The layers of checking, cheapest first

  1. Unit tests. Every function, every revert path, called by the right and the wrong account.
  2. Fuzz tests. The tool calls your function with thousands of random inputs and looks for one that breaks an assertion.
  3. Invariant tests. You state a rule that must always hold, such as "the sum of all balances equals total supply", and the tool tries random sequences of calls to break it.
  4. Fork tests. Run against a local copy of the real chain, so your contract meets the real tokens and protocols it will depend on.
  5. Static analysis. Tools such as Slither scan the code for known bad patterns.
  6. Testnet deployment. A public rehearsal with valueless coins.
  7. Independent audit and bug bounty. Outside specialists read the code, and a public reward stays open afterwards.

Launch checklist

  • Publish and verify the source on a block explorer so anyone can match it to the deployed bytecode.
  • Move ownership to a multi-signature wallet before any real money arrives.
  • Start with limits on deposits and raise them over time.
  • Have monitoring and a rehearsed pause procedure.
  • Write down who can upgrade, who can pause, and how long the timelock is. Users will ask.

Intermediate

How a decentralized app works

A dApp is a normal web or mobile front end whose back end is a smart contract. If you build apps today, most of the picture is familiar. Three things move.

  • Login is a signature. The app asks the wallet for your address. No password is stored anywhere.
  • Reads are free, writes cost gas. Reading a balance is a plain query to a node. Changing anything is a transaction you sign and pay for.
  • Writes are slow and can fail. The UI must show pending, confirmed and failed states. It is closer to tracking an order than to a normal API response.
  • The app talks to the contract through its ABI. The ABI is a JSON description of the contract's functions, the same role an API spec plays for a REST service. Libraries such as ethers.js, viem and web3.dart turn it into callable methods.
  • Big data stays off chain. Images and documents go to IPFS or ordinary storage. The chain keeps only a hash of the file, which proves it has not been swapped.
  • Lists and search need an indexer. A chain cannot answer "show my last 20 orders" efficiently. A service such as The Graph listens to contract events and builds a queryable database from them.

Custodial and self-custody wallets

A custodial wallet is an exchange account. The company holds the keys, and you get password reset and support, much like a bank. A self-custody wallet such as MetaMask keeps the key on your device. You get full control and full responsibility. Newer smart-contract wallets try to give both, using passkeys, spending limits and recovery through trusted contacts.

Advanced

Scaling and Layer 2

A public chain is slow because every node repeats every computation. Designers talk about a trilemma: decentralization, security and speed, where pushing one tends to cost another. Bitcoin and Ethereum chose the first two. A card network handles thousands of payments a second. Ethereum's base layer handles a few dozen.

The main answer is to do the work elsewhere and use the main chain as the court of record. Such a system is called a Layer 2, and the most common kind is a rollup.

Analogy

A tab at a restaurant. You order many times during the evening and the waiter keeps a running note. Only the final bill goes through the card machine.

Optimistic rollupZK rollup
How Layer 1 knows the batch is honestIt assumes so. Anyone can challenge within a window, usually about 7 daysEach batch carries a mathematical proof that Layer 1 checks
Withdrawal to Layer 1Slow, because of the challenge windowFast, once the proof is accepted
Hard partSomeone must be watching for fraudProducing proofs takes heavy computation
ExamplesArbitrum, Optimism, BasezkSync, Starknet, Linea

A zero-knowledge proof lets you prove a statement is true without revealing the details behind it. The classic picture is proving you are over 18 without showing your date of birth. Rollups use the same maths to prove "these 5,000 transactions were executed correctly" in one small proof.

Ethereum's March 2024 upgrade added a cheaper kind of data space for rollups, called blobs, which cut Layer 2 fees sharply. Other approaches include sidechains, which are separate chains with their own security, and bridges, which move assets between chains. Bridges have been the target of some of the largest thefts in the field, so treat them as the risky part of any design.

Limits you should state honestly in any proposal

  • The chain cannot check the real world. If someone enters "organic" for a non-organic crate, the false record is preserved perfectly. The link between a physical item and its record is the weak spot.
  • Privacy is hard. Data that many parties replicate is hard to keep confidential and harder to delete, which conflicts with privacy laws that grant a right to erasure. The usual design keeps personal data off chain and stores only a hash.
  • Keys must be managed. Companies need hardware security modules, approval flows and recovery plans.
  • Rules differ by country and keep changing, especially for tokens and customer funds.

Intermediate

Step 1 · Connect a wallet

A browser wallet adds an object to the page, window.ethereum. The app sends requests to it. The wallet shows a prompt and the user decides. The app never sees the private key.

Analogy

Paying on a shopping site with UPI. The site sends a request, your UPI app opens, and you approve with your PIN there. The site never learns the PIN.

import { createPublicClient, createWalletClient, custom, http } from 'viem'
import { sepolia } from 'viem/chains'

// Reads go through your node provider. No wallet needed.
const publicClient = createPublicClient({ chain: sepolia, transport: http(RPC_URL) })

// Writes go through the user's wallet.
const walletClient = createWalletClient({ chain: sepolia, transport: custom(window.ethereum) })

// Opens the wallet's "Connect" prompt. Call it from a button tap, never on page load.
const [account] = await walletClient.requestAddresses()

// The user can switch account or network at any time, from inside the wallet.
window.ethereum.on('accountsChanged', (accounts) => { /* reset the session */ })
window.ethereum.on('chainChanged', (chainId) => { /* re-check the network */ })
  • Connecting only shares the address. It gives the app no power to move funds. Each transaction needs its own approval.
  • Check the network. The wallet may be on a different chain from the one your contract is on. Compare chain IDs before every write. Sepolia is 11155111 and Ethereum mainnet is 1.
  • Show the page without a wallet. Reads need only the public client, so a visitor can see the campaign before connecting anything.

Every read is a network request to your provider, and providers bill by request. Batch reads together with a multicall, cache them, and refresh when a new block arrives instead of on a fast timer.

Intermediate

Step 3 · Send a transaction

A write passes through several states, and it can stop at three different points. Your screen needs a design for each one.

Analogy

Tracking a food order: placed, accepted, on the way, delivered. You would not show "delivered" the moment the customer taps Order, and the app must cope with a restaurant that cancels.

import { parseEther, BaseError, ContractFunctionRevertedError } from 'viem'

async function pledge(amountEth) {
  try {
    // 1. Dry run. Catches reverts and missing funds before the wallet opens.
    const { request } = await publicClient.simulateContract({
      account, address: CROWDFUND_ADDRESS, abi,
      functionName: 'pledge', value: parseEther(amountEth),
    })

    // 2. Wallet prompt. Resolves with the hash as soon as the user signs.
    const hash = await walletClient.writeContract(request)
    setState({ status: 'pending', hash })          // save the hash, show an explorer link

    // 3. Wait for the block.
    const receipt = await publicClient.waitForTransactionReceipt({ hash })
    setState({ status: receipt.status === 'success' ? 'done' : 'failed', hash })
  } catch (err) {
    // A custom error from the contract, decoded by name through the ABI.
    const revert = err instanceof BaseError && err.walk(e => e instanceof ContractFunctionRevertedError)
    if (revert?.data?.errorName === 'TooLate') return showMessage('This campaign has ended.')
    if (err.code === 4001 || /rejected/i.test(err.shortMessage ?? '')) return   // user cancelled. Not an error.
    showMessage('Could not send the pledge. Nothing was charged.')
  }
}
Try it · follow one pledge through its states
Pick a case and press the button. Each line shows the state and what the screen should do.

Save the transaction hash as soon as you get it. If the user closes the app while it is pending, you can look up the receipt on the next launch and show the right result.

Step 4 · Events and indexing

The screen needs a list of recent pledges. The contract stores only a total per backer. It has no list, and it could not return one cheaply if it did. The history lives in the Pledged events.

// Live updates while the screen is open.
const unwatch = publicClient.watchContractEvent({
  address: CROWDFUND_ADDRESS, abi, eventName: 'Pledged',
  onLogs: (logs) => logs.forEach(l => addRow(l.args.backer, l.args.amount)),

// Past events, by block range. Fine for small ranges.

  address: CROWDFUND_ADDRESS, abi, eventName: 'Pledged', fromBlock: DEPLOY_BLOCK,

Asking a node for old events works for a small contract. It gets slow over long block ranges, and providers limit how far back one request may go. A real app adds an indexer: a service that follows the chain, stores each event in a normal database, and serves queries.

Analogy

A library catalogue. The books are the truth. The catalogue is built from them so you can search by author in a second, and it can be rebuilt if it is lost.

The indexer runs a little behind the chain. After a successful pledge, add the new row to the list yourself from the receipt, or the user will see their pledge missing for a few seconds.

Advanced

Sign in with a wallet

Many dApps still have a backend, for profiles, notifications or anything too costly to keep on chain. That backend needs to know which address it is talking to. An address typed into a form proves nothing. A signature does.

Analogy

Signing the visitor register at a society gate. The guard writes today's date and a serial number on the line first, so yesterday's signature cannot be reused.

  • The nonce is a random value the server issues once. It stops someone replaying an old signature.
  • The message should state the site's domain, the chain ID and an expiry time, in words the user can read in the wallet. The standard format is called Sign-In with Ethereum, EIP-4361.
  • After that the server issues a normal session token, as in any app.
  • For structured data, such as an order the user signs off chain, use typed data signing, EIP-712. The wallet then shows named fields instead of an unreadable blob.

Rules that make a dApp feel trustworthy

  • Say what the wallet is about to ask before it asks. "You will confirm a pledge of 0.1 ETH" removes the surprise.
  • Disable the button while a transaction is pending, so a double tap does not send two.
  • Show amounts in familiar units with a sensible number of decimals, and the fee estimate beside them.
  • Link every transaction to a block explorer. It is the user's independent receipt.
  • Do not mark important actions final on the first block. Recent blocks can occasionally be replaced, so wait for a few confirmations or for finality when real value depends on it.
  • Do not ask for an unlimited token approval by default.
Advanced

Front-end security

The contract may be flawless and users can still lose money through the screen in front of it. The front end decides what the wallet is asked to sign, so whoever controls the front end controls that request.

Hijacked website
An attacker who takes over your domain, your hosting or one of your script dependencies can swap the contract address for their own. Pin dependency versions, protect DNS and deploy accounts with strong two-factor login, and keep the contract address in reviewed code.
Phishing copies
A cloned site on a lookalike domain asks users to "verify" their wallet. Tell users plainly that you will never ask for a seed phrase, because no real app needs one.
Blind signing
If the wallet shows only a hex string, the user cannot tell what they are approving. Use typed data and verified contracts so the wallet can show readable details.
Leftover approvals
An old unlimited allowance stays active for years. Request exact amounts and give users a way to see and revoke what they granted.
Exposed keys
An RPC key in front-end code is public. Restrict it by domain in the provider's dashboard. Never ship a private key that holds funds inside an app.
Trusting your own indexer
Use the indexer to display data. Before any action that moves value, read the current state from the chain.
Intermediate

Shipping checklist

  1. Develop on a local chain. Anvil or Hardhat gives you instant blocks and accounts with test ETH.
  2. Keep one config per chain: chain ID, RPC URLs, contract addresses, deployment block, explorer URL. Nothing else in the app should hard-code these.
  3. Generate the ABI from the build. Copying it by hand leads to an app that calls functions the deployed contract does not have.
  4. Deploy to a testnet and verify the source on the explorer. Run the whole flow with a fresh wallet, on a real phone.
  5. Walk every exit from the transaction diagram: reject, wrong network, no funds, revert, app killed while pending.
  6. Set up a fallback provider and watch your request counts.
  7. Monitor the contract's events and alert on anything unexpected, such as an ownership change.
  8. Go to mainnet or a Layer 2 with small limits first, and raise them as confidence grows.
Practice

Questions and answers

The questions people ask most, grouped by level. Try to answer each one aloud before opening it.

Basic
Is blockchain the same thing as Bitcoin?

No. Blockchain is the record-keeping method. Bitcoin is one application built on it, the first one. Email and the internet have the same relationship.

Where is the blockchain stored?

On every full node. For Bitcoin that is tens of thousands of computers around the world, each holding the complete history. There is no master copy.

If everything is public, how is it private?

It is pseudonymous. The chain shows addresses, not names. Once an address is linked to you, for example through an exchange that checked your identity, your whole history at that address is readable.

Can a transaction be reversed?

Not by anyone on the network. Once confirmed it stays. The receiver can send the money back with a new transaction if they choose to. Send to a wrong address and it is usually lost.

What does a miner or validator actually do?

They collect pending transactions, check them, pack them into a block and propose it. Miners earn the right by solving a hash puzzle. Validators earn it by locking up a deposit. Both are paid in new coins and fees.

Why can't I just copy a coin like I copy a file?

A coin is not a file. It is an entry in the shared ledger. Copying data on your own computer changes nothing, because every other node still holds the real record and will reject a spend that the ledger does not support.

What is a wallet, really?

A key manager. It stores your private keys and signs transactions with them. The coins never sit "in" the wallet. They are entries on the chain that your key can move.

Intermediate
What stops someone creating thousands of fake nodes to outvote everyone?

Votes are not counted per node. They are weighted by something costly: computing power in Proof of Work, locked coins in Proof of Stake. A thousand fake identities with no hardware or stake behind them have no weight. This defence is called Sybil resistance.

Why did Ethereum move from Proof of Work to Proof of Stake?

Mainly energy. The change cut Ethereum's electricity use by about 99.95%. It also removed the need for specialised mining hardware and made later scaling upgrades easier. The trade-off is that influence follows wealth held in ETH, and the protocol is more complex.

What is the difference between a coin and a token?

A coin is native to its chain and pays that chain's fees: BTC on Bitcoin, ETH on Ethereum. A token is created by a smart contract on top of a chain. USDC on Ethereum is a token, and you still need ETH to pay the gas to move it.

Why are fees sometimes high?

Block space is limited and sold to the highest bidders. When many people want in at once, the price rises. Nothing is wrong with the network. It is an auction for a scarce resource, and Layer 2 networks exist to make it cheaper.

Is a smart contract a legal contract?

Not by default. It is a program. It enforces what the code says, not what the parties meant. Some jurisdictions recognise agreements carried out by code, but a bug or a dispute still ends up with lawyers and courts.

If contracts cannot be changed, how do teams fix bugs?

Either they deploy a new contract and ask users to move, or they build in an upgrade path from the start. The common pattern is a proxy: users call a fixed address that forwards to a replaceable logic contract. Upgradeable contracts are only as trustworthy as whoever controls the upgrade.

What is a nonce?

A number used once. In mining it is the value a miner keeps changing to get a hash that meets the target. In an Ethereum account it is a transaction counter that prevents the same signed transaction from being replayed.

How does a private chain differ from a shared database?

In a shared database one administrator can change anything. In a permissioned chain, each member runs a node, every change is signed, and no single member can rewrite history without the others noticing. If one company runs all the nodes, the difference largely disappears.

Advanced
What is finality, and why do Bitcoin and Ethereum describe it differently?

Finality is the point after which a block will not be reversed. Bitcoin's is probabilistic: the chance of reversal shrinks with every block on top, and it never reaches exactly zero. Ethereum's Proof of Stake adds explicit finality. Once two thirds of the stake has voted for a checkpoint, reversing it would require destroying at least a third of all staked ETH.

What is MEV?

Maximal extractable value. Whoever orders transactions in a block can profit from that position, for example by placing their own trade just before and after a large one. It is a hidden cost to users. Private transaction relays and fair-ordering designs try to reduce it.

Where does a rollup's data live, and why does it matter?

A rollup must publish enough data for anyone to rebuild its state. If that data goes to Ethereum, users can always exit even if the rollup operator disappears. If it goes somewhere cheaper, fees drop and you add a new party to trust. This is the data availability question.

What is account abstraction?

Making a user's account a smart contract instead of a bare key pair. The account can then define its own rules: sign in with a passkey, set daily limits, let an app pay the gas, or recover through trusted contacts. It removes much of the seed-phrase burden. ERC-4337 is the main standard.

Why are cross-chain bridges attacked so often?

A bridge locks assets on one chain and issues matching tokens on another. The locked pool is a large target, and its safety depends on a small set of signers or on complex verification code. A flaw in either lets an attacker mint or release assets they never paid for.

How does sharding relate to rollups?

Sharding splits a chain's work across groups of nodes. Ethereum dropped its plan to shard execution and now treats rollups as the place where execution scales. The base layer concentrates on being a secure, cheap place for rollups to publish data.

What would quantum computers do to all this?

A large enough quantum computer could derive a private key from an exposed public key, breaking today's signatures. Hash functions are much less affected. No such machine exists yet, and quantum-resistant signature schemes are standardised and being planned into upgrades. The practical risk is a slow migration, not a sudden collapse.

Smart contracts deep dive
Why can't my app read the return value of a transaction?

A transaction is processed later, inside a block, so there is nothing to return at the moment you send it. You get a receipt with a success flag, the gas used and the events emitted. Design write functions to emit an event carrying whatever the app needs.

What is the difference between require, revert and assert?

All three undo the transaction. require checks a condition and carries a message. revert with a custom error does the same job more cheaply and is the current habit. assert is for things that should be impossible. If one fires, the contract has a bug.

Why is storing data on chain so expensive?

Every full node must keep it forever and include it in every future state calculation. The fee pays for that permanent shared burden. An event is far cheaper because nodes do not need it to run contracts.

If private variables are readable, how do contracts keep anything secret?

They do not. Designs that need secrecy use commit-then-reveal, where you publish a hash first and the value later, or zero-knowledge proofs, or they keep the secret off chain entirely.

What is the difference between call and delegatecall?

A call runs the other contract's code on the other contract's storage. A delegatecall runs the other contract's code on your own storage, with the original sender preserved. Proxies depend on it, and it is dangerous for the same reason.

Why does approve plus transferFrom exist when transfer already works?

A contract is not notified when tokens are transferred to it, so it cannot react. With an allowance, the contract itself pulls the tokens inside its own function and can do the rest of its work in the same transaction. Newer standards let a signed message replace the separate approve step.

Can a contract call itself on a schedule?

No. Nothing runs unless a transaction triggers it. Recurring jobs are done by outside bots, often paid a small reward by the contract for calling the function at the right time.

Is an audited contract safe?

Safer. An audit is a time-boxed review by people who can miss things, and it covers only the version they were shown. Several of the largest losses came from audited code or from changes made after the audit. Look for multiple audits, a live bug bounty, time in production, and sensible admin controls.

Building a dApp deep dive
Does a dApp need a backend at all?

A simple one does not. The front end, a node provider and the contract are enough. Most real products add one for indexing, notifications, profiles and anything private. The rule is that the backend may make the app nicer, and the contract alone decides who owns what.

Why do I need an RPC provider? Can the app not talk to the chain directly?

Talking to the chain means talking to a node. Running a node needs storage, bandwidth and upkeep, and a phone cannot do it. A provider runs nodes for you behind a URL. It can see your requests and can go down, which is why apps keep a fallback.

My transaction has been pending for ten minutes. What happened?

Usually the fee offered is below what block producers currently accept, so it waits in the mempool. The user can speed it up from the wallet, which sends the same transaction again with the same nonce and a higher fee. Only one of the two will be mined.

What is a reorg, and should my UI care?

A reorg is when the last block or two are replaced by a competing branch. A transaction you saw as mined can briefly return to pending. For a like button it does not matter. For releasing goods or crediting a balance, wait for several confirmations or for finality.

How can people use my app if they hold no ETH for gas?

Someone else pays. With smart-contract wallets a service called a paymaster can sponsor the fee, or accept it in a stablecoin. Many consumer apps on Layer 2 networks do this so that new users never meet the word gas.

Can I build a dApp in Flutter or native mobile code?

Yes. The concepts are identical. You need a library that encodes calls from the ABI and a way to reach a wallet, which on mobile means a deep link to a wallet app or an embedded wallet SDK. The contract side does not change at all.

Is the front end itself decentralized?

Usually not. Most dApp sites sit on ordinary hosting behind an ordinary domain. Some teams also publish the site to IPFS so it stays reachable if the main host goes away. The contract keeps working either way, and anyone can build another front end for it.

How do I support several chains?

Deploy the contract to each one. It will get a different address on each unless you plan for matching addresses. Keep a config entry per chain, read the wallet's chain ID, and pick the matching entry. Balances and history are separate per chain, so say clearly which network the user is looking at.

Reference

Glossary

ABI
The description of a contract's functions that an app uses to call it.
Address
A short identifier derived from a public key. Where funds are sent.
Block
A batch of transactions plus a header that links it to the previous block.
Consensus
The rule by which nodes agree on the next block.
dApp
An application whose back-end logic runs in smart contracts.
EVM
Ethereum Virtual Machine. The runtime that executes contract code on every node.
Fork
Two competing versions of the chain, temporary or permanent.
Gas
The unit that measures computation on Ethereum. You pay for it in ETH.
Hash
A fixed-length fingerprint of data. One way, and sensitive to any change.
Layer 2
A network that processes transactions off the main chain and settles on it.
Mempool
The waiting area for transactions not yet in a block.
Merkle root
A single hash that summarises every transaction in a block.
Node
A computer that stores the chain and checks new blocks.
Nonce
A number used once. The value miners vary, or an account's transaction counter.
Oracle
A service that brings outside data onto the chain.
Private key
The secret number that controls an account. Never share it.
Rollup
A Layer 2 that posts compressed batches of transactions to Layer 1.
Seed phrase
12 or 24 words that can regenerate all the keys in a wallet.
Slashing
Destroying part of a validator's deposit as a penalty for cheating.
Smart contract
A program stored on a blockchain that runs when called.
Stablecoin
A token designed to hold the value of a currency.
UTXO
Unspent transaction output. Bitcoin's unit of ownership.
Validator
A participant who stakes coins to propose and vote on blocks.
Zero-knowledge proof
A proof that a statement is true which reveals nothing else.

What to do next

Reading gets you the vocabulary. These steps, in this order, get you the skill. All of them use test networks where the coins are free and worth nothing.

  1. Read a real block. Open a block explorer such as Etherscan or mempool.space and find the previous hash, the Merkle root and the fee of one transaction.
  2. Set up a test wallet. Install a self-custody wallet, switch it to the Sepolia test network, and get test ETH from a faucet. Use a fresh wallet with no real funds.
  3. Deploy the escrow contract. Paste the code from Part 2 into Remix, the browser IDE for Solidity, and deploy it to Sepolia. Call confirmDelivery from the buyer and from another account and compare the results.
  4. Write your own token. Build an ERC-20 using the OpenZeppelin library. Read the library code. It is short.
  5. Move to a local toolchain. Use Foundry or Hardhat to write tests. Reproduce the reentrancy bug on purpose, then fix it.
  6. Build a small dApp. One screen that connects a wallet, reads a value from your contract, and sends one transaction with pending and confirmed states.
  7. Try a Layer 2. Deploy the same contract to a rollup testnet and compare the fee.
  8. Run this course's own code. The contracts, tests and dApp calls shown on this page are in a ready project at ~/Documents/Blockchain-Academy-Starters. Its README lists the three commands.
  9. Explore the enterprise side. Run the Hyperledger Fabric test network locally and deploy the sample chaincode.
