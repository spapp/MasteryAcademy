Redis, Kafka and RabbitMQ Field Guide

Redis keeps small pieces of data in memory so they come back in under a millisecond. Kafka keeps an ordered record of everything that happened so many systems can read it at their own pace. RabbitMQ hands each job to a worker and forgets it once the work is done. Docker is how you run all three on your laptop. ZooKeeper is the coordinator Kafka depended on until version 4. Each tab goes from the first command to production patterns.

How they connect: Docker starts the servers. Redis, Kafka and RabbitMQ do the work. ZooKeeper explains how older Kafka clusters chose a controller. The Docker tab stays close to these servers. The DevOps Mastery Academy has the wider Docker course.

Basics and core commands

What Redis is

Redis is a server that holds data in RAM and answers by key. You give it a name, it gives you the value. Because nothing is read from disk on the request path, a lookup usually takes well under a millisecond.

Think of it as a shared dictionary that every instance of your app can reach over the network. The values are not only strings. Redis also has lists, sets, hashes and sorted sets built in, and each one has commands that run on the server.

Commands run one at a time on a single thread. That is why INCR is safe when a hundred clients call it at once: no two commands ever interleave.

Strings, keys and expiry

SET user:42:name "Asha"        # OK
GET user:42:name               # "Asha"
EXISTS user:42:name            # (integer) 1
DEL user:42:name               # (integer) 1
GET user:42:name               # (nil)

SET otp:42 "918273" EX 300     # expires after 300 seconds
TTL otp:42                     # (integer) 300, counts down
TTL user:42:name               # -2 = key does not exist, -1 = no expiry

INCR page:home:views           # (integer) 1, atomic counter
INCRBY page:home:views 10      # (integer) 11
  • Name keys with colons, from general to specific: user:42:cart. Redis does not care, but people and tools do.
  • Give cache keys an expiry. A cache with no TTL grows until memory runs out.

Trap. KEYS * walks every key and blocks the server while it does. It is fine on your laptop and an outage in production. Use SCAN 0 MATCH user:* COUNT 100, which returns a page and a cursor.

Caching from your app (cache-aside)

        
The most common pattern. Ask Redis first. On a miss, read the database, store the answer with a TTL, return it. On a write, update the database and delete the key.


// Node.js, package "redis"
import { createClient } from 'redis';
const redis = createClient({ url: 'redis://localhost:6379' });
await redis.connect();

async function getProduct(id) {
  const key = `product:${id}`;
  const hit = await redis.get(key);
  if (hit) return JSON.parse(hit);
  const row = await db.products.findById(id);
  if (row) await redis.set(key, JSON.stringify(row), { EX: 300 });
  return row;
}
async function updateProduct(id, patch) {
  await db.products.update(id, patch);
  await redis.del(`product:${id}`);
}


# Python, package "redis"
import json, redis
r = redis.Redis(host="localhost", port=6379, decode_responses=True)

def get_product(pid):
    key = f"product:{pid}"
    hit = r.get(key)
    if hit:
        return json.loads(hit)
    row = db.find_product(pid)
    if row:
        r.set(key, json.dumps(row), ex=300)
    return row

        
Trap. Treat Redis as optional in this pattern. If it is down, the code should fall through to the database, not return an error.

      


      

        
Pipelines, transactions and Lua

        
    
          
  • Pipeline. Send many commands in one network round trip. It saves time and gives no atomicity.
    • 
          
  • MULTI / EXEC. Queue commands and run them as one uninterrupted block. There is no rollback: if one command fails, the others still apply.
    • 
          
  • WATCH. Optimistic lock. EXEC returns nil if a watched key changed, and you retry.
    • 
          
  • Lua script. Runs on the server as one atomic step. Use it for "read, decide, write".
    •

Level 3 · 1 to 2 weeks
Production patterns


      

        
Invalidation and the stampede

        
When a popular key expires, every request misses at once and they all hit the database together. Three fixes, usually combined:

        
    
          
  • Add random jitter to TTLs (300 seconds plus 0 to 60) so keys do not expire together.
    • 
          
  • Let one request rebuild the value behind a short lock while the others wait or serve the old value.
    • 
          
  • Refresh hot keys in the background before they expire.
    • 
        

        
Also cache "not found" for a short time. Otherwise a request for an id that does not exist reaches the database every time.

      


      

        
Memory limit and eviction


maxmemory 2gb
maxmemory-policy allkeys-lru

        
    
          
  • noeviction (default): writes fail when memory is full. Right when Redis is your source of truth.
    • 
          
  • allkeys-lru / allkeys-lfu: drop the least recently or least frequently used key. Right for a pure cache.
    • 
          
  • volatile-ttl, volatile-lru: only evict keys that have an expiry.
    • 
        

      


      

        
Rate limiting

        
Fixed window: count requests per user per minute. The script keeps the increment and the expiry in one atomic step, so a crash between them cannot leave a counter that never expires.


-- KEYS[1] = rate:user42:202611131045   ARGV[1] = window seconds
local n = redis.call('INCR', KEYS[1])
if n == 1 then redis.call('EXPIRE', KEYS[1], ARGV[1]) end
return n                       -- caller rejects when n > limit

        
A fixed window allows a burst of twice the limit across the boundary. For a smoother limit, keep request timestamps in a sorted set, remove the ones older than the window with ZREMRANGEBYSCORE, and count the rest with ZCARD.

      


      

        
Pub/Sub, Streams and locks

        
    
          
  • Pub/Sub delivers to whoever is connected right now. A subscriber that is offline misses the message. Good for live notifications, wrong for work that must happen.
    • 
          
  • Streams store the messages. A consumer group gives each message to one worker, and the worker confirms with XACK. Unconfirmed messages can be claimed by another worker.
    • 
        


XADD orders * user 42 sku 9                       # "1731490000000-0"
XGROUP CREATE orders billing $ MKSTREAM
XREADGROUP GROUP billing w1 COUNT 10 BLOCK 5000 STREAMS orders >
XACK orders billing 1731490000000-0

        
A lock is one command: SET lock:report 7f3a NX PX 30000. The random value is your token. Release only if the token is still yours, in a script, so you never delete a lock someone else took after yours expired.


if redis.call('GET', KEYS[1]) == ARGV[1] then
  return redis.call('DEL', KEYS[1])
else return 0 end

        
Trap. A Redis lock can expire while its holder is paused. It prevents duplicate work most of the time. Where a double run would corrupt data, also check a version number in the database.

Replication, Sentinel and Cluster

        
    
          
  • Replication. Replicas copy the primary asynchronously. A write acknowledged by the primary can be lost if it dies before the replica receives it.
    • 
          
  • Sentinel. Separate processes that watch the primary and promote a replica when it fails. One dataset, automatic failover.
    • 
          
  • Cluster. Splits keys across primaries using 16,384 hash slots. The slot is CRC16 of the key, modulo 16384. Use it when the data or the write load no longer fits one machine.
    • 
        

        
In Cluster, a multi-key command only works when all keys are in the same slot. Force that with a hash tag: only the part in braces is hashed, so {user:42}:cart and {user:42}:profile land together.

      


      

        
Operating it

        
    
          
  • Find slow commands with SLOWLOG GET 10, memory with INFO memory and MEMORY USAGE key.
    • 
          
  • A big key (a list with millions of items) makes one command slow, and one slow command delays everyone. Delete big keys with UNLINK, which frees memory in the background.
    • 
          
  • Watch the hit rate: keyspace_hits / (keyspace_hits + keyspace_misses) from INFO stats.
    • 
          
  • Never expose port 6379 to the internet. Set a password or ACL users, bind to private addresses, use TLS between networks.
    • 
          
  • Redis 8 folded JSON, search, time series and probabilistic types into the main server. Valkey is the open-source fork many cloud providers now run; the commands in this guide work on both.
    •

Check yourself

        

          
Why is Redis fast?
Data lives in memory, the structures are simple and purpose-built, and commands run on one thread so there is no locking. Network I/O is multiplexed, so one thread serves thousands of connections.

          
What happens when memory is full?
It depends on maxmemory-policy. With noeviction writes return an error. With an LRU or LFU policy Redis removes keys to make room.

          
MULTI/EXEC or Lua?
MULTI runs a fixed list of commands together. Lua can read a value and decide what to write based on it, all in one atomic step. Use Lua when the logic branches.

          
Pub/Sub or Streams?
Pub/Sub does not store anything, so offline subscribers miss messages. Streams store entries, support consumer groups and acknowledgements, and can be replayed.

          
How do you keep cache and database consistent?
Write the database first, then delete the cache key, and keep a TTL as a safety net. Accept a short stale window, or use change data capture to invalidate when you cannot.

          
Why can Redis lose an acknowledged write?
Replication is asynchronous and AOF usually syncs once a second. A crash in that gap loses the latest writes. WAIT reduces the risk and does not remove it.

          
What is a hash tag?
The part of a key inside braces. In Cluster only that part decides the slot, which lets related keys share a slot so multi-key commands and scripts work.

The log and the CLI


      

        
What Kafka is

        
Kafka is a set of servers that store events in the order they arrived. An event is a small record such as "order 17 was placed". Producers add events to the end. Consumers read forward from wherever they stopped.

        
The difference from a normal queue is that reading does not remove anything. Events stay for a set time, seven days by default, so several teams can read the same events independently and a new service can replay history.

        
Use it when many systems need to react to the same facts, or when traffic arrives faster than the receiver can process it and you need a buffer that does not lose data.

Level 2 · 3 to 5 days
Reliable producers and consumers


      

        
Keys decide ordering

        
Kafka guarantees order only within one partition. Events with the same key go to the same partition, so choose the key by asking "which events must stay in order?". For orders that is the order id. For a wallet it is the user id.

        
Trap. Adding partitions later changes which partition a key maps to, and old and new events for the same key may be read out of order. Pick the partition count with room to grow.

      


      

        
Offsets, commits and delivery guarantees

        
A consumer saves its position by committing an offset. When it restarts, or its partition moves to another consumer, reading resumes from the last commit. When you commit decides what happens on a crash.

        

          
GuaranteeHowOn a crash

          
At most onceCommit first, then processThe event is lost

          
At least onceProcess first, then commitThe event is processed again

          
Exactly onceTransactions, or at least once plus an idempotent handlerThe effect appears once

        

        
Most systems run at least once and make the handler safe to repeat: keep the event id in the database with a unique constraint, or use an upsert.

Producer settings that matter

        
    
          
  • acks=all: the write is confirmed only after the in-sync replicas have it. acks=1 is faster and can lose data when a leader dies.
    • 
          
  • enable.idempotence=true: retries cannot create duplicates or reorder events. It is the default in current clients.
    • 
          
  • linger.ms and batch.size: wait a few milliseconds to send events in batches. Much higher throughput for a small delay.
    • 
          
  • compression.type=lz4 or zstd: smaller batches on the wire and on disk.
    • 
        

      


      

        
Replication

        
Each partition has one leader and several followers on other brokers. Producers and consumers talk to the leader. Followers that are caught up form the in-sync replica set (ISR). If the leader dies, a member of the ISR takes over.

        
The standard safe setup is replication factor 3, min.insync.replicas=2 and acks=all. You can lose one broker with no data loss and no downtime. With two brokers gone, writes are refused instead of being accepted unsafely.

      


      

        
Retention and compaction

        
    
          
  • Delete (default): events older than retention.ms, or beyond retention.bytes, are removed. Right for event history.
    • 
          
  • Compact: Kafka keeps at least the latest event for every key and removes older ones. Right for "current state" topics such as user settings. An event with a null value deletes the key.
    • 
        

      

    


    

      
Level 3 · 2 to 4 weeks
Production patterns


      

        
Failures: retry topics and a dead letter topic

        
One bad event must not block a partition forever. After a few attempts, publish it to a retry topic that is consumed with a delay, and after the last attempt to a dead letter topic, for example orders.dlq, with the error in a header. Then commit and move on. Alert on the dead letter topic and build a way to replay it.

        
Trap. Moving an event to a retry topic breaks ordering for its key. If order matters, park all later events for that key too, or stop the partition and page someone.

      


      

        
Exactly once and the outbox

        
Kafka transactions let a consumer read from one topic, write to another and commit its offset as a single atomic step. Consumers with isolation.level=read_committed never see the aborted writes. This covers Kafka-to-Kafka pipelines only.

        
The moment a database is involved, use the outbox pattern. In the same database transaction that changes the order, insert a row into an outbox table. A separate process, often Debezium reading the database log, publishes those rows to Kafka. The database change and the event can no longer disagree.

      


      

        
Schemas

        
Producers and consumers are deployed at different times, so the event format is a contract. A schema registry stores Avro, Protobuf or JSON Schema definitions and rejects a change that would break readers. The everyday rule for backward compatibility: you may add a field with a default and you may not remove or rename a field that readers use.

      


      

        
Connect and stream processing

        
    
          
  • Kafka Connect moves data in and out without custom code. Source connectors read from systems such as Postgres (change data capture); sink connectors write to systems such as Elasticsearch or S3.
    • 
          
  • Kafka Streams is a Java library for transforming streams: filter, join, count per time window. It keeps state locally and backs it up to Kafka.
    • 
          
  • Flink and ksqlDB do the same job as separate systems, Flink with more power and ksqlDB with SQL.
    • 
        

      


      

        
Rebalances and lag

        
When a consumer joins, leaves or stops polling, the group reassigns partitions. That is a rebalance, and frequent ones stall processing. The usual causes and fixes:

        
    
          
  • A handler slower than max.poll.interval.ms (5 minutes by default) gets the consumer removed. Lower max.poll.records or move slow work off the polling loop.
    • 
          
  • Rolling deploys shuffle everything. Use the cooperative sticky assignor, or the newer consumer group protocol in Kafka 4, so only the affected partitions move. Static membership (group.instance.id) lets a restarted pod keep its partitions.
    • 
          
  • Lag that grows steadily means consumers are too slow. Add consumers up to the partition count, speed up the handler, or add partitions.
    • 
        

      


      

        
Sizing, cluster and security

        
    
          
  • Partition count sets the maximum number of consumers working in parallel. Start from target throughput divided by what one consumer handles, then add headroom. Thousands of tiny partitions cost memory and slow recovery.
    • 
          
  • Since Kafka 4.0 there is no ZooKeeper. A group of controller nodes runs the metadata using KRaft, Kafka's own Raft implementation.
    • 
          
  • Turn on TLS for traffic, SASL for identity and ACLs so each service can touch only its own topics and groups.
    • 
          
  • Watch under-replicated partitions, consumer lag, request latency and disk usage. Mirror topics to another region with MirrorMaker 2 when you need disaster recovery.
    •

Check yourself

        

          
How is Kafka different from a queue like RabbitMQ?
A queue hands each message to one worker and deletes it. Kafka keeps an ordered log; each consumer group tracks its own position, so many groups read the same events and can replay them.

          
Where is ordering guaranteed?
Within a single partition only. Use the same key for events that must stay in order.

          
Two consumers in one group, one partition. What happens?
One consumer gets the partition and the other sits idle as a standby. Parallelism is capped by the partition count.

          
What does acks=all with min.insync.replicas=2 give you?
A write succeeds only when at least two replicas have it, so losing one broker loses no acknowledged data. If fewer than two replicas are in sync, the producer gets an error.

          
Why can a consumer see the same event twice?
It processed the event and crashed, or lost its partition in a rebalance, before committing the offset. The next owner starts from the last commit.

          
What is consumer lag?
The log end offset minus the group's committed offset, per partition. It is the number of events waiting to be processed.

          
When do you use a compacted topic?
When consumers need the latest value per key, not the full history: configuration, profiles, a changelog used to rebuild state.

          
What problem does the outbox pattern solve?
Writing to a database and publishing to Kafka are two systems, and one can fail after the other succeeded. Writing the event to an outbox table in the same transaction makes them succeed or fail together.

Queues and first messages


      

        
What RabbitMQ is

        
RabbitMQ is a message broker. Think of a post office. One program hands it a message. RabbitMQ keeps the message in a queue, delivers it to a program that is ready for it, and deletes it once that program says the work is done.

        
The sender does not wait and does not need to know who will do the work. That is the point. A web request can say "send this email" and return at once, while a worker sends the email a moment later.

        
Use it for background jobs, for spreading work across several workers, and for letting one service tell others that something happened without calling each of them.

QueueA line of messages waiting for a consumer.

          
BindingA rule that connects an exchange to a queue.

          
Routing keyA label on each message that the exchange compares with the bindings.

          
ConsumerA program that receives messages and acknowledges them.

Not losing messages

        
Four settings work together. Leave one out and a restart or a crash can lose work.

        
    
          
  • Durable queue. The queue itself survives a broker restart.
    • 
          
  • Persistent message. The message is written to disk, not held only in memory.
    • 
          
  • Publisher confirm. The producer waits until the broker says "stored".
    • 
          
  • Manual acknowledgement. The consumer says "done" only after the work has finished. If it crashes first, the broker gives the message to another consumer.
    • 
        

        
Prefetch limits how many unacknowledged messages one consumer may hold. With no limit, the broker pushes everything to the first worker that connects and the others sit idle.

      


      

        
Code: Node


// setup.mjs, package "amqplib". Producer and worker both call this.
export async function setup(ch) {
  await ch.assertExchange('jobs.dlx', 'fanout', { durable: true });
  await ch.assertQueue('jobs.failed', { durable: true });
  await ch.bindQueue('jobs.failed', 'jobs.dlx', '');
  await ch.assertQueue('jobs', { durable: true, deadLetterExchange: 'jobs.dlx' });
}


// producer.mjs
import amqp from 'amqplib';
import { setup } from './setup.mjs';

const conn = await amqp.connect('amqp://guest:guest@localhost:5672');
const ch = await conn.createConfirmChannel();
await setup(ch);

for (const photo of [1, 2, 3]) {
  ch.sendToQueue('jobs', Buffer.from(JSON.stringify({ photo })), { persistent: true });
}
await ch.waitForConfirms();          // the broker has stored all three
await conn.close();


// worker.mjs
import amqp from 'amqplib';
import { setup } from './setup.mjs';

const conn = await amqp.connect('amqp://guest:guest@localhost:5672');
const ch = await conn.createChannel();
await setup(ch);
await ch.prefetch(1);                // one unfinished job at a time per worker

await ch.consume('jobs', async (msg) => {
  const job = JSON.parse(msg.content.toString());
  try {
    await resize(job);
    ch.ack(msg);                     // done: the broker deletes it
  } catch (err) {
    ch.nack(msg, false, false);      // failed, do not requeue: goes to jobs.dlx
  }
});

    ch.basic_ack(delivery_tag=method.delivery_tag)

What "delivered" means

        
With manual acknowledgements you get at-least-once delivery. A worker can finish the job and crash before it acknowledges, and the message is delivered again. Make handlers safe to repeat: record the message id in your database with a unique constraint, or write the result as an upsert.

        
Order is kept for one queue with one consumer. Several consumers, or a message put back on the queue, break that order. If order matters for a customer, send all of that customer's messages to the same queue and read it with one consumer.

Production patterns


      

        
Failed messages and retries

        
A message is dead-lettered when a consumer rejects it without requeue, when it sits longer than its time-to-live, or when the queue is full. If the queue names a dead letter exchange, the message is sent there instead of being deleted. You saw that with photo 2.

        
For a delayed retry, dead-letter into a wait queue that has no consumers and a time-to-live of, say, 30 seconds, and make that queue dead-letter back to the work queue. The message returns by itself after the delay. Count the attempts from the x-death header and park the message in a failed queue after a few tries.

        
Trap. nack with requeue set to true puts the message straight back at the front. A message that always fails then loops at full speed. In a test for this guide, a quorum queue on RabbitMQ 4.4 delivered one always-requeued message 4,432 times in four seconds and never gave up. Reject without requeue and let a dead letter exchange handle the retry.

When RabbitMQ pushes back

        
RabbitMQ is fastest when queues are short. A queue that only grows means consumers are too slow or absent. Two alarms protect the broker:


rabbitmq-diagnostics status
Memory high watermark setting: 0.6 of available memory
Low free disk space watermark: 0.05 gb

rabbitmq-diagnostics check_local_alarms
Node rabbit@rabbit reported no local alarms

        
When memory passes the watermark or free disk falls below the limit, the broker stops accepting messages from producers until it recovers. Publishing appears to hang. Give queues a maximum length or a time-to-live so that a stuck consumer cannot fill the disk.

Connections and monitoring

        
    
          
  • Open one connection per process and keep it open. Use a channel per thread or per task. Opening a connection for every message is the most common cause of a slow, overloaded broker.
    • 
          
  • Reconnect with a delay when the connection drops, and declare queues again on reconnect.
    • 
          
  • Watch per queue: messages ready, messages unacknowledged, consumer count, publish and acknowledge rates. Ready growing means too few consumers. Unacknowledged growing means stuck consumers.
    • 
          
  • The broker serves metrics for Prometheus on port 15692. rabbitmq-diagnostics check_running exits with 0 when the node is healthy, which suits a container health check.

Check yourself

        

          
Exchange or queue: where does a producer send?
Always to an exchange. The exchange uses bindings and the routing key to decide which queues get a copy. Sending "to a queue" uses the default exchange behind the scenes.

          
What is the difference between * and # in a topic binding?
* matches exactly one word. # matches zero or more words. order.* matches order.paid and not order.paid.eu; order.# matches both.

          
What happens to a message that matches no queue?
It is dropped. To catch these, set an alternate exchange or publish with the mandatory flag so the broker returns it.

          
Why set prefetch?
It caps unacknowledged messages per consumer, so work is shared fairly and a slow worker does not hoard messages in memory.

          
What do you need so a broker restart loses nothing?
A durable queue, persistent messages, publisher confirms, and manual acknowledgements after the work is done. For a node failure, also a quorum queue.

          
What is a dead letter exchange?
An exchange that receives messages a queue gives up on: rejected without requeue, expired, or pushed out by a length limit. It is how failed messages are kept and retried.

          
Classic or quorum queue?
Quorum for data that matters, because it is copied to several nodes and survives a node failure. Classic for temporary or rebuildable data on one node.

          
When would you choose Kafka over RabbitMQ?
When events must be kept and replayed, when many independent readers need the same stream, or when the volume is very high.

Containers and core commands


      

        
What Docker is

        
Docker packs a program together with everything it needs to run, then runs that package the same way on any machine. You did not install Redis or Kafka for this guide. You ran a package someone else built.

        
Two words carry most of it. An image is the package: files plus the command to start. It never changes. A container is one running copy of an image, with its own files, its own network address and its own process list.

        
A container is not a virtual machine. It is a normal process that the operating system keeps separated from the others, so it starts in about a second. On a Mac, Docker Desktop runs one small Linux machine in the background and all containers live inside it.

    Volumes: keeping data
    
        
    Files written inside a container belong to that container. Delete it and start a new one, and Redis is empty. A volume is storage that Docker keeps separately and attaches at a path.
    

    docker volume create redis-data
docker run -d --name redis -v redis-data:/data redis:8 redis-server --appendonly yes
docker exec redis redis-cli SET city Bengaluru     # OK
docker rm -f redis                                 # container gone

docker run -d --name redis -v redis-data:/data redis:8 redis-server --appendonly yes
docker exec redis redis-cli GET city               # Bengaluru
    
        
    A named volume (redis-data:/data) is managed by Docker and is right for database files. A bind mount (./src:/app/src) maps a folder from your machine and is right for source code you are editing.

    docker network create shop

docker run --rm --network shop redis:8 redis-cli -h redis PING

    The Kafka listener trap
    
        
    A Kafka client connects twice. First to the address you gave it, to ask for the cluster layout. Then to the address the broker advertises for itself. If the broker advertises localhost:9092, a client in another container follows that to its own localhost and fails.
    
        
    The fix is two listeners, as in the file above. INTERNAL advertises kafka:19092 for other containers. HOST advertises localhost:9092 for programs on your Mac. Each client uses the one that matches where it runs.

    Production habits
    

      
    
        
    Health checks and start order
    
        
    Plain depends_on waits only until the other container has started, not until the server inside is ready. Kafka takes several seconds to accept connections. A health check plus condition: service_healthy makes the API wait for a real answer. Your app should still retry its connections, because servers also restart later.
    
      
    

      
    
        
    Limits and restarts
    

    docker run -d --name redis --memory 256m --cpus 1 --restart unless-stopped redis:8
docker stats --no-stream redis
redis   11.68MiB / 256MiB   0.37%
    
        
      
          
    • Without a memory limit, one container can take all the memory on the machine. With one, the container is killed when it goes over, so set Redis maxmemory below the limit.
      • 
          
    • --restart unless-stopped brings the container back after a crash or a reboot. on-failure restarts only on a non-zero exit.
      • 
        
    
      
    

      
    
        
    Images: small, pinned, not root
    
        
      
          
    • Pin versions. redis:8 and apache/kafka:4.3.1 give the same result next month. latest, used in this guide for convenience, does not.
      • 
          
    • Use a small base (-alpine or -slim) and a multi-stage build so compilers and caches stay out of the final image. The API image above is 254 MB, most of it the Node runtime.
      • 
          
    • USER node in the Dockerfile runs the app as a normal user. If the app is broken into, the attacker is not root.
      • 
          
    • Never copy secrets into an image or write them in a Dockerfile. Anyone with the image can read them. Pass them at run time.
      • 
        
    
      
    

      
    
        
    Stateful servers in containers
    
        
    Redis and Kafka hold data, so they need more care than a stateless API. Give each one a volume, give Kafka brokers stable names, and stop them gracefully so they can flush to disk. In Kubernetes this is what a StatefulSet does. Many teams run their apps in containers and use a managed Redis and a managed Kafka instead.

    Check yourself
    
        
    
          
    Image or container?
    An image is the read-only package. A container is a running copy of it with its own writable files. Many containers can run from one image.
    
          
    How is a container different from a virtual machine?
    A virtual machine runs a full operating system. A container is a process on the host's kernel, separated by the operating system, so it is smaller and starts in about a second.
    
          
    What does -p 8080:80 mean?
    Port 8080 on your machine forwards to port 80 inside the container. Host first, container second.
    
          
    Where does data go when a container is removed?
    Files in the container are lost. Files in a volume or a bind mount stay.
    
          
    Why can the API reach Redis at the name redis?
    Compose puts all services on one network, and Docker's built-in name lookup resolves each service name to its container.
    
          
    Why does Kafka in Docker need two listeners?
    Clients reconnect to the address the broker advertises. Containers need the service name, programs on the host need localhost, so the broker advertises one of each.
    
          
    depends_on is set, yet the app fails at startup. Why?
    Without a health condition, depends_on waits for the container to start, not for the server to be ready. Add a health check and condition: service_healthy, and retry in the app.

    Level 1 · 2 to 3 hours
    Znodes and the shell
    

      
    
        
    What ZooKeeper is
    
        
    A cluster of servers has to agree on a few small facts. Which servers are alive? Which one is in charge? What is the current configuration? ZooKeeper is a small, very reliable store built to hold exactly those facts.
    
        
    It looks like a file system. Data lives in a tree of nodes called znodes, each with a path such as /brokers/ids/1 and a small value. Every server in a ZooKeeper group sees every change in the same order, so two clients can never both believe they are the leader.
    
        
    It is not a database for your application data. A znode holds at most about 1 MB, and the whole tree sits in memory.
    
      
    

      
    
        
    Start it and open the shell
    

    docker run -d --name zk -p 2181:2181 zookeeper:3.9
docker exec -it zk zkCli.sh
[zk: localhost:2181(CONNECTED) 0]
    
      
    

      
    
        
    Core commands
    

    ls /                               # [zookeeper]
create /shop "hello"               # Created /shop
get /shop                          # hello
set /shop "v2"
get -s /shop                       # v2, then details: dataVersion = 1 ...
create /shop/config "retries=3"
ls /shop                           # [config]

create -e /shop/worker-1 "alive"   # -e: temporary, tied to this session
create -s /shop/job- "a"           # -s: ZooKeeper adds a number
create -s /shop/job- "b"
ls /shop                           # [config, job-0000000002, job-0000000003, worker-1]

get -w /shop/config                # read and ask to be told about the next change
set /shop/config "retries=5"       # WatchedEvent type:NodeDataChanged path:/shop/config

delete /shop/config
deleteall /shop                    # delete a node and everything under it
quit
    
        
    The job numbers start at 2 because the counter belongs to the parent and config and worker-1 were created first.
    
      
    

      
    
        
    Three ideas that make it useful
    
        
    
          
    IdeaWhat it doesUsed for
    
          
    Ephemeral node (-e)Deleted automatically when the client that made it disconnects or stops sending heartbeats"I am alive" markers
    
          
    Sequential node (-s)Gets a growing number added to its nameFair ordering: queues, locks, elections
    
          
    Watch (-w)Tells the client once when a node changes; set it again to keep watchingReacting to changes without polling
    
        
    
        
    Put the first and third together and you have failure detection. Each worker creates an ephemeral node. Everyone else watches the parent. When a worker dies, its node disappears and the watchers are told.

    Ensemble and quorum
    
        
    One ZooKeeper server is a single point of failure, so production runs a group called an ensemble. A change is accepted only when more than half of the servers have it. That majority is the quorum.
    
        
    
          
    ServersMajority neededFailures survived

    Four servers survive no more failures than three, which is why ensembles have an odd size. Three is normal, five for large clusters.
    
        
    This is a real run of three servers. Each prints its role when asked with srvr.
    

    zk1: Mode: follower     zk2: Mode: follower     zk3: Mode: leader

docker compose stop zk3            # stop the leader
zk1: Mode: follower     zk2: Mode: leader       zk3: down
set /shop v2                       # still works: 2 of 3 is a majority

docker compose stop zk2            # now only 1 of 3
zk1: This ZooKeeper instance is not currently serving requests

docker compose start zk2 zk3
zk1: Mode: follower     zk2: Mode: leader       zk3: Mode: follower
get /shop                          # v2, on the server that was down
    
        
    One server left alone refuses to answer. That is deliberate. It cannot know whether the other two are dead or merely unreachable, and answering could produce two different truths.
    
      
    

      
    
        
    Leader, followers and sessions
    
        
      
          
    • One server is the leader. Every write goes through it and is copied to the followers in a fixed order. The protocol is called ZAB.
      • 
          
    • Reads are answered by whichever server the client is connected to, so a read can be a moment behind.
      • 
          
    • A client holds a session and sends heartbeats. If none arrive within the session timeout, the session expires and its ephemeral nodes are removed.
      • 
        
    
        
    Trap. A long garbage-collection pause looks the same as a crash. The session expires, the node vanishes, and a healthy process loses its role. Timeouts are a trade between fast detection and false alarms.
    
      
    

      
    
        
    Leader election, the standard recipe
    
        
    Every candidate creates an ephemeral sequential node under one parent, for example /election/n-. The candidate with the lowest number is the leader. Each other candidate watches only the node just before its own. When the leader dies, its node disappears, exactly one candidate is told, and it takes over.
    
        
    A lock works the same way: lowest number holds the lock. In Java, use the Curator library for these recipes. The edge cases are hard to get right by hand.
    
      
    

      
    
        
    What Kafka kept in ZooKeeper
    
        
    This is from a real two-broker cluster on Kafka 3.6 (image confluentinc/cp-kafka:7.6.1) after creating the topic orders with 3 partitions and replication factor 2.
    

    ls /
[admin, brokers, cluster, config, consumers, controller, controller_epoch, feature, ...]

ls /brokers/ids                    # one ephemeral node per live broker
[1, 2]
get /brokers/ids/1
{"endpoints":["PLAINTEXT://kafka1:9092"],"host":"kafka1","port":9092, ...}

get /controller                    # ephemeral: the broker in charge of the cluster
{"version":2,"brokerid":1, ...}

get /brokers/topics/orders         # which brokers hold each partition
{"partitions":{"0":[2,1],"1":[1,2],"2":[2,1]}, ...}
get /brokers/topics/orders/partitions/0/state
{"leader":2,"leader_epoch":0,"isr":[2,1], ...}
    
        
    Then broker 1, the controller, was stopped:
    

    ls /brokers/ids                    # its ephemeral node is gone
[2]
get /controller                    # broker 2 won the race to create it
{"version":2,"brokerid":2, ...}
get /brokers/topics/orders/partitions/0/state
{"leader":2,"leader_epoch":1,"isr":[2], ...}
    
        
    That is the whole mechanism. Brokers announce themselves with ephemeral nodes. The first broker to create /controller becomes the controller. When it dies, the node vanishes, the others are told through a watch, and one of them creates it again.
    
      
    

      
    
        
    See the election
    
        
    
          
    A model of three Kafka brokers on ZooKeeper. Stop and start brokers and watch the tree. In the model the lowest running id wins; on a real cluster whichever broker creates the node first wins.

    ZooKeeper answers short text commands on its client port. Only srvr is allowed by default. Allow more with 4lw.commands.whitelist in the config, or ZOO_4LW_COMMANDS_WHITELIST=ruok,srvr,mntr on the Docker image.
    

    echo ruok | nc localhost 2181      # imok

Connections: 1

    Disks and housekeeping
    
        
      
          
    • Every write is saved to the transaction log before it is confirmed. A slow disk makes the whole ensemble slow, so give the log a fast disk of its own.
      • 
          
    • Old snapshots and logs are not deleted by default. The Docker image ships with autopurge.purgeInterval=0, which means never. Set it to 1 (hours) or the disk fills.
      • 
          
    • Keep the servers close together. Spreading an ensemble across distant regions adds latency to every write.
      • 
          
    • Do not store large values, do not use it as a queue, and do not run two servers: two cannot survive one failure.
      • 
        
    
      
    

      
    
        
    Why Kafka left ZooKeeper
    
        
      
          
    • Two systems to install, secure, monitor and upgrade for one product.
      • 
          
    • When the controller failed, the new one had to load all metadata from ZooKeeper before it could work. With hundreds of thousands of partitions that took minutes.
      • 
          
    • Metadata lived in two places, the controller's memory and ZooKeeper, and they could drift apart.
      • 
        
    
        
    KRaft replaces it. A small group of Kafka nodes called controllers keeps the metadata as a Kafka log and agrees on it with the Raft protocol. Standby controllers already have the data, so failover is quick.
    
        
    
          
    QuestionKafka with ZooKeeperKafka with KRaft
    
          
    Systems to runKafka plus a ZooKeeper ensembleKafka only
    
          
    Where metadata livesZnodesAn internal Kafka topic, __cluster_metadata
    
          
    Who is controllerThe broker that created /controllerThe leader of the controller quorum
    
          
    Controller failoverSlower as partitions growFast, standbys are already in sync
    
          
    Kafka versionsUp to 3.9Production-ready from 3.3, the only mode from 4.0
    
        
    
      
    

      
    
        
    Moving an old cluster to KRaft
    
        
    You cannot upgrade a ZooKeeper cluster straight to Kafka 4. The path goes through 3.9, the last release that speaks both.
    
        
      
          
    • Upgrade the cluster to Kafka 3.9.
      • 
          
    • Start a new KRaft controller quorum with migration enabled. It copies the metadata out of ZooKeeper.
      • 
          
    • Restart brokers one at a time in migration mode. Metadata is now written to both places, so you can still roll back.
      • 
          
    • Restart brokers in KRaft mode, then finalize. After that there is no way back.
      • 
          
    • Shut ZooKeeper down, then upgrade to Kafka 4.
      • 
        
    
        
    This migration was not run for this guide. Follow the Apache Kafka documentation for your exact version and rehearse it on a copy of the cluster first.
    
      
    

      
    
        
    Where ZooKeeper still runs
    
        
    HBase, Hadoop high availability, SolrCloud and many older Kafka clusters depend on it. The same job is done by etcd in Kubernetes and by ClickHouse Keeper in ClickHouse. The ideas carry over: a small group that agrees by majority, temporary nodes or leases for liveness, and watches for change.

    Check yourself
    
        
    
          
    What is ZooKeeper for?
    Holding small shared facts that a cluster must agree on: who is alive, who leads, current configuration. It gives every client the same ordered view of changes.
    
          
    What is an ephemeral node?
    A znode tied to the session that created it. When the session ends or expires, ZooKeeper deletes it. It is how others learn a process has died.
    
          
    Why an odd number of servers?
    Changes need a majority. Four servers tolerate one failure, the same as three, so the extra server adds cost without adding safety.
    
          
    What happens when the ensemble loses its majority?
    The remaining servers stop serving requests. Refusing is safer than letting two halves of a split network accept different writes.
    
          
    How did Kafka choose its controller with ZooKeeper?
    Every broker tried to create the ephemeral node /controller. The one that succeeded became controller. The rest watched the node and raced again when it disappeared.
    
          
    Why did Kafka replace ZooKeeper with KRaft?
    To run one system instead of two, to remove the slow metadata reload on controller failover, and to support far more partitions per cluster.
    
          
    Can a ZooKeeper-based cluster upgrade directly to Kafka 4?
    No. Upgrade to 3.9, migrate the metadata to KRaft there, and only then move to 4.
