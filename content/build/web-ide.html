Visual Studio on a Mac. The full Visual Studio IDE runs only on Windows (the Mac edition was retired in 2024). What is installed here is Visual Studio Code, a different and lighter product. Their debug keys match: F5 start, F9 breakpoint, F10 step over, F11 step into. If you sit at a Windows Visual Studio one day, add Ctrl T go to anything, Ctrl . quick fix, F12 go to definition and Ctrl KthenCtrl D format.

Reading the key symbols

⌘ Command   ⌥ Option   ⌃ Control   ⇧ Shift   ⏎ Return   ⌫ Delete   ⎋ Escape. Two keycaps joined by "then" are a chord: press the first, release, press the second.

Function keys need one setting. On a Mac keyboard F5 to F12 change brightness and volume unless you hold fn. Debugging uses them all day, so turn on System Settings → Keyboard → Keyboard Shortcuts → Function Keys → "Use F1, F2, etc. keys as standard function keys". All keys in this guide are the macOS defaults; if one does nothing, look it up in that IDE's keymap screen, because a plugin or your own change may have taken it.

The five habits that make someone look fast

  1. Open by name, never by clicking through folders. One key, type three letters, Return.
  2. Run commands by name. You do not need to remember where a menu item lives if you can type its name in the command palette.
  3. Jump through code, do not scroll. Go to definition, find usages, go back. That is how you read a codebase you did not write.
  4. Let the IDE edit. Rename, extract, quick fix and multi-cursor change twenty places as safely as one.
  5. Pause the program instead of guessing. A breakpoint shows you the real values. A logpoint prints them without you touching the code.

Cursor: VS Code with an agent built in

Cursor is built on VS Code, so everything in the VS Code tab works here: the same layout, extensions, launch.json and debug keys. What Cursor adds is three AI surfaces: Tab completion as you type, the Agent pane that edits many files, and inline edit on a selection. You have version 3.29 installed.

  1. Activity Bar: Explorer, Search, Source Control, Run and Debug, Extensions.
  2. Side Bar: whichever view the Activity Bar selected.
  3. Editor: grey text is a Tab suggestion; red/green blocks are an agent edit waiting for review.
  4. Agent pane: your prompt, the mode and model pickers, each step the agent took, and the review button.
  5. Panel: Terminal, Problems, Output, Debug Console.
  6. Status bar: git branch, error count, Tab status.

Working with the agent like a pro

  • Say where, what, and how you will check. "In @cart.ts, the discount is applied as a multiplier instead of a percentage. Fix it and run the cart tests." beats "fix the bug".
  • Plan first for anything over one file. Read the plan, correct it, then let it edit.
  • Read every diff. Keep or undo block by block. An agent edit is a pull request from a fast junior, not a finished change.
  • Rules save repeating yourself. Project rules live in .cursor/rules; your global ones are in Cursor Settings → Rules → User Rules. Yours already tell Cursor to read ~/ai-handoff first.
  • Use checkpoints. Each agent message has a restore point, so you can go back to the state before a bad turn.
  • Paste the error, not a description of it. Stack trace and failing command go in as text.
  • Debugging with it. Ask the agent where to put a breakpoint and what to look at, then run the debugger yourself. It reasons about the code; only the debugger knows the real values.

Keys

Debugging: launch.json

VS Code needs to be told how to start or join your program. That lives in .vscode/launch.json. launch starts the program under the debugger; attach joins one that is already running.

{
  "version": "0.2.0",
  "configurations": [
    { "name": "Node: this file", "type": "node", "request": "launch",
      "program": "${file}", "skipFiles": ["<node_internals>/**"] },
    { "name": "Python: FastAPI", "type": "debugpy", "request": "launch",
      "module": "uvicorn", "args": ["app.main:app", "--reload"], "justMyCode": true },
    { "name": "Attach to Node on 9229", "type": "node", "request": "attach", "port": 9229 }
  ]
}
  • F5 runs the configuration selected at the top of the Run and Debug view.
  • skipFiles and justMyCode stop Step Into from diving into library code.
  • For Node without any config: open the command palette, run "Debug: JavaScript Debug Terminal", then start your app normally in that terminal. Breakpoints just work.
  • Right-click the gutter for Conditional Breakpoint, Logpoint and Hit Count. Logpoint text uses braces: sum is {sum}.
  • In the Call Stack, right-click a frame → Restart Frame to re-run a function without restarting the app (where the debugger supports it).

Pro tricks

  • code . in a terminal opens the current folder. Both code and cursor are already on your PATH.
  • In ⌘ P: type @ for symbols in the file, :42 for a line, > for commands, # for symbols in the project.
  • Settings have two levels: User (all projects) and Workspace (.vscode/settings.json, shared with the team). Workspace wins.
  • Profiles keep separate extension sets, for example one for Python and one for web.
  • Useful extensions: Dart + Flutter, Python, ESLint, Prettier, GitLens, Error Lens, REST Client, Remote - SSH, Docker.
  • tasks.json + preLaunchTask builds before each debug run.
  • Snippets: command palette → "Snippets: Configure Snippets". Type the prefix, press Tab.
  • AI in plain VS Code is GitHub Copilot: ⌘ I inline chat, ⌃ ⌘ I chat view.

Debugging here

  • Debug an app that is already running: Run → Attach Debugger to Android Process. No rebuild needed.
  • Right-click the red dot for Condition, and to untick Suspend and tick "Evaluate and log" (that is this IDE's logpoint). ⇧ click on the gutter creates a non-suspending one directly.
  • Suspend: Thread, not All. In the same popup. With All, every thread freezes and the app may show "not responding".
  • Exception breakpoint: ⇧ ⌘ F8 → + → Java Exception Breakpoints. The app pauses at the line that throws, before the stack unwinds.
  • Evaluate ⌥ F8 runs any expression while paused, including calling your own functions.
  • Reset Frame (the arrow beside a frame in Frames; older versions call it Drop Frame) rewinds to the start of the current function.
  • Other inspectors: Layout Inspector (live view tree), App Inspection (database and network), Profiler (CPU, memory).

Debugging a request end to end

  1. Start the app with 🐞, not ▶.
  2. Put a breakpoint on the first line of the controller method.
  3. Right-click the red dot and set Suspend: Thread. A server handles many requests at once; with All, every other request freezes too.
  4. Send the request from the HTTP client, Postman or curl. The app pauses.
  5. Step into the service, then the repository. Use Evaluate ⌥ F8 to call repository.findById(42) on the spot.
  6. Read the Frames list from the bottom: filter chain → dispatcher → your controller. That is the path every Spring request takes.
  • Only one bad request? Add a condition: id == 42.
  • A 500 with no clue? Add a Java Exception Breakpoint for the exception class named in the log.
  • Stream pipeline wrong? While paused on a .stream() chain, press "Trace Current Stream Chain" in the Debug toolbar to see the data after each step.
  • SQL looks wrong? Set spring.jpa.show-sql=true and watch the console while stepping.

Breakpoints in Xcode

  • Edit a breakpoint: double-click it. You get Condition, Ignore (skip the first N hits), Action, and "Automatically continue after evaluating actions".
  • Logpoint: Action → Log Message, text like sum is @sum@, and tick Automatically continue. It prints and never stops.
  • Breakpoint navigator ⌘ 8 → + gives the special kinds: Swift Error, Exception (Obj-C crashes pause at the throwing line), Symbolic (stop in any function by name, even one you have no source for, such as -[UIViewController viewDidAppear:]), Runtime Issue, Test Failure.
  • Share one: right-click → Share Breakpoint puts it in the project for the team. Move to User to have it in every project.
  • Watchpoint: right-click a variable in the Variables view → Watch. The app pauses when the value changes, whoever changed it.

LLDB console: the ten commands

Flutter DevTools

A set of inspectors that connect to a running Flutter app. The IDE debugger answers "what is the value on this line"; DevTools answers "why is this widget this size", "why is this screen slow" and "what did the app send over the network". You have Flutter 3.41.4.

  1. Tool tabs. The set depends on the app type and build mode.
  2. Inspector toggles that draw on the device itself.
  3. Widget tree. Select widget mode lets you tap a widget on the device to find it here.
  4. Layout explorer for the selected Row, Column or Flex: change alignment and flex live to test a fix.
  5. Properties of the selected widget, including the constraints it received and the size it chose.

How to open it

  • Android Studio: once Run or Flutter Attach is connected, click the DevTools button in the Run / Debug window toolbar, or open the Flutter Inspector tool window on the right.
  • Terminal: flutter attach prints a line with a DevTools link. Open it in Chrome.
  • Standalone: run dart devtools, then paste the "Dart VM service is listening on …" URL into its connect box.
  • VS Code / Cursor: command palette → "Flutter: Open DevTools".

Your BigBasket setup. For iOS the path is the same as for breakpoints: Flutter Attach first, then run from Xcode, then open DevTools from the attach session. Dart debugging tricks that pair with it

  • debugger() from dart:developer is a breakpoint written in code; debugger(when: cart.isEmpty) is a conditional one.
  • Hot reload keeps state and breakpoints; hot restart resets state. If a change does not show, it was probably in initState or a global, which need a restart.
  • Performance → "Track widget builds" shows which widgets rebuild each frame. A whole screen rebuilding on every tap is the most common cause of jank.
  • "Highlight repaints" draws a colour-cycling border around anything that repaints. A list that flashes while only one item changed needs a RepaintBoundary or a narrower rebuild.
  • debugDumpApp() prints the widget tree to the console when you cannot open the Inspector.
  • Exception breakpoints work for Dart too: in Android Studio tick "Break on exceptions" in the Flutter debug settings, or use the Breakpoints dialog.

Breakpoints and debugging

A debugger does three things in every IDE: it pauses your program at a line, shows you every value at that moment, and lets you move forward one step at a time. Practise here first, then do the same in a real IDE.

Missions

  1. Put ● on line 10, press Start. Read discountPct in Variables. Step over once and read discount. What should line 10 have been?
  2. Restart. Put ● on line 8 and press Step over, then Step into, at the same point. Watch the Call stack to see the difference.
  3. While inside lineTotal, press Step out. Where do you land?
  4. Change line 8 to ◐. Continue now skips the first pass through the loop. Why?
  5. Change line 8 to ◆ and remove everything else. Press Start: the program never pauses, yet the console shows sum on each pass.

Reading the paused screen

  • Call stack (Frames): the top line is where you are; each line below is who called it. Click a lower frame to see that caller's variables at the moment it made the call.
  • Variables: everything in scope. Values that just changed are highlighted.
  • Watch: expressions you pin so they stay visible as you step, such as items.length.
  • Evaluate / console: run any expression against the paused program. You can call functions and change values to test a fix before writing it.
  • Threads: mobile apps have many. UI work must be on the main thread; the stack tells you which one you are on.

When a breakpoint is ignored. Check, in order: you pressed Debug and not Run; breakpoints are not muted; the build is Debug, not Release; the running app was built from the code you are looking at; the debugger is attached to the right process (for BB Flutter that means Flutter Attach was waiting before the app started).

Postman

The workbench for calling APIs by hand: build a request, read the response, save it, and run a whole set as a test. It is to backend work what the debugger is to code. You have Postman 12.36.

  1. Header: workspace switcher, search, and the active environment.
  2. Sidebar tabs in Postman 12: Items (Collections, Environments, Specs, Flows), Services, History of everything you sent, and Local Files.
  3. Request builder: method, URL, Send, and tabs for query params, auth, headers, body and scripts.
  4. Response: body with status, time and size; tabs for cookies, headers and test results.
  5. Footer: the Console shows the exact request that left your machine, after variables were filled in. Globals, Vault and Tools (Runner, Cookies, Trash) also live here.

When two scopes define the same name, the narrower one wins: local, then environment, then collection, then global. Hover a {{variable}} in the URL to see which value it resolved to.

Tokens. A variable's value syncs to the Postman cloud and to anyone in a shared workspace unless you mark it sensitive or keep it in the Vault. Put real tokens in the Vault, never in a collection you export or share.

Scripts: turning a request into a test

The Scripts tab has two slots. Pre-request runs before sending; Post-response runs after and is where tests go. Both are JavaScript with a pm helper.

// Post-response on "POST /login": check, then save the token for later requests
pm.test("status is 200", () => pm.response.to.have.status(200));
const body = pm.response.json();
pm.test("has a token", () => pm.expect(body.token).to.be.a("string"));
pm.environment.set("token", body.token);

// Pre-request anywhere: a fresh value on every send
pm.variables.set("requestId", crypto.randomUUID());
console.log("sending with", pm.variables.get("requestId"));
  • Auth once, not per request: set Authorization on the collection (Bearer {{token}}) and leave each request on "Inherit auth from parent".
  • Run them all: right-click a collection → Run. Requests go in order, tests are counted, and a CSV or JSON data file repeats the run once per row.
  • From the terminal or CI: the Postman CLI runs the same collection without the app.

Postman has no breakpoints. Its debugger is the Console ⌥ ⌘ C, which shows the real URL, headers and body that were sent, plus every console.log from your scripts.

Pro tricks

  • Paste a whole curl … command into the URL box; Postman turns it into a request.
  • Code in the right sidebar (the </> icon) gives the request as cURL, Swift, Kotlin, Dart, Python or JavaScript code.
  • Save a response as an Example; a Mock Server can then return it, so the app can be built before the backend is ready.
  • Import an OpenAPI file to get a full collection with every endpoint.
  • Fork a shared collection before you experiment, so teammates' copy is untouched.
  • Claude and Cursor can read your Postman workspace through the Postman connector you already have set up.
